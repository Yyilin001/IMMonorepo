# 涟漪 · Local IM

一个完全本地运行的 Flutter IM 演示与性能实验项目。默认生成 **10,000 个会话**，启动后默认**每 3 秒接收 1 条**本地 Mock 消息，可切换到每秒 100、1,000、3,000 或 5,000 条。无需后端、账号、数据库或网络资源。

## 运行

本项目使用本机 Flutter **3.50.0 / Dart 3.14.0** 创建，Material UI 依赖与当前 SDK 模板保持一致。

```bash
flutter pub get
flutter run -d macos --profile
```

macOS Release/Profile 构建仅支持 Apple Silicon（M 系列），已在项目 `pubspec.yaml` 中配置，不依赖本机全局 Flutter 设置。

Android 在 `android/app/build.gradle.kts` 中限定为 `arm64-v8a`，默认 APK 和 AAB 均只包含这一种架构。直接使用下列命令，无需添加架构参数或 `--split-per-abi`：

```bash
flutter build apk --release
flutter build appbundle --release
```

APK 输出为 `build/app/outputs/flutter-apk/app-release.apk`，AAB 输出为 `build/app/outputs/bundle/release/app-release.aab`。Android 运行设备也需要支持 arm64。

也生成了 iOS、Android 工程。通过 `flutter devices` 找到设备后运行：

```bash
flutter run -t lib/mock_main.dart -d <device-id> --profile
```

iOS 真机需要本机有效的开发签名。性能应在目标真机的 Profile/Release 模式下复测；Debug 或模拟器结果不能代表真机表现。

## 原生 Android Compose 版

用 Android Studio 打开 [compose-android](../compose-android)，选择 JDK 17 和 Android SDK Platform 36，运行 `app`。最低运行版本为 Android 12（API 31）。应用名为「涟漪 · Compose」，可与 Flutter 版同时安装。

```bash
cd compose-android
./gradlew :app:assembleDebug
./gradlew :app:installDebug
```

页面使用 Jetpack Compose 和 Navigation 3。路由只携带类型与标量参数。会话、消息、设置和分页窗口通过只读状态流发布，嵌套集合使用 Kotlin 持久化集合。会话列表按不可变排序树取行，更新单条消息时共享其余子树。应用偏好、联系人备注与删除状态、最近搜索保存在设备上。聊天记录、草稿、个人资料和模拟运行统计按本次运行保留。

`./gradlew :app:testDebugUnitTest` 验证排序快照、游标和缓存边界。连接 Android 12 设备后，`./gradlew :app:connectedDebugAndroidTest` 运行原生交互测试。下文的 Flutter 性能数据仅对应原 Flutter 工程。

## 已实现

- 10,000 个可搜索会话，支持未读筛选、置顶、全部已读。
- 会话长按菜单支持置顶/取消置顶、免打扰开关、单个会话标为已读；文字气泡长按可复制文字，图片气泡长按可查看预览；实时消息、历史消息及自己发送的消息均可使用。手机会话操作使用带头像的圆角底部面板，消息复制使用贴近气泡的紧凑深色浮层；桌面同时支持圆角右键菜单。菜单固定按下时的目标，重排或消息窗口淘汰不会误操作其他内容，也不会为未打开的会话创建聊天窗口。
- 手机底部“消息 / 联系人 / 我”，桌面侧栏提供相同入口；按需创建页面并保留各标签状态。
- 联系人目录支持好友/群聊筛选、姓名/账号搜索；查看个人或群聊资料后可发起聊天。
- 聊天头像可打开资料；个人页支持查看、编辑昵称、地区和签名，取消编辑不会保存。
- 桌面多栏工作台；手机采用会话首页与全屏聊天，iPhone 支持侧滑返回，保留搜索和列表位置。中文界面与离线头像。
- 手动发送、立即本地回显、650ms 后模拟回复、会话草稿。
- 点击聊天输入栏的「+」在输入栏下方展开附件面板。iOS 和 Android 可选「相册」或「拍照」，macOS 点击「相册」打开文件选择器。预览并确认后发送，保留文字草稿。图片复制到应用私有目录，消息显示缩略图，点击或长按可查看大图。实时 Mock 和预置历史中的图片继续使用占位卡片，会话摘要显示“[图片]”。聊天记录仍按本次运行保存。
- 历史记录游标分页：进入会话首批加载 100 条（已有少量实时缓存时补足），上滑自动加载，后续每页 100 条，支持加载中、失败重试和没有更多记录。
- 历史场景开关：正常、慢速、离线、下次失败、重复与乱序回包。
- 原生独立 Isolate 逐条生成消息；3 秒/条及 100/1k/3k/5k 每秒档位，可暂停与恢复，可切换热点/全量均匀随机模式。
- 接收速率曲线、累计接收、缓存数量、淘汰数量、单条处理耗时、状态通知耗时、帧耗时指标。手机运行监控使用大字号分组卡片，速率按钮至少 52 点高，开始/暂停固定在底部，支持窄屏和字体缩放。
- “3 秒/条”从启动或恢复起等待 3 秒生成一条消息，切换会话或分布模式不会重置发送期限；低频档不追赶补发，消息仍逐条接收和发布。
- 浏览会话列表时锁定顺序，回到顶部恢复按最新消息排序。
- 阅读历史时保持当前位置，新消息在接收时逐条追加到底部并更新提示；在底部时自动跟随，点击“回到最新”可直接回到实时窗口。
- 跟随最新时，文字和图片新消息以 180 毫秒淡入并轻微上移；完整高度立即参与布局，动画不延迟入库或 Riverpod 发布。历史补页、阅读旧消息、滚动中及系统减少动态效果时跳过动画；100 条/秒及以上模拟接收跳过动画，手动发送仍可播放，同时最多 4 条动画，屏外消息不补播。
- 最近 20 个聊天窗口按会话独立保留：切换后恢复分页、滚动位置、历史阅读状态和新消息计数，草稿独立保存。

暂停按钮控制压测消息源；手动发送、历史请求与模拟回复仍然可用。会话记录、历史档案、草稿和未读仅存于内存，重启恢复初始数据。

## 手机体验

手机启动进入会话列表，底部可切换“消息 / 联系人 / 我”；点开会话进入独立聊天页面，返回或 iPhone 侧滑保留搜索、筛选与列表滚动位置。聊天正文为 16pt，使用紧凑输入栏、44pt 发送按钮，键盘弹出时聊天内容随可用空间调整。统计卡片不常驻聊天页面，模拟流量控制收纳在会话首页的监控面板中。iOS 桌面显示名称为“涟漪”。

会话行的手势识别器按展示位置保持稳定，按下时记录当时看到的会话 ID；按住期间即使连续重排，松开仍打开原会话。拖动或取消不会打开聊天，无障碍激活使用当前显示的会话。不冻结触摸期间的排序，也不引入计时合并。回归测试覆盖触摸、鼠标、连续 100 次重排、尚未绘制的状态更新、取消、拖动和无障碍点击。

界面导航不改变逐条接收和 Riverpod 细粒度发布。测试覆盖小屏键盘避让、发送和草稿恢复、侧滑返回后的列表位置，以及原有组件重建范围。

“我”和“我的资料”右上角提供应用设置入口，支持聊天字号、默认背景、新消息动画、长按触感、导航未读角标和会话内容预览，另有编辑资料、关于和恢复默认入口。应用偏好通过 `shared_preferences` 保存到本机，启动时恢复；各设置立即更新独立 Riverpod 状态，保存操作顺序执行并可在失败后重试。恢复默认只重置应用偏好，不删除消息、资料或会话单独背景。字号作用于消息正文与输入框；默认背景不会覆盖单独设置的会话背景。关闭角标不改变未读计数，关闭预览只隐藏会话列表内容，实时消息仍逐条处理。

设置测试覆盖序列化兼容、快速连续修改与保存顺序、保存失败重试、默认背景与会话覆盖、手机/桌面导航、320px 与 1.6 倍字号布局、真实聊天开关效果，以及 1,000 条消息不重建设置页。

联系人资料支持备注、最多 6 个标签、电话号码和补充说明，提供昵称、地区、签名、添加来源与时间，群聊显示群名、成员数量、群介绍和加入信息。备注优先显示于联系人、会话列表和聊天标题，保留原昵称，并支持按备注拼音、原昵称、账号或标签搜索联系人。资料页右上角可编辑备注、置顶和设置免打扰；电话与账号可复制。用户填写的信息独立保存在本机，重启恢复；他人的昵称、地区及签名仍是只读模拟资料。

联系人编辑只发布相应资料及目录变化，不改变会话时间、顺序或未读，也不创建未打开会话的消息列表。资料设置里的置顶/免打扰与聊天页同步，消息到达不会通知这些控制项。新增测试覆盖本机恢复与失败重试、备注清空/取消/排序/搜索、聊天标题同步、复制电话、群聊表单、320px 大字号，以及 1,000 条消息的资料页重建隔离。

联系人设置提供红色“删除联系人”按钮，确认后从通讯录和搜索结果移除，停止模拟收发并取消该联系人的待回复任务。删除状态保存在本机，已有会话、聊天记录、备注和草稿保留；原会话输入区显示已删除提示，可在资料页或输入区重新添加。群聊不提供好友删除操作。删除失败可重试，异步保存完成不会误关闭用户已返回的其他页面；测试覆盖这些路径及 1,000 条被删除联系人的到达事件不会入库或创建会话。




## 联系人与资料

联系人按姓名拼音、英文字母排序，非字母开头归入末尾的 `#` 组；同名按稳定 ID 排序。好友、群聊和搜索结果使用相同规则，右侧字母索引可直接跳到对应分组，也可用完整拼音搜索。拼音转换采用 [lpinyin](https://pub.dev/packages/lpinyin)，排序键仅在目录创建时计算，与实时会话排序分离。好友和群聊均从已有会话元数据建立目录，默认共 10,000 个条目；列表懒加载，详细资料按 ID 按需生成，不为每个联系人预建状态对象。手机可以从资料页进入聊天，返回时保留资料页及联系人搜索；桌面“发消息”返回消息工作台并选中对应会话。聊天头像打开资料后，“发消息”返回已有聊天。

“我 → 我的资料 / 编辑资料”可以修改昵称、地区和签名。输入空昵称会提示修正，保存后个人页与资料页立即同步。当前为本地 Mock：联系人资料固定生成，个人修改仅保存在当前应用内存，重启恢复默认；界面明确显示这一范围。

`contactDirectoryProvider`、`contactResultsProvider`、`contactProfileProvider(id)` 与消息预览/排序状态分离；`myProfileProvider` 单独发布个人资料，`workspaceSectionProvider` 管理标签选择。隐藏标签暂停 UI 订阅，业务数据仍逐条处理与发布，不新增定时合并。新增测试覆盖目录搜索、资料按需创建、好友/群聊聊天路由、资料保存/取消、桌面入口，以及隐藏消息页时 1,000 条消息的逐条同步通知和联系人重建隔离。

## 聊天设置与未读提示

聊天右上角的“…”打开设置页，可查看好友或群聊资料、置顶聊天、设置免打扰、查看历史记录，以及选择浅白、薄荷、暖杏三种背景。免打扰在本地 Mock 中表现为会话静音标记和灰色未读标记，消息仍照常接收并计入总未读。置顶影响实际会话排序；背景按会话独立生效。设置在聊天窗口缓存淘汰后仍保留，但应用重启恢复默认。

手机底部“消息”和桌面侧栏显示总未读角标，超过 99 显示 `99+`，无障碍标签保留完整数量；为零时隐藏。独立的 `totalUnreadProvider` 在每条消息处理、进入会话和全部已读操作中同步发布，不依赖性能采样定时器，也不重建整个导航栏。

聊天滚动指示器在滚动时出现，停止后自动淡出；仅有实时消息追加时不会常显。新测试覆盖 iOS 实际淡出动画、字母跳转及搜索、设置与聊天路由、背景隔离、设置页高频收消息不重建，以及总未读逐条通知与清零。

## 切换消息分布

在“运行监控 → 消息分布”选择模式；手机通过会话首页右上角的监控按钮打开面板。

- **热点模式**（默认）：有当前会话时，10% 定向发送给当前会话、20% 在 ID 前 100 个会话中随机选择、70% 在全部会话中随机选择。未选择会话时，前两部分合为 30% 热点流量。
- **全量均匀随机**：每条消息在全部会话中独立等概率抽取，忽略当前会话和热点权重。允许连续选中同一会话，不保证有限时间内每个会话收到相同数量的消息。

运行中可直接切换；暂停时可预先选择，恢复后使用所选模式。切换不清空消息、不重置消息 ID、不改变速率，也不更改置顶。前 3 个会话默认置顶，如需观察普通会话上浮，可在聊天标题取消置顶。随机种子仍固定，便于复现测试。

配置到达 Isolate 后用于后续生成的每条消息；切换前已发送的少量在途消息仍按原目标处理。两种模式共用逐条事件、逐条 ACK 和同步通知路径，没有毫秒合并。

## 体验历史场景

1. 打开会话，上滑到顶部，或点击聊天标题右侧的历史按钮。首次进入加载 100 条，后续每次读取 100 条，补页保持已有消息位置。
2. 在右侧“运行监控”向下滚动至“历史记录场景”；手机从会话首页右上角的监控按钮打开面板。
3. 切换“慢速”查看加载状态；切换“历史服务离线”触发错误，恢复“正常”后点击聊天里的“重试加载”。“模拟下次请求失败”只影响下一个历史请求。
4. “重复与乱序回包”让 Mock 返回重复消息和打乱的页面，客户端按稳定 ID 去重、按历史序号恢复顺序。
5. 压测开启时阅读历史，新消息继续入库，右下角显示新消息数量。点击它回到最新，再上滑可补回阅读期间到达的消息。

阅读历史只暂停自动滚动，不暂停消息追加。窗口有空间且记录连续时，每次 `receive()` 返回前，新消息就已进入聊天列表并同步发布；即使模拟历史服务离线也不受影响。`pending` 记录阅读期间的新消息提示数量，`unloadedNewer` 只记录超出内存窗口的未加载后缀。到达真正的最新记录后清除提示并恢复自动跟随；显式点击“回到最新”或发送消息可直接到最新。

消息列表使用双向 Sliver 和稳定的阅读原点，向新方向扩展不会把旧记录挤走；各会话保留原点及带符号的滚动偏移。阅读窗口达到 2,000 条后保留正在看的记录，超出的后续消息仍逐条入库、归档并更新计数；向下滚动到已加载末端时，再按游标每次补接 30 条并淘汰最旧部分，必要时在同一可见边缘重设坐标原点。补页的模拟网络延迟不参与实时收消息路径。新端请求失败可重试，返回最新或窗口淘汰使旧请求失效；档案过期导致无法连续补齐时明确提示，不自动跨越缺口。

预置数据包含：林知夏 8 条、Flutter 技术交流 12,000 条、陆星野无预置记录，其余会话通常有 360～630 条。实时流可能继续给这些会话增加消息；预置记录按页生成，不会一次创建所有会话的完整历史。


## 数据与渲染设计

```text
Mock Isolate：按每条消息的生产时间逐条发送
       │ 每条一个 SendPort 事件、一个 ACK
       ▼
ChatEngine.receive：立即入库、更新未读、更新排序索引
       │ 同步通知，没有业务层等待窗口
       ├── ConversationListNotifier → 行 / 数量 Notifier.state
       └── TimelineStructureNotifier → 单消息 / 结构 Notifier.state
           （Store 只更新索引、返回差异，不持有监听器）
       ▼
Flutter 正常帧调度 + ListView.builder 按需构建可见内容
```

- **不使用固定毫秒窗口合批、debounce、throttle 或自定义按帧延迟发布。** `receive()` 返回前，模型、会话排序索引及监听者通知均已更新。每条消息单独传递，不打包成列表。
- 会话排序使用带子树大小的 Treap 有序索引，单条更新与按位置读取为期望 O(log N)，无需每条消息重新排序或复制 10,000 行。UI 构建时只读取可见位置。
- 置顶会话优先，同组按最后收发的本地序号降序，同序号按会话 ID 升序。历史页面按独立的历史序号去重排序，回填不会改变会话预览、未读数和实时吞吐计数；实时流仍不模拟网络乱序校正。
- `ConversationStore` 是只读**实时视图**，包含当前搜索、未读筛选与锁序投影，不应当作可长期持有的历史快照；确需完整不可变副本时显式调用 `engine.snapshot()`，实时接收路径不调用它。筛选条件变化时重建投影，实时消息只增量更新发生变化的会话。
- Flutter 按正常屏幕帧调度绘制；逐条通知不意味着每条消息都产生一个物理屏幕帧，也没有额外人为等待。
- 会话列表每行固定 82px，使用懒加载，避免一次创建上万个 Widget。
- 浏览列表时仍保留位置保护：只锁定展示顺序，底层索引始终逐条正确更新。回到顶部立即恢复当前排序；此行为由用户滚动触发，不依赖定时窗口。
- 实时缓存全局最多 **40,000 条**，每个会话最多 **500 条**，初始跟随实时流时保留约 **200 条**的窗口；点击回到最新保留已经加载的窗口容量，最多 **2,000 条**。阅读窗口最多 **2,000 条**；达到上限后保留当前阅读区域，向新端移动时分页滑动窗口，也可直接回到最新。
- Mock 历史档案独立保留最多 **100,000 条实时消息**，单会话最多 **5,000 条**，因此实时缓存淘汰后仍能从历史档案补回。预置历史按游标确定性生成，不占用这份档案的空间。历史档案超限后淘汰最旧实时记录，并在跨过缺口的历史页明确提示，不假装拥有无限历史。
- 请求使用排他的历史序号游标而不是偏移量，实时新消息不改变旧页边界。同一会话的重复触发不发起并行分页；A→B→A 复用 A 的在途请求，各会话的回包只写入自己的窗口。窗口被淘汰或返回最新导致请求过期时，旧结果被忽略。
- 向历史方向滚动时，距顶部约 3 屏便提前加载下一页（触发距离限制在 1,200～3,600 逻辑像素）。按距离立即触发，不使用时间合并；请求在途、历史耗尽、窗口已满时不重复加载，失败后由用户重试，补页保持当前阅读位置；新页完成布局后才使用新的滚动距离判断，避免惯性滚动期间按旧距离多取一页。
- 阅读历史时保留现有消息位置，旧页追加到历史端，新消息逐条追加到新端；窗口内可直接连续浏览，不等待历史请求。点击回到最新优先保留当前消息列表，只重设滚动原点，不重新加载近期窗口、不因数量不足补页。若已接收的新消息超过阅读窗口上限，先同步拼接本地缓存中连续的新端记录；无法接续时只展示本地已有的连续最新段，避免拼接出未声明的消息缺口，全程不发起历史请求。每个保留的 Session 额外引用最后一条实时消息，保证全局缓存淘汰后仍可立即定位最新。
- 全局双向链表与每会话队列共享节点，淘汰为 O(1)。会话摘要在历史消息淘汰后仍保留。
- 独立消息通道最多有 64 条未确认消息；达到上限时暂停生成，收到单条 ACK 后继续，避免无限积压。此数量上限不延迟已收到消息的处理。
- Mock 生产端按目标速率计算每条消息的到期时间。操作系统定时器精度可能让相邻事件靠得很近，但每条消息仍独立发送、处理和通知。
- 默认热点流量优先覆盖当前会话和前 100 个热点会话；全量均匀随机模式按全部会话等概率抽取，两种模式都逐条处理。
- 缓存上限约束的是消息条数，不是整个进程的内存字节数。

性能仪表每 500ms 采样一次；650ms 用于模拟对方回复；历史请求的 100ms/1.5s 用于模拟响应延迟。这些时间均不用于合并实时消息，历史请求完成后立即发布结果。

## Riverpod 状态架构

使用手写 Provider，无需代码生成。`lib/core` 的数据模型、排序与 Store 不依赖 Flutter / Riverpod；`lib/state` 负责业务状态、依赖组装和生命周期；界面通过 `ref.watch` 订阅，通过 `ref.read(...notifier)` 调用操作。

| Provider / 模块 | 职责与生命周期 |
| --- | --- |
| `engineProvider` / `historyRepositoryProvider` | 应用作用域的数据与历史仓库，页面卸载不清空数据 |
| `conversationStoreProvider` / `timelineStoreProvider(id)` | 纯数据投影、消息窗口和位置索引；无回调、无通知 |
| `conversationListProvider` | 搜索、未读筛选、锁序、全部已读，以及行/数量状态的同步发布 |
| `selectedConversationProvider` | 当前会话选择与已读处理 |
| `chatSessionProvider(id)` | 各会话独立的置顶、分页、请求代次、阅读冻结、新消息计数和滚动位置 |
| `chatSessionsProvider` | 按最近打开顺序保留最多 20 个 Session，淘汰时撤销 keepAlive |
| `conversationRowProvider(index)` | 自动释放的行订阅，位置对应内容改变时同步更新 |
| `messageProvider((conversationId, messageId))` | 自动释放的单消息订阅，内容变化或从窗口移除时同步更新 |
| `conversationCountProvider` / `timelineStructureProvider(id)` | 数量独立通知；消息写入统一经过结构 Notifier，直接更新对应消息状态 |
| `listProviderRegistryProvider` | 缓存已创建的原生 Riverpod Notifier 引用，随 build/onDispose 维护；不保存用户监听回调 |
| `mockRuntimeProvider` / `historyScenarioProvider` | Isolate 启停、速率、错误与历史故障模拟 |
| `draftProvider(id)` / `draftStoreProvider` | 单会话草稿独立通知；Provider 自动释放，非空草稿保留到应用结束，发送后删除 |
| `metricsProvider` | 性能采样与帧回调，独立于逐条状态更新 |
| `messageActionsProvider` | 逐条收发命令、Mock 回复；销毁作用域时取消待执行回复 |

列表项是 Riverpod 原生 Notifier family，**不会全部监听一个全局列表或版本号再执行 select**。`ConversationListNotifier` 在更新索引后，仅比较已创建行 Provider 的显示字段，直接提交变化行的 `state`。`TimelineStructureNotifier` 根据单次数据变更返回的 ID 差异，直接提交对应消息 Provider 的 `state`；仅插入、删除、重排时更新自己的结构版本。当前选择、置顶、历史提示等小状态使用 `select` 限制组件重建。

Engine / Repository 保存消息数据，Session 管理独立的阅读窗口，Store 仅提供展示索引和同步的差异计算。已删除 `observeSlot`、`observeCount`、`observeMessage`、`observeStructure` 及全部 Store 监听器集合。消息新增、删除、重排与内容修改分开通知，最近窗口和历史阅读窗口都有上限，不会逐条复制万级会话全集。排序变化仍需要更新受影响的显示位置。

应用根部 `ProviderScope` 拥有资源；Repository、Isolate、采样定时器、帧回调、Mock 回复通过 `ref.onDispose` 清理。测试使用独立 `ProviderContainer` 和资源 override，避免全局单例污染。聊天窗口按会话 ID 隔离，最近打开的 20 个 Session 通过 keepAlive 保留；超出上限时释放最久未打开的窗口，旧页不能写入再次打开的新 Session。初始窗口按需创建，万级联系人不会各自创建一个 Provider。

保留窗口内，历史阅读模式下的后台消息也逐条追加到窗口，保持旧记录及阅读原点，达到窗口上限后的后续记录按需补页；跟随最新的后台窗口逐条更新。UI 使用带会话 ID 的组件 Key、阅读原点和该会话的滚动偏移恢复位置。返回最新将偏移重置为 0，保留已加载列表并使在途补页失效；尚未加载任何消息时保留原始首次请求。超过缓存上限后，分页和滚动位置会丢弃，再次进入从近期消息重新开始；消息仓库和非空草稿不随窗口淘汰。各 Session 最多展开 2,000 条，默认保留窗口的消息项总数上限为 40,000（资源回收期间可能短暂存在正在卸载的窗口），并非为所有会话无限保留历史。

启动时的 microtask 仅用于在 Widget 构建结束后启动 Mock 和初次历史加载。**实时消息没有 microtask、定时器或按帧合并发布。** Riverpod/Flutter 的正常绘制与自动释放调度，不改变 `receive()` 返回前已完成业务更新的保证。

## 每条消息的重建范围

状态管理使用 **flutter_riverpod 3.5.0**，通过 `ProviderScope`、`NotifierProvider`、参数化 Provider 和 `Consumer` 实现。已移除原来的 `ChatController`、`ChangeNotifier` / `ValueNotifier` 状态通道与 `ValueListenableBuilder`。UI 按显示字段订阅。

| 场景 | 组件重建范围 |
| --- | --- |
| 会话内容变化，位置不变 | 只有对应的已挂载会话行；其他行和列表容器不重建 |
| 屏外会话更新，未影响已挂载位置 | 无会话行重建 |
| 新消息让会话排序前移 | 只更新内容或占位会话发生变化的已挂载位置；列表容器不重建 |
| 当前聊天新增消息 | 更新消息列表结构；新增消息组件，复用已有消息组件 |
| 单条消息内容变化，ID 与顺序不变 | 只重建对应消息气泡 |
| 加载历史页 | 更新消息列表结构，复用已有消息组件，更新历史加载提示 |
| 阅读历史时收到新消息 | 更新新消息计数，历史消息窗口保持不变 |
| 切换选中会话 | 会话列表只更新旧、新选中行；聊天区域切换内容 |

会话行按可见位置建立订阅（包含 ListView 预加载区域），仅在显示字段变化时通知。数量未变时不触发列表容器的 builder；数量变化仍需更新列表结构。消息使用稳定 ID、`findChildIndexCallback` 和缓存的 Widget 实例保留已有元素；每条已挂载消息独立订阅自己的内容。行与消息 Provider 使用 `autoDispose`，失去订阅后由 Riverpod 回收并移除对应的 Notifier 引用；Widget 缓存有上限。资源回收调度不参与消息接收或状态发布。

排序移动会影响被挤动的位置，插入消息也需要列表布局，因此不能把“只重建变化组件”理解为“完全不发生列表结构更新或布局”。不会为每条新消息重新 build 所有已有消息气泡。聊天标题的置顶按钮只订阅当前会话的置顶状态；历史提示只订阅实际显示字段，游标变化不单独触发提示重建。性能仪表仍按独立采样周期更新。

## 当前边界

本项目模拟文本消息、收发与在线状态，不包含真实网络、登录、附件传输、语音视频、磁盘持久化、断线重连或服务端一致性。当前消息源使用 `dart:isolate`，面向原生平台；没有配置 Web 版本。
