# 服务端消息链路的模型与 PB 边界

房间执行层只接收类型化请求；跨节点传输在发送边界编码 PB，在接收边界验证原始字节签名后解码一次。不能为了分发、比较内容或计算队列预算再次序列化。

## 执行路径

- TCP：客户端 PB → Gateway 解码及校验 → 房间请求模型。
- 同进程：可信本地端口 → 模型身份和权限检查 → Host → 执行句柄 → 房间 Lane → 业务服务。此路径不运行网络编解码器。
- 跨节点：请求模型 → PB → 签名 → Cluster 二进制参数 → 验签 → PB 解码为模型 → 同一条房间执行路径。
- 响应：本地直接返回模型；远端在发送边界编码、签名，接收边界验签并解码。会话、进程 incarnation、序号、attempt、recipient 的绑定检查仍然执行。

## PB 契约

`Protocol/im_actor/v1/actor_value.proto` 定义内部协议。高频认证调用和响应使用固定字段号，并持有一次编码的 PB 业务体。RPC invoke、lookup、订阅续期批次使用 HotRPCRequest/HotRPCResponse；房间发送、发送结果、订阅命令/结果、日志拉取/分页使用固定字段 HotRoomRequest/HotRoomResponse。其他低频封闭的 Codable 业务模型才映射到有类型的 PB Value/Object/Array。这不是把 JSON 字符串塞进 PB：整数分别使用 sint64/uint64，Data 使用 bytes，UUID 使用 16 字节，Date 使用参考时刻的 double，枚举及嵌套模型使用对象字段。

高频部分还覆盖订阅投递/批次/回执、实时事件和 Gateway 信封、Shard 发布以及 Journal 水位和控制通知。映射直接在生成的 PB 类型和领域模型之间进行，不经过 Codable、Value 树、字段名字典或字段排序。集合按业务数组映射；集合/字典需要稳定输出时只排序其业务身份（例如接收用户）。领域构造器继续校验发送内容和指纹；接收方继续验证订阅、租约、权限及实时投影。

低频通用部分仍带业务 CodingKeys 字段名，不等同于每个业务 DTO 都有独立 `.proto` message。字段名、枚举分支和标量类型属于协议契约，不能随意修改。固定字段协议使用生成的 SwiftProtobuf 编解码器。低频通用业务体先一次计算所有节点的长度，再一次写入 PB 缓冲；信封用已知字节长度写入，避免通用嵌套 Message 对每个子树重复计算编码长度。独立生成的 SwiftProtobuf 编码器用于验证逐字节一致性。编码字段排序用于稳定的控制指纹；验签直接检查收到的字节，不重新编码。

原来的 JSON fallback 和 IMVA 内层帧已删除。内部节点需要一起升级，不能混跑旧 JSON 节点。Cluster 外层保留 IMVP 二进制参数帧；生产 Host 和 Client 默认启用二进制调用，避免再次 Base64 编码签名体。

策略快照的 facts、策略变更 command/receipt 都是模型，不再是包着 JSON 的 Data。停用命令在适配边界转换到持久化模型并执行原有领域校验；持久化日志的格式保持不变。

## 预算

网络入口继续限制实际 PB 报文大小，并在验签之后解码。解码拒绝缺少种类、重复对象键、未知 PB 字段、越界整数、非有限浮点以及超过 64 层的值。

本地请求预算独立计算保守的模型保留成本，不构造 Data。高频调用、发送结果、订阅及日志分页采用明确的模型成本函数，不在热路径使用反射；常见发送命令复用构造时计算的 `estimatedRetainedBytes`；控制模型按有界模型结构计算，溢出、过深或无法安全计量的引用对象拒绝准入。预算里的 bytes 指标现在表示保留成本，不是旧 JSON 编码长度，不应直接比较新旧预算峰值。

许可只存身份和成本，持续覆盖排队、执行、结果不确定及对账阶段。取消或超时不能提前归还仍在执行的工作。订阅及恢复批次按单个项目成本增量选择，不反复编码越来越大的数组。资料推送的内容抑制直接比较模型，不编码 JSON 指纹。

## 保留的 JSON 边界

此改造没有修改以下已有契约：HTTP API 的 JSON、JWT 的标准 JSON claims、配置和诊断日志、PostgreSQL JSONB/recordset 输入及既有客户端投影事件载荷。这些有独立的数据库查询或客户端协议依赖。数据库读取在适配边界解码；已有投影载荷按原始字节传递，不在 Actor 分发层反复解析。

因此，本轮消除的是消息 Actor 请求/响应、节点通信以及本地预算和比较中的 JSON 往返；并非把仓库所有 JSON 或持久化载荷都改成 PB。

## 生成与检查

- `scripts/generate_actor_protobuf.sh`：使用仓库解析的 SwiftProtobuf 插件生成代码。
- `scripts/check_actor_protobuf_generated.sh`：验证生成结果没有漂移。
- `scripts/check_actor_serialization_boundaries.py`：禁止 Actor RPC 使用 JSON，以及 Runtime 依赖 PB/JSON 编解码器。
- 这些检查已加入 `scripts/run_v2_swift_tests.sh`。

功能验证覆盖 PB 标量、嵌套与非法输入、验签及会话绑定、原生 Cluster 传输、房间生命周期、取消、未知提交结果、订阅及预算释放。性能变化需要同配置实测，不因换成 PB 就预先承诺吞吐提升。

## 本轮验证（2026-10-11）

171 项相关 Swift 测试、14 项压测脚本测试通过；PB 生成一致性、序列化边界检查及三个 Release 可执行文件构建通过。

R167 与 R165 使用同一套配置：6 个 Gateway，每节点 6 条消息写连接、2 个数据库 EventLoop；10,000 在线，30 秒房间预热后测量 3000 msg/s、180 秒。两轮测量均发送并最终确认 540,000 条消息，前台投递校验通过。R167 有 113 次 SERVER_BUSY 重试，最终业务失败为零；测试后服务清理完成。

初版 PB 实现 R166 出现重试耗尽，未保留其重复计算编码长度及热路径反射实现。修正后的 R167 单 Gateway 调用栈中，PB 编码、解码 inclusive CPU 占比分别约 8.55%、11.91%，预算反射约 0.78%。这些调用存在包含关系，不能相加。通用 PB 业务模型仍有容器分配和动态类型适配成本，不能把换协议本身等同于消除了序列化成本。

## 跨节点往返检查

普通发送在物理引用缓存命中时执行一次 invoke，请求内已绑定精确 activation；`roomActor(for:)` 只在缓存未命中时 lookup。入站直接调用 Host 执行业务，返回结果。续期已有按 Host 的批次调用。此次没有删除握手、续期或首次 lookup；这些不能直接按每条消息的额外往返计算。调用计数从现有 physical_lookups、business_invocations、cached_local_calls/cached_remote_calls 等传输指标核对。

高频协议的低频 escape hatch 使用独立的 cold_value 字段；解码后拒绝通过该字段携带已支持的高频枚举分支，避免无意回退到通用树。热协议和前一版通用协议需要全节点共同升级，不支持混跑。

## 固定字段协议的功能验证

184 项相关 Swift 测试通过。新增覆盖富文本发送、附件/提及/回复、指纹一致性、成功/拒绝/延后结果、全部订阅命令和投递分支、续期批次、日志分页、实时 payload、Journal 通知/结果，以及未知类型、缺失必需子消息、重复授权用户和通用分支冒充高频消息的拒绝。真实 Cluster 网络测试继续覆盖认证、回放防护、生命周期和投递。

## 固定字段协议复测 R168（2026-10-11）
