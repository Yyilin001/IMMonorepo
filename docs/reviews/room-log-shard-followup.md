## 独立房间分片裁剪

此前网关仅为控制数据库创建房间日志裁剪 worker，独立房间库没有对应任务。现在复用按数据库地址去重的 `roomOwnerMaintenanceDatabases`，为控制库及各房间库分别保留裁剪器和扫描游标。一个库失败后继续检查其余库；取消则结束维护任务。房间存储配置只允许 `im_v2` schema，因此同一地址不需要再按 schema 拆分。

## 摘要查询的数据分布测量

使用当前规范 schema，在独立临时 PostgreSQL 16 数据库中运行从当前 `PostgresV2RoomSummaryStore` 提取的首屏 SQL。每页请求 50 条，实际读取最多 51 条以判断 hasMore；每个场景 ANALYZE 后运行三次 `EXPLAIN (ANALYZE, BUFFERS, FORMAT JSON)`。房间活动时间随编号递增。测试没有消息正文、已读回执、并发流量或跨分片网络，结果只衡量该查询形态，不能作为生产延迟承诺。

| 房间数 | 用户成员分布 | 三次执行时间范围（毫秒） |
| --- | --- | --- |
| 10000 | 最冷的 50 个 | 0.219–0.235 |
| 10000 | 全部房间 | 0.244–0.260 |
| 10000 | 最冷的 1000 个 | 5.081–5.175 |
| 10000 | 没有成员关系 | 0.036–0.050 |
| 100000 | 最冷的 50 个 | 0.294–0.306 |
| 100000 | 全部房间 | 0.312–0.323 |
| 100000 | 最冷的 10000 个 | 67.148–70.134 |
| 100000 | 没有成员关系 | 0.040–0.043 |

最冷 10000 成员场景中，执行计划按活动顺序读取 90052 个房间，并执行 90052 次成员索引探测，最终返回 51 条。极稀疏成员场景则选择先读取成员关系再排序。因此当前查询返回量有界，但扫描成本不是固定的；已修正源码中相反的性能描述。

原始执行计划：`/tmp/imv2-summary-distribution-results.json`。探针：`/tmp/imv2_summary_distribution_probe.py`，仅创建并删除自身唯一命名临时库。

后续优化需比较“活动索引优先”和“成员关系优先”的计划，覆盖冷热偏斜、不同成员比例、后续分页和多物理分片。不能直接强制一种计划：成员优先可能改善冷成员场景，却使加入全部房间的首屏退化为大范围读取和排序。本轮保留 SQL 行为，将该问题作为明确的性能优化项；未引入逐成员消息写索引。
