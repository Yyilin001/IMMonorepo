# V1 main capacity baseline protocol

Status: **configuration fixed; no capacity numbers measured or approved**. Source revision is `f1cdd78d6a21bf0ae23da627c0710c65115236aa`. The machine-readable settings and scenario digests are in `IMV2/scripts/virtual-actor-fixtures/capacity-main-v1.json`; `bash IMV2/scripts/validate_v2_virtual_actor_capacity.sh` rejects changed scenarios. The baseline must use a clean checkout of that revision, never the original workspace's uncommitted Distributed Actor changes.

Use one dedicated 4 CPU / 16 GiB machine and an isolated `imv2-va-v1-capacity-*` project. Keep the exact Linux Swift image, PostgreSQL 16 image, connection budget, DB settings, data seed, credentials, owner mapping, TLS listener, resource limits and load-generator arguments identical for main and candidate. The loader and server must have separate recorded CPU/RSS counters. Do not sample while another Swift build or fault suite uses the host. Save image digests, revision, `Package.resolved` SHA-256, Compose configuration, DB settings, credential count (never credentials), scenario digest, boot IDs and wall-clock window with each run.

Run the 100-connection smoke once to validate credentials, TLS and result extraction. Its ten-second phase is not a capacity baseline. Each measured workload uses 120 seconds of warmup, 300 seconds of steady measurement and 60 seconds of cooldown, with three runs per revision in `main, candidate, candidate, main, main, candidate` order. Recreate or deterministically reseed disposable data between runs; verify the same room-to-owner mapping and capacity profile. If main accepted-throughput coefficient of variation exceeds 10%, repair the test environment and rerun both revisions before drawing a regression conclusion. C0 freezes numeric throughput, p95/p99, SQL, CPU and RSS budgets from stable main measurements before candidate results are inspected.

Measure same-room hot writes, many rooms on one owner, mixed sends/room-log reads/batch queries, cold activation/retirement and fault recovery peak separately. Existing `direct-1500-message-only-900-server-saturation.json` can cover many-room writes after the pair-to-owner map is verified; `high-active-10000.json` supplies the read/write mix but requires two 5,000-connection workers and its own full resource window. Main has no Actor activation/retirement, so record the main equivalent as a room-open/read/write cost and label the added Actor lifecycle cost on candidate. The actor-specific workloads and fault barriers still require real host/probe APIs. Report accepted commands/s, p95/p99, SQL calls/command, batch size, CPU seconds/command, peak RSS, maximum queue depth and recovery time, alongside correctness failures and rejected commands. Missing metrics cannot be silently treated as zero.

Existing tooling review: `run_v2_gateway_load_guarded.sh` uses macOS `caffeinate` and a locally built Release generator, so it is a Mac load client, not a Linux server harness. `run_v2_high_active_10000.sh` fixes TLS port 443, needs two credential files, `ulimit -n >= 65536`, and still drives full scenario rates when connections-per-worker is reduced. `run_v2_gateway_load_partitioned.sh` hardcodes a historical destination address and requires an external profile URL. `capture_v2_postgres_profile.sh` needs PostgreSQL `pg_stat_statements`, `psql`, and an explicitly disposable database for statistics reset. `docker-compose.capacity-profile.yml` enables SQL/WAL timing on the existing isolated test stack. None of these creates an isolated account/gateway capacity stack; `docker-compose.local-account.yml` publishes fixed ports and images, so it is excluded from concurrent V1 runs. The capacity runner must be parameterized before real measurements begin.

Run plan after the resource window opens: validate configuration; build the five existing Release products through `run_v2_virtual_actor_linux.sh`; execute focused existing tests; bring up a dedicated, port-parameterized capacity stack; seed/verify data and credentials; run smoke, then the full interleaved main/candidate campaign; capture PostgreSQL profiles before/after each run; write immutable reports under this review directory. Current W0 provides the first two preparation steps and the test/fault topology. It does not claim G5 performance evidence.
