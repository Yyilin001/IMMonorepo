# G3 caller-only Gateway remote atomic append

Status: **static test harness prepared; Linux execution pending an assigned functional window**. No batch result or throughput claim is recorded here yet.

`IMV2/scripts/test_v2_virtual_actor_application_stack.py --remote-gateway --remote-batch` retains the real Account HTTPS, Gateway TLS/protobuf and Operator smoke. Gateway is a caller only; the separate `actor-host` container owns both direct-room leases. The opt-in Host alone enables shard-credit size 32, append batch size 8, one lane and a 25 ms maximum wait. The 25 ms test setting improves the chance that two independent TLS processes arrive together; it is not the default 2 ms profile and provides no throughput or latency evidence.

The shell fixture registers A, B and C through Account HTTP. It creates direct rooms A-B and B-C, establishes accepted relationships using Gateway protocol commands, and warms B as sender in both rooms. It verifies that C is not a member of A-B. Two authenticated B-device TLS connections then wait on a private release marker and each sends one fixed client-message ID to a different room. The NIO Gateway handles requests serially within one connection, and the direct atomic store admits only one command per room per batch wave, so both independent connections and both rooms are necessary. Four bounded waves allow ordinary process scheduling variance; none is counted as a batch merely because it was concurrent.

Before and after those waves, the runner scrapes only the Actor Host loopback `/metrics` endpoint and requires the *committed* `im_v2_direct_room_log_append_atomic_requests_total` increase to exceed the *committed* atomic batch count increase, with batch increase positive. It also checks each stable ID has exactly one `messages` row and one matching `message_send_completions` row, new per-room message sequences are contiguous, and replay of every same ID returns the original acceptance without another durable effect. C then sends to known room A-B and must receive a non-retryable denial with zero message and completion rows. These checks happen after metric sampling, so the negative path cannot inflate batch evidence. Both room leases must remain live on the separate Actor Host at the same epoch.

When execution is permitted, retain the unique run's `result.json`, `smoke.log`, probe logs and cleaned Compose resource evidence. A passing `result.json` must contain `remoteBatch.metricsDelta` with `requests > batches > 0`, accepted IDs and sequences, non-member denial, and the remote topology. A failed run remains a failed result; there is no fallback to scalar sends or a relaxed metric predicate.
