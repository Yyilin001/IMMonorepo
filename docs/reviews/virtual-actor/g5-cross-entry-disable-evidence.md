# #20 Account disable across live Gateway and Room Actor entries

Status: test harness prepared; the disposable Linux application run is pending a scheduled execution window. No pass claim is made from static checks.

`test_v2_virtual_actor_application_stack.py --remote-gateway --cross-entry-disable` keeps the real Actor Host, caller-only Gateway, Account HTTP, and Operator HTTP in separate containers. The existing local account smoke first accepts a direct message and reads it from the peer through the TLS/protobuf Gateway. It then pauses with a private `0600` fixture. The runner verifies that the warmed room has a live lease owned by the separate Actor Host and starts exactly two sessions using the original user's device credential. The held read session retrieves the baseline message before it declares readiness; the held send session authenticates. Both sessions must remain alive at the pre-disable barrier.

The ordinary account smoke then performs its existing assertion and Push HTTP checks. Immediately before submitting the Operator disable, it waits at a second barrier. The runner confirms that neither old session has closed, creates a marker visible to both held probes, then releases the HTTP request. A socket that closed before this marker is classified as a test failure. This establishes session liveness immediately before the real disable operation without comparing timestamps from different processes. Only after the Operator returns HTTP 200 with `outcome=disabled` and the runner independently sees the matching `account_disables` row does it release the two held sessions. They try a new send with a fixed `clientMessageID` and a new room-log pull for the same room. A successful `messageAccepted` or `groupEventPage` fails the probe. A correlated `FORBIDDEN`/`UNAUTHENTICATED` response, or a connection closed after the second barrier was released, is an accepted denial. If a request was dispatched before its socket closed, the runner waits through the normal 30-second business deadline plus five seconds before its final SQL assertion. The new operation must have zero `messages` and `message_send_completions` rows; the room message count must remain at its baseline. It also verifies that the Actor lease still belongs to the same Host epoch and neither Host nor Gateway container restarted. The original Account HTTP checks after disable remain in place: access and refresh credentials return 401, while the prior assertion returns 403.

This is a cross-entry account-disable test, not a membership-revision test. It uses one disposable PostgreSQL instance for this application-stack scenario and therefore does not claim a separate owner/control database network partition. The `--cross-entry-disable` and `--busy-sigterm` options are mutually exclusive. Default smoke behavior remains unchanged.
