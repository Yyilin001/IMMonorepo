# #14 direct-room credit refill and activation fence

The opt-in `V2RoomCreditRefillFencePostgresTests` added in `d9fe262fe6ac1fc8df82bd39f2d73036f23058ff` exercises the production `PostgresV2RoomWriteStore` direct-room fast append against a disposable PostgreSQL database. These are store-level PG schedules, not a multi-Host or full Linux application run.

The first test warms a direct room with four accepted appends, then consumes its one-credit batch. It blocks a second production append *inside* its business transaction, after the activation fence, using a test-only `BEFORE INSERT` advisory lock. `pg_blocking_pids(pid)` identifies the separate test backend blocking that business transaction; a second send has exhausted process-local credits and reaches the refill's room-lock wait on another connection. While both waits are present, the credit snapshot shows two database reservations and six used room-window commands. Releasing the test gate lets both sends commit: three reserved and committed credits, no returned or active credits, seven used room-window commands, seven messages, and successful release of the original activation token. The schedule checks that the warm refill and business fence do not create a self-wait cycle.

The second test injects a PostgreSQL trigger exception before a warm direct insert. The confirmed rollback returns exactly one process-local credit while the database reservation stays spent: two reservations, one returned/active credit, six used room-window commands, and five messages. It then exercises the *local cleanup rule* for an uncertain credit by calling `discard` followed by `release`; the returned count remains one and active count becomes zero. This portion does **not** inject a real lost COMMIT ACK or independently establish a transaction outcome-unknown classification. After the old activation is released and a successor acquires epoch +1, both old-token credit acquisition and old-writer replay throw `activationChanged`. The successor accepts a new message; the final counts are three reservations, two returned credits, eight used room-window commands, and six messages.

The native test command reported **2/2 passed** in [third.log](/Users/yyl/.codex/virtual-actor-builds/p0/credit-fence-native/third.log), then **2/2 passed again** in [repeat.log](/Users/yyl/.codex/virtual-actor-builds/p0/credit-fence-native/repeat.log). The first run's two cases took 1.357s and 1.267s; the repeat took 1.569s and 1.446s. The logs contain SwiftPM warnings but no reported test issue. Both runs use the disposable-database opt-in gate; the test rejects an already-installed `im_v2` schema and drops its own schema on completion.

Linux verification of this new suite was still running when this record was written. No Linux pass is claimed here. The broader, previously completed Linux checks are documented separately in [G5 Linux regression evidence](g5-linux-regression-evidence.md).
