# Hot Gateway CPU diagnostic, main versus fdf6838e

The formal 125 send/s hot campaign stopped because candidate `fdf6838e9b0276eaf7e90acec3bed5d8fd8511fd` exceeded the frozen Gateway CPU budget: 2.7628 ms per acknowledged message versus main's 1.4277 ms and the 2.1330 ms limit. Its SQL, p95, and p99 checks passed. This separate profile locates likely CPU costs; it is **diagnostic only**, not another formal capacity sample or a change to the budget.

Both diagnostic runs used the clean frozen harness `461ef788be10686ed8497ef8078b12aa4ef49d1c`, the same common loader (`72d27c4e9358483705136a68ada2a04d2673bf6b566978065aac5bc7f3221364`), hot fixture, 100 connections, 0.25 rate scale (125 scheduled sends/s), and 120/300/60-second phases on the isolated `colima-imv2-va-capacity` 4-CPU VM. Main used `f1cdd78d6a21bf0ae23da627c0710c65115236aa`; candidate used the fdf revision above. The external diagnostic driver SHA-256 is `b6bfb21f46ba0ce071d63886cbb23c9ec768ddd0e2cd99f4f0935cc12f79cfcf`. It attached a task-only perf sidecar to Gateway PID 1 for 45 seconds, starting 20 seconds into steady state, at 49 Hz with `task-clock:u` and DWARF call chains. No Gateway container capability or VM setting was changed. Both frozen runners finished successfully with 52,500 acknowledged and durable sends, zero workload failures, unchanged room cardinality, and private-project cleanup. The profiler and its report containers were also removed.

The candidate consumed 6.31 s more PID 1 user CPU and 1.36 s more PID 1 system CPU in comparable windows. These are short separate runs, not a paired counterfactual. The sampled user stacks point to application signing and verification as one material candidate cost: candidate exclusive leaves include `fe_mul_impl` 4.58%, `fe_sq_tt` 2.93%, `fe_add` 1.47%, and SHA-512 1.10%; inclusive stacks include Ed25519 verify 9.71% and sign 4.21%. Main's top exclusive leaves were Swift runtime work (`swift_release` 4.92%, metadata-cache equality 3.69%, `swift_retain` 2.87%, `swift_beginAccess` 2.46%), while its largest identifiable application inclusive path included PostgresNIO channel reads (16.80%). Candidate also has Postgres/NIO, Swift retain/release, JSON, and SQL-row decoding work. The percentages describe each run's **sampled user CPU**, not total Gateway CPU or absolute cross-run savings. Inclusive frames nest, so their percentages must not be added; the different sample counts and unresolved libc frames limit precision. The `task-clock:u` profile excludes the measured additional system CPU.

The demangled `V2ActorTrustStore.verify<V2ActorSessionHello>` label is an optimized **merged generic specialization**, not proof that SessionHello is being repeated. Of the candidate's 546 sampled stacks, 66 contain that symbol; 35 also contain `verifyReply`/authenticated-reply frames, and 28 contain `SessionAuthenticator.accept`. A representative reply stack runs through `V2RoomClusterClient.exchange → V2ActorTrustStore.verifyReply → verify<AuthenticatedReply> →` the merged specialization, then Ed25519 verification. The profile therefore supports per-RPC cryptographic verification overhead, but cannot establish actual Hello counts or a session-cache defect. The agent reviewing session reuse should use direct event/count evidence before changing it. Sampling likewise does not establish that cryptography explains all of the candidate CPU regression.
