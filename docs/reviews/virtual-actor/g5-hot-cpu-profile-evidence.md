The sampled user stacks point to application signing and verification as one material candidate cost: candidate exclusive leaves include `fe_mul_impl` 4.58%, `fe_sq_tt` 2.93%, `fe_add` 1.47%, and SHA-512 1.10%; inclusive stacks include Ed25519 verify 9.71% and sign 4.21%. Main's top exclusive leaves were Swift runtime work (`swift_release` 4.92%, metadata-cache equality 3.69%, `swift_retain` 2.87%, `swift_beginAccess` 2.46%), while its largest identifiable application inclusive path included PostgresNIO channel reads (16.80%). Candidate also has Postgres/NIO, Swift retain/release, JSON, and SQL-row decoding work. The percentages describe each run's **sampled user CPU**, not total Gateway CPU or absolute cross-run savings. Inclusive frames nest, so their percentages must not be added; the different sample counts and unresolved libc frames limit precision. The `task-clock:u` profile excludes the measured additional system CPU.

The demangled `V2ActorTrustStore.verify<V2ActorSessionHello>` label is an optimized **merged generic specialization**, not proof that SessionHello is being repeated. Of the candidate's 546 sampled stacks, 66 contain that symbol; 35 also contain `verifyReply`/authenticated-reply frames, and 28 contain `SessionAuthenticator.accept`. A representative reply stack runs through `V2RoomClusterClient.exchange → V2ActorTrustStore.verifyReply → verify<AuthenticatedReply> →` the merged specialization, then Ed25519 verification. The profile therefore supports per-RPC cryptographic verification overhead, but cannot establish actual Hello counts or a session-cache defect. The agent reviewing session reuse should use direct event/count evidence before changing it. Sampling likewise does not establish that cryptography explains all of the candidate CPU regression.
