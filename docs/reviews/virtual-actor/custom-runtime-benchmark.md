# 自定义 Actor 运行时同机对照（2026-11-06）

首次运行时对照没有证明明显性能收益：两组均完成 10,000 在线、2,000 msg/s 的固定负载，业务网关 CPU 仅降低 1.2%，内存略增，发送 ACK P99 从 103 ms 增至 396 ms。随后定位到网关同步请求阻塞消息入口，完成隔离修复；同一自定义运行时的修复前／后完整对照中，ACK P99 为 **169 → 69 ms**。后者验证了入口隔离的收益，不能转化为运行时本身的容量或 CPU 优势。

## 对照与负载

- 旧版：`47a8e11ad1ba945636457f5d6692c559d2deb003`，仓库原有 Apple `DistributedCluster` 及项目补丁。
- 新版：`codex/custom-distributed-actor-runtime` 工作区，包含本轮发现的准入计量和 Linux socket 选项修复。源码、产品 SHA256 均在证据目录冻结；尚未提交的工作区不能只用 HEAD 表示。
- 复用 [2026-10-16 横向扩展压测](../../../IMV2/docs/09-capacity/horizontal-scaling-2026-10-16.md) 的运行器和固定档位，本轮重新测旧版，不用历史数字作百分比的分母。
- Apple M4 Pro / 14 核 / 48 GiB；专用 Colima arm64 VM 为 12 vCPU / 32 GiB；Swift 6.4 Linux Release、PostgreSQL 16。
- 4 个 Gateway/RoomHost 各独占 1 vCPU，分别限 2816 MiB，HTTPS edge 各 256 MiB；共享 PG 固定 2 vCPU / 4 GiB；4 个负载分片共用 4 vCPU / 6 GiB；账号与三个控制进程共用余下 2 vCPU。
- 10,000 用户、10,000 直聊房间、5,000 双端前台房间；128 字节消息，10 Hz 调度。认证及房间准备后，200 msg/s 预热 60 秒、静置 10 秒、2,000 msg/s 正式测量 60 秒。没有注入故障或重连，不运行容量搜索。
- 两组使用相同镜像、同一个 Release 压测器、相同场景、逻辑夹具与 256 分区 owner 分配。认证密钥为各轮独立生成，数据拓扑保持一致。

正式窗口为北京时间 01:42:51–01:43:51（旧版）与 02:16:26–02:17:26（新版）；中间进行了启动诊断和重建，测量期间没有构建。每组只测一次，没有交错复测。

## 尾延迟与证据边界

新版后段出现更多未确认消息：四个负载分片合计的逐秒样本最高为 82 条（第 60 秒），旧版最高 40 条（第 18 秒）；新版第 52–60 秒的多个样本较高。两组正式窗口内均无 Gateway warning/error。现有日志足以确认本轮尾延迟变差，不能直接归因到某个运行时函数。

两组 PG 平均消耗约 92–93% 的 2 核预算，都在正式窗口发生 WAL 触发的频繁 checkpoint；新版首轮 checkpoint 的 sync 为 0.358 秒，旧版为 0.175 秒。这是需要继续区分的数据库/I/O因素，不是已证明的根因，不能用它排除新运行时的责任。

四个负载器各只有 33,000 次 WIRE_SUBMIT 和 33,000 次 ACCEPTED（包含预热），没有恢复查询或超时重试。去掉发送前等待后 P99 差异依然存在，客户端排队和消息重试不足以解释回退。P50 基本一致，是尾部少量请求出现额外等待，而非全部消息都慢了约四倍。

对 Gateway 的累计业务计时器继续核对：正式窗口内的 `owner_write_future` 均值约为 11.66 → 11.63 ms；截至收尾的生命周期最大值为 116.93 → 75.63 ms。`room_queue_wait` 的生命周期最大值为 121.16 → 78.67 ms，`owner_ready_wait` 为 83.86 → 41.71 ms。生命周期最大值不是 P99，阶段可能重叠，不能相加或与客户端分位数相减；但这些已记录阶段没有呈现相应的数百毫秒恶化，削弱了“消息写入 SQL 变慢导致 ACK P99 回退”的解释。其他数据库准入等待仍未被完整排除。

当时的缺口是逐请求的跨层时间线，原始对照的 send-path trace 配置为 off。随后追加的两轮定向诊断已将慢请求定位到网关输入队列，见下一节。**ACK P99 的 3.84 倍不能直接当成 Actor 运行时执行速度的比值**。已有分析脚本及结果为证据目录的 `analyze-tail.py`、`tail-metric-analysis.json`、`tail-completion-check.py` 和 `tail-completion-check.txt`。

只取得一个固定档位的 A/B 样本，CPU 的约 1% 差异不能视为稳定收益。该测试共享物理宿主、Linux 内核、loopback 网络与单主 PG；没有测跨机器 RTT、极限吞吐、长时间稳态、分配热点或故障恢复性能。

### 追加定位：同步请求阻塞消息入口

保持 10,000 在线、2,000 msg/s 的同一档位，仅做两轮诊断，不运行容量搜索或完整测试矩阵：

1. `tail-diagnostic/` 使用原冻结新版二进制，开启约 1/64 操作采样。客户端 ACK P99 为 **559 ms**，超过原先 500 ms 门槛；120,000 条消息全部确认，业务失败、漏心跳为零。2,070 条 gateway trace 的最大值却只有 **81.11 ms**，RPC 扣除接收端处理后的额外耗时最大 **12.53 ms**，ACK 写出最大 **6.35 ms**。原 trace 从消息准入后开始，遗漏了输入队列。
2. `ingress-diagnostic/` 仅给 Gateway 增加入站时间线，同时开启既有心跳诊断；运行时、协议、限额和其他三个冻结产品保持原样。客户端 ACK P99 为 **171 ms**，最大 **1,012.91 ms**。正式公共窗口内采样 **1,870** 条消息，其中 **20** 条超过 100 ms；**12 条排在 syncPull（命令 30）后，8 条排在 syncAck（命令 32）后**。这 20 条的入口排队占总耗时至少 **76.9%**。正式采样中，准入后的业务处理最大 90.50 ms，ACK 写出最大 6.06 ms。

最长的一条相关消息（同一操作 ID）为：

| 阶段 | 耗时 |
| --- | ---: |
| 收到最后一个输入 TCP chunk 至开始派发 | 623.47 ms |
| 消息执行至结果就绪 | 40.27 ms |
| 结果就绪至 ACK 写出完成 | 0.03 ms |
| 整条 Gateway 时间线，含其他调度间隔 | 664.67 ms |

代码中的直接阻塞链：

- `V2NIOGatewayChannelHandler.processNext` 在 `processing == true` 时不派发下一批，必须等 `receiveInboundFrames` 整批返回。
- `V2GatewayByteStream.receiveInboundFrames` 对普通命令逐个 `await session.receive`，同步命令等待期间，后到消息只能停在输入队列。同一批中排在同步命令后的帧也会等待。
- `V2GatewayDomainCommandHandler.handle` 将 `syncPull`、`syncAck` 归入 `.sync` 并等待数据库准入。本档位每 Gateway 的同步并发预算为 3。
- 已有 `messageSendTasks` 并发只在消息出队、会话校验和准入之后启动。因此消息执行不会阻塞后续心跳，但前面的慢同步请求仍会阻塞后续消息，隔离并不对称。

原始 A/B 的数据库同步准入指标与此一致：已采样窗口内，发生排队的同步准入平均等待 **156.46 → 331.81 ms**，等待超过 500 ms 的完成项 **222 → 6,015**。旧/新取样覆盖分别为正式窗口内约 3.8–59.4 秒、0.1–56.0 秒，不能将计数直接当作严格等时吞吐比较。完整正式窗口内的同步 pull 发起数 **15,078 → 16,473**，同步线路尝试 **28,064 → 30,553**；这是 `syncAvailable` 驱动的附带同步工作，固定消息速率没有固定其实际请求数量。

**已确认的是同步数据库排队经由单连接串行输入路径放大了 ACK 尾延迟。** 消息写事务本身和已采样远程消息 RPC 没有出现对应的数百毫秒恶化。尚不能将“新版为何产生更多同步工作”唯一归因于运行时某个函数，通知时序、合并与共享数据库负载仍可能影响差异；两次诊断的 559/171 ms 也表明尾部具有明显波动。开启诊断及增加入口计时不是性能修复，不能把第二轮较低的数值当作优化收益。

优先修复边界应是：认证完成后，消息发送的有界准入与同步控制队列分离；同步 pull/ack 之间仍保持所需顺序，保留认证吊销、连接关闭、取消及任务回收约束。数据库同步排队和通知合并可继续独立优化，不能仅放大数据库并发预算来掩盖入口阻塞。

本轮仅补齐默认关闭的诊断计时，未改变命令调度行为。Linux Release 构建通过；两轮均完整确认 120,000 条正式消息，10,000 前台游标全部追平，业务失败和漏心跳为零，业务进程正常退出。第一轮因 P99 超过 500 ms 未通过延迟门槛，第二轮通过。未新增或运行无关测试。

复核入口为证据目录的 `parse-tail-traces.py`、`parse-heartbeat-diagnostics.py`、`analyze-ingress-diagnostic.py` 和 `ingress-diagnostic-summary.json`。原始候选源码/产品未覆盖；诊断源码、产品另存 `source-ingress-diagnostic/`、`ingress-diagnostic-*-sha256.*` 和 `im-actor-ab-ingress-20261106` 卷。

## 网关入口隔离修复

`V2GatewayByteStream.receiveTransportFrames` 现在负责认证后的分流：发送／结果恢复使用现有消息预算，其他命令进入单个控制任务的 FIFO。NIO 只等待本批准入，不再等待同步命令的数据库工作。握手、认证与注册先完成；控制批次的字节与数量额度包含正在执行的批次，直到业务及响应写入实际结束才释放。关闭时先退役物理连接，丢弃未执行控制、取消任务，drain 再等待控制任务与消息任务结束。数据库并发、消息窗口和协议均未调整。

定向验证限于 **9 个 test / 25 个 case**：新增 6 个 case 覆盖同包及跨包绕过慢同步、控制顺序、关闭期间实际任务所有权、控制字节／批次数上限；另复核既有认证、大帧协商、分片 EOF、关闭回收和消息预算／写入取消边界。全部通过，Linux Release Gateway 构建以及 Server/Actor 序列化边界检查通过；没有执行全套测试。

压测的修复前产品取原冻结自定义运行时 `im-actor-ab-candidate-20261106`，修复后取 `im-actor-ab-ingress-fix-20261106`。只替换 Gateway 产品，压测器、Account 和 Placement 三个产品的 SHA256 相同；诊断采样均关闭，仍使用前述 10,000 在线、4 节点各 1 vCPU、2,000 msg/s 和 60 秒正式窗口。

## 初次运行时对照的修复与预检失败

1. 原始新版在控制面 quorum 就绪前失败，未进入正式测量。直接原因是 NIO `socketOption(.tcp_nodelay)` 使用 `SOL_SOCKET` 层；Linux 将选项号 1 解释为需要额外权限的 `SO_DEBUG`，导致 `setsockopt` 返回 EACCES。已改为 `tcpOption(.tcp_nodelay)`，保持默认容器权限，Linux Release mTLS 与正式控制面启动均通过。
2. 诊断时发现执行准入按每个请求的最大回复帧预留额度。8 MiB 回复上限会把控制通道的小请求压至单并发。现按实际请求字节保留执行额度，回复用精确 `wireByteCount` 在编码前单独申请预算；取消仍须等业务实际返回才释放执行额度。新增两个小控制调用同时执行的回归通过。它不是上述 EACCES 的根因。
3. 主分支压测器的内嵌算法源码摘要过期，首轮被预检拒绝。仅更新摘要常量，重新构建同一个公共压测器供两组使用，没有改变压测行为。两组剥离调试信息后的压测器 SHA256 均为 `23904621c20dc8c389156b721ae75af44bca551f911480531a225dd3863c8d49`。
4. 新版重测曾两次在容器 Git 元数据采集失败。最终只为控制容器显式设置只读 `/workspace` 的 `safe.directory` 并保留 Git trace；业务二进制、镜像、负载算法及资源限制不变。包装脚本及摘要留存。

上述失败全部保留，不作为吞吐为零或容量上限。最终测量使用修复后的冻结源码。附加验证限于 7 个定向测试（8 个 case）、macOS 与 Linux Release 双进程 TLS smoke、协议生成和序列化边界检查；没有跑完整测试矩阵。
