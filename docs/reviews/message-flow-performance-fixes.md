# 消息链路性能修复方案（2026-09-30）

## 范围与依据

当前 App 先持久化发送意图，再由账户任务调度器提交 messageSendOperation。房间 Owner 验证授权，数据库原子提交消息、房间事件与操作回执；回执不能早于事务提交。正文通过连续实时事件或房间游标补拉进入 SQLite，界面只读本地投影。

本次覆盖前次审查的六个性能放大点：跨房间正文恢复串行、跨房间详情失效、整页刷新附带元数据重复读取、当前发送操作缺少批量事务、reaction 明细读取、附件待发送状态 N+1 查询。

资料选择：

- [Swift Concurrency](https://docs.swift.org/swift-book/documentation/the-swift-programming-language/concurrency/)：独立任务采用结构化并发，任务组退出前等待子任务；取消必须协作传播。
- [Swift 并发运行时](https://www.swift.org/migration/documentation/swift-6-concurrency-migration-guide/runtimebehavior/)：不能以无界任务堆积替代并发预算。
- [Apple SwiftUI 性能](https://developer.apple.com/documentation/xcode/understanding-and-improving-swiftui-performance)：缩小依赖更新范围，避免高频更新反复执行不必要工作。
- [SQLite Query Planning](https://www.sqlite.org/queryplanner.html)：利用现有索引筛选有限窗口，减少应用层搬运明细；新增索引需有查询证据。
- [PostgreSQL Explicit Locking](https://www.postgresql.org/docs/current/explicit-locking.html)：事务锁与回滚语义决定批量幂等和提交边界，不能提前响应或取消围栏。

以上是修复设计依据，性能收益仍须按当前版本测量，不能沿用历史吞吐数字。

## 修复设计

### 1. 房间恢复

目录、状态、摘要保留既有批量协议与公平轮转。正文处理采用滑动任务窗口，默认并发 4，可配置范围 1～16；每轮仍只消费既有房间预算。同房间完整的读游标、拉取、应用仍由 V2GroupEventSyncEngine 串行保护。每个子任务携带自己的恢复 work 围栏，授权拒绝只结束对应房间；失败、停止和取消均排空子任务。

### 2. 详情刷新

失效摘要携带有界房间范围，范围未知、删除、全局状态或权限变化保守地全局失效。范围合并不能丢失紧急标记，订阅首次仍全量刷新。详情页只接收当前房间或全局失效。

区分时间线与元数据变化；正文、reaction、回执和发送状态变化不应反复查询标题、群公告和角色策略。保留 80～800 条窗口和稳定消息身份；相同时间线不重新赋值、不推进滚动 revision。权限撤销与内容移除保留立即取消/刷新路径。

已读推进不依赖时间线是否变化：不可见事件或仅元数据事件也可能推进已应用的房间游标，因此刷新仍检查最新已读位置。紧急刷新替换被取消的读取时，合并原读取范围，避免漏掉元数据或时间线失效。

### 3. 可恢复发送操作批次

房间调度器合并相邻、同类型的 sendOperation，保留管理操作、结果确认与其他屏障的顺序。批次受既有数量、字节与截止时间预算限制。每条消息仍验证操作指纹、提交期限、激活 token 和权限；正文与该消息的不可变回执处于同一提交事务。可处理的业务拒绝保留各自结果；提交不确定必须按批次传播结果未知，等待同操作 ID 的恢复确认。

批次只在事务提交后返回结果和发布新接受消息。不得因重放再次发布，也不得重建幂等标识。减少提交次数是本次实现目标；SQL 单条执行成本、热点房间锁和吞吐的进一步优化依赖真实负载测量。

### 4. Reaction 展示查询

现有原始记录 API 保留。App 时间线展示选择聚合查询，数据库按 message_id、reaction 计算数量及当前用户参与标记；不搬运每位参与者身份。时间线定位窗口与正常分页使用相同聚合语义和同次数据库快照。复用现有 (message_id, reaction, actor_user_id) 索引，不新增重复索引。

### 5. 附件待发送快照

用一次数据库事务先结算已观察到投影的发送结果，再读取有限的 preparing 及 submitted 页面。preparing 通过依赖 JOIN 和聚合得到完成数、总数、暂停、过期、拒绝、处理中状态，不逐条解码资源载荷。准备与已提交行来自同一快照，消除跨 await handoff 的重复/消失竞争。

维持首屏 preparing 上限 200、submitted 每页 200 加一条探测、既有顺序和重试/取消语义。此改动不扩展为全局资源引擎重构。

## 验证范围

- ClientKit：跨房间重叠与并发预算、取消/围栏/拒绝隔离；投影失效范围及事务回滚；reaction 聚合与原始兼容；附件混合状态及 handoff。
- App：失效合并与房间过滤、时间线 no-op 和元数据刷新边界；必要的模拟器单元测试构建。
- Server：相邻操作批次、屏障顺序、回执与正文原子性、重放及事务回滚；必要的服务端构建与可丢弃数据库定向验证。
- 不运行无关全套测试，不重复大规模历史扫描，不以单元测试冒充性能压测。

## 实际落地与验证

由三个 GPT-6 Luna 子代理分别并行实现恢复并发、UI 刷新和服务端批次；主代理实现聚合查询与附件快照，并完成集成复查。

- ClientKit 定向测试通过：恢复并发及取消、成员权限围栏、拒绝隔离、失效合并及表到刷新范围的映射、reaction 原始/聚合读取、附件状态及 handoff。
- iOS 模拟器定向测试通过：6 个通知器测试、4 个刷新所有权测试、2 个详情页测试；覆盖紧急取消后的范围保留、相同时间线不增加 revision、元数据刷新不读时间线，以及两种情况下已读游标继续推进。
- 服务端定向测试通过：18 个房间调度测试；PostgreSQL 群聊/私聊操作回执用例覆盖批次接受、重放和回执失败时整体回滚；现有 Owner 工厂发送、读取、退役后恢复用例通过。
- App 与服务端相关构建通过，`git diff --check` 通过。仅使用可丢弃 PostgreSQL 数据库验证事务，没有运行全套回归或大规模压测。

本次交付验证了语义和调用路径，没有测量修改后的吞吐量或 P95/P99。批次内部仍顺序执行每条消息的 SQL；未知范围或删除仍保守触发全局刷新，这些是明确保留的边界。

## 后续性能验收

性能数据应分别记录本地排队到服务器受理、服务器提交到本地投影、本地投影到 UI 可见。冷恢复测多房间少正文与少房间大缺口；在线测其他房间活跃而当前房间空闲，以及当前房间高频消息/reaction。服务器使用当前 messageSendOperation 实际入口，记录每批提交数、P95/P99、锁等待、WAL 和恢复正确性。

历史千房间/万房间结果仅用于定位问题，不作为本次修改后的收益或延迟承诺。
