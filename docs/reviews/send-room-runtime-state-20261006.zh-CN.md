# 普通私聊发送：房间运行时状态直接落库

## 范围与路径

当前内存权限模式、普通账号的好友或接收者已经回复的私聊、无媒体/提及/回复/转发、关闭内容审核时，复用房间运行时状态，跳过 Owner 独立预检 SQL。尚未收到对方回复的陌生人配额、特殊账号、复杂内容、旧授权模式继续使用已有业务路径。

房间状态按精确 activation 保存。初始化使用一条 MVCC 查询读取房间配置、成员/禁言、双方配对标记、房间序号/时间线序号和房间命令额度。普通后续发送从当前已提交内存状态生成候选序号和写入材料，不使用提前准备时的旧游标。

- 房间序号和时间线序号：运行时生成候选值，同一事务内按房间连续推进。
- 房间额度：按当前内存计数检查并计算；保留原有“接受消息占用额度”的语义，随消息一起持久化。没有另加数据库额度预留查询。
- 分片额度：开启消息事务前由信用池持久预扣。凭据携带实际预扣窗口的状态、身份、版本、有效期和操作身份；普通路径不再独立读取分片额度行。信用池初始化、额度补充和窗口失效仍可能访问数据库。
- 配对标记：直接使用房间内存。稳定会话不再读取或锁定配对行，首次回复/资料展示/发送能力恢复才做相应写入。
- 完成记录：接收者由可信写入材料提供，不再为了生成完成记录重新 JOIN 私聊配对表。

稳定会话的消息事务为 BEGIN、事务超时配置、组合持久化语句、COMMIT。组合语句更新房间游标和房间额度，写入消息、完成记录和操作回执。必要的回复/投影变更仍在同一事务中执行额外 SQL。

## 提交与恢复

内存只在 COMMIT 确认后推进。旧回执重放不再次增加序号或额度。

最终 UPDATE 同时核对内存起点：房间/时间线游标、成员版本、容量配置、冻结状态、房间额度计数/上限及绑定的额度窗口身份。它不是独立的锁查询或 Actor 执行租约围栏，而是防止旧候选状态覆盖数据库新状态的条件写入。正常写入仍获得数据库固有行锁。

条件不匹配、事务失败或提交结果未知时，失效对应房间状态。只有确认回滚才允许既有批次隔离/标量恢复；提交未知不自动重发。后续执行重新加载已提交状态，发送结果仍按原 ID 查询。

运行时路径先持久化消息/房间状态，再写需要变化的配对标记，维持 room→pair 的锁顺序；任一后续写入失败会回滚整个事务。

房间管理、维护、转发及兼容消息操作沿用现有失效入口。控制权限快照携带 scope 版本，版本变化使相应房间状态失效，包括两次发送之间策略变化后恢复到相同值的情形。这里沿用当前会话约定的运行时生命周期边界，不增加真实部署的跨节点失效闭环。

## 指标

新增 `owner_runtime_state`，记录运行时写入材料准备。原 `owner_preflight` 只记录兼容数据库预检，不把内存计算伪装成 SQL 预检耗时。冷恢复时运行时状态加载仍可能执行 SQL。

## 2026-10-07：发送成功结果统一为 completion

普通发送操作只持久化 `message_send_completions` 成功事实，并与消息在同一条写入语句、同一事务提交。新增可空的 `operation_fingerprint`（公开操作 v1，包含首次提交截止时间）和 `operation_resolved_at_ms`（原确认时间），两列必须同时存在或同时为空；既有 `request_fingerprint` 继续表达内容 v3。域 API 的历史成功允许没有操作元数据，但仍依赖不可变内容指纹和消息身份去重。

TCP ACK 在内存构造，提交后返回；准备缓存保存类型化成功事实，拒绝既不落库也不进入结果缓存。成功查询、重试及重启恢复直接读取 completion 的列，不再读取或编解码完整回执 JSON。私聊策略拒绝在操作路径上不生成 denial 事件、投影或结果；其他失败的命令正文回滚后直接返回错误。拒绝之后重复提交会按当前权限、内容和截止时间重新判断，查询不到成功仍表示 unresolved。

删除独立 `message_send_operation_receipts` 表与生产读写。私聊普通批量 SQL 将新增字段直接纳入已有 typed VALUES 参数绑定，并校验消息和 completion 的完整写入数量。成功台账继续独立于正文保留，不能通过内容清理使旧成功请求再次入库。既有授权证明属于历史跨数据库授权路径，仍按原事务义务完成，不是第二份消息发送回执。

本地迁移 `IMV2/sql/migrate-message-send-success-record.sql` 要求旧发送/查询进程先停止；只迁移已接受回执中的公开指纹和精确确认时间，验证它们与 completion 的内容摘要、消息 ID、序号一致，然后删除旧表及拒绝记录。存在无法匹配的成功时整笔回滚，重复运行安全。已在一次性 PostgreSQL 验证成功保留、拒绝丢弃、重复执行、异常回滚及不可变触发器恢复；未对真实环境执行迁移。

## 2026-10-07：发送共享资源收敛

房间 Actor 继续独立排序和独立提交事务。数据库归属沿用房间持久化的 room shard；Actor 故障恢复或迁移不改变存储归属。每个服务进程按数据库 URL/schema 复用房间资源，消息连接池按物理数据库 URL 建立，不创建跨节点许可或跨房间发送事务。

内存权限模式下，房间轮次直接调用权限准备，生产工厂不再安装 Preparation Collector。相同 scope 的首次加载继续复用节点缓存的 single-flight；首次 SQL 读取只受控制连接池的真实借用闸门约束，不占消息写连接或额外逻辑读准入。旧授权模式保留原适配路径。

Owner 保留每房间 FIFO、ready 房间轮转和有界请求/字节保护；执行容量来自消息池实际普通连接数，排除续租预留。未绑定房间的资源申请直接等待实际连接池，取得连接后才选择仍有效的房间轮次，并在该连接上独立执行。正常路径不再申请 foreground_write 工作许可，不再次借连接，也不套用配置的批处理执行上限。连接任务根保留到实际借用 future 结束；排队取消/截止时间取消真实池票据，在执行事务不因其他房间取消而提前释放。已准备的成功重放直接返回，不借写连接。

增加 message_write 工作池及 IM_V2_DATABASE_MESSAGE_WRITE_CONNECTIONS_PER_EVENT_LOOP。启用隔离后与 foreground、sync、delivery、projection、maintenance 分开，其预算计入每 EventLoop 和进程总连接限制。缺少新参数的旧部署继续使用原池。默认本地示例合计仍为 8 条工作连接/EventLoop（消息1、前台2、同步1、投递1、投影2、维护1）；候选压测每节点合计仍为11（消息2、前台4、同步1、投递1、投影2、维护1）。本地示例前台每 EventLoop 保留1条续租连接，候选压测保留2条，消息池不消耗该预留。候选压测的投影并发设置为1，与投影池2条连接（含快照构建器）匹配；本地示例的4个 EventLoop 不需要降低投影并发。独立权限控制/路由池继续计入既有额外连接预算。数据库内部 CPU/WAL/I/O 仍共享。

## 2026-10-07：提交后先归还写连接，再完成房间状态和结果

生产消息调度路径的提交后工作移出物理连接借用范围：事务确认 COMMIT 后，将发送结果缓存、房间已提交游标更新及本地提交通知登记为只包含内存与通知对象的异步动作。连接池借用完成、实际连接归还后，调度器立即释放该轮次的连接预算，允许其他房间取得连接；随后顺序执行这些动作，完成后才恢复调用方并解除房间执行占用。同房间下一轮始终等待这一完整边界，ACK 仍经原有 TCP 返回路径发送。

### 已确认的跨房间同步竞争

每个 Gateway 只有一个 V2GatewayRoomSubscriptionAuthority，整个 State 由单个 Mutex 保护；所有房间的通知许可、成员状态、续期、控制更新都访问它。enqueueIfCurrent 为保证验证与入队原子性，持锁执行传入的 enqueue 回调。V2NIOGatewayChannelHandler 的普通通知回调在其中分配/复制 ByteBuffer、创建 promise，并调用 context.writeAndFlush。原生栈实际捕获到这条回调进入 NIOSSLHandler.flush/doUnbufferActions/writeDataToNetwork 及 socket write。因此临界区包含 TLS 处理与同步写出，其他房间及多个 NIO/Swift 工作线程会等待同一把锁。

R51 观察到 1,219 个 mutex 阻塞叶样本，其中 1,128 个（92.5%）属于该 authority；R52 中段仍有 940 个 mutex 阻塞叶样本，其中 912 个（97.0%）属于它。后者证明竞争持续存在，不能仅归因于首次初始化。这些是线程栈观察次数的比例，不是 CPU 百分比或客户端延迟占比；空闲 kevent/workqueue 栈不计入上述 mutex 样本。

## 房间 Actor 与连接 EventLoop 许可改造（2026-10-07）

本次落地 R52 后提出的结构方案，未运行压测、未调整数据库/连接池配置、未改动消息 Owner 事务或 TCP 消息 PB 协议。

### 状态归属与正常通知路径

V2GatewayRoomSubscriptionAuthority 现在只承担房间句柄和连接索引的目录职责。每个房间拥有独立 V2RoomSubscriptionActor；房间状态机由该 Actor 独占，不再通过节点级 Mutex 执行房间控制、续期、成员更新或许可生成。Actor 的 enter/leave 覆盖完整轮次，包括等待许可投影安装，防止 await 期间重入导致同房间控制确认顺序倒置。跨房间不共享这个执行占用。

连接在 NIO handlerAdded 时创建 V2RoomSubscriptionSocketGate，并在认证注册完成前绑定。它使用 NIOLoopBound 保存生命周期、前台房间/generation，以及各房间的 fence、授权 incarnation、成员 revision、单调时钟 deadline。实际 socket 提交只访问所属 EventLoop 的这个投影，无需读取房间 Actor、房间目录或连接索引。

路径为：

```text
房间 Actor：验证控制序列、更新成员/围栏
  → 向相关连接 EventLoop 提交许可变更
  → 等待安装完成
  → 确认控制结果 / 提供带版本的通知许可

连接 EventLoop：核对生命周期、fence、成员授权 incarnation、deadline、detail generation
  → 同步 channel.write
  → 检查结束后 flush/TLS
```

捕获的 Permit 携带连接 gate 引用；只给新捕获的连接补装投影。消息数据事件不会无条件重建全部权限投影。权限控制及租约 deadline 变化主动更新已有投影；更新值相同时跳过重复提交，完成后清除 Future barrier，避免每条消息等待一组已经完成的安装 Future。

ByteBuffer 准备与 flush 从普通通知和作者补充通知的许可回调移出。普通通知被拒绝时，预先创建的 write promise 也完成收尾。前台批次仍在逐帧许可检查内 write，检查结束后批量 flush。

### 撤权与生命周期边界

撤权、控制断点、暂停、房间 retirement、新 activation/fence 都使旧授权失效。Actor 先更新状态并提交 EventLoop 投影，再等待相关安装完成后返回控制结果。因此控制确认之后，晚到的旧 Permit 即使此前已经进入写队列，也会在真正写入时被丢弃。重加入会生成新的 authorizationID，旧 Permit 不会因为相同 member revision 或房间恢复而复活。

连接兴趣更新由连接目录在自己的短同步操作内按序提交 EventLoop 事件，再等待完成；避免两个调用方读取快照后把较旧的兴趣事件后提交。取消 detail interest 不撤销 account delivery 权限。关闭/替换连接会关闭旧 socket gate；绑定异步边界之后重新核对 Registry 生命周期，避免清理完成后补登记一条已经失效的连接。

租约到期由最终 EventLoop 检查单调时钟 deadline 拒绝写出，无需等待一个定时撤权事件。权限/续期 RPC 和既有 reset/恢复边界保留。

### 批次、调度与保留的同步边界

生产 RoomSubscriptionIngress 的跨房间批次按 fence 分组，各组并行、组内保持顺序；RPC 总响应仍等待本批所有房间结果，但慢房间不阻止其他组更新和提交通知。移除 Ingress 中重复的 sources Mutex/围栏表，归属校验使用 activation 的 source shard 与房间状态机安装的 exact fence/service。房间容量及历史围栏保留预算统一由 Authority 目录管理。

Coordinator 的相关读取变为 async；补充关系/围栏重验、关闭检查和 admission 重入保护，并在真正启动续期调用时再次检查并发预算，避免 await 期间新前台请求占用名额后仍按旧余量超额启动。

本改造不是宣称整个进程无锁：房间句柄查找、容量/历史记录和连接索引保留短 metadata Mutex；它们不包围房间状态转换或生产 NIO 的通知回调/TLS flush。非 NIO 传输及测试仍使用每房间的同步投影门和连接生命周期检查，以保持同步许可接口的语义；生产连接最终检查使用 EventLoop 本地状态。此前 IMV2_DIAGNOSTIC_ROOM_AUTH_LOCK 计数不再挂接到房间状态机，不能用其空计数代表新路径的等待时间。

### 验证

新增真实 EventLoop 回归覆盖：撤权确认后拒绝延迟写入、重新加入不能复活旧 Permit、取消/重新注册 detail interest、关闭连接、以及一个房间等待安装时另一个房间可完成操作。现有房间权限、Registry、多设备、字节流、作者补充通知、恢复与真实 Actor Cluster 传输回归共同验证。最终相关回归 137 项通过（Server Tests 134 项、真实 Actor Cluster 传输 3 项），Release IMV2ServerApp 构建通过。新增隔离用例同时验证：旧连接撤权安装完成之前不释放房间容量，完成后可使用释放的名额。实现验证阶段未测端到端性能收益，后续 R53 结果见下文。测试记录 `/tmp/imv2-room-eventloop-tests-final.log`；最终构建 `/tmp/imv2-room-eventloop-release-final.log`。

## 数据库任务调度改造（2026-10-07，R53 后）

本次针对持连接期间的任务恢复和交接等待实施结构优化，没有调整连接预算、数据库参数或消息事务的 SQL，没有运行压测。Swift 6.4 下使用 SE-0417 TaskExecutor preference，限定在物理数据库连接回调内，避免直接修改全局执行器。

### 超时与取消

获取连接和事务的超时由 NIO Scheduled 定时器执行，不再为每次借连接创建 sleep Task，也不再在借到连接后 await watchdog.value。定时器使用独立的同步失效门：回调只运行一次，disarm 与已经执行中的短回调互斥，返回后迟到回调不能再访问连接。实际获取到连接后解除 acquisition-only 定时器，选定的房间事务仍拥有自己的绝对截止时间；BEGIN/COMMIT 边界继续检查有效状态及截止时间。

物理连接回调在结束前解除计时器、标记 loanFinished，并等待已经触发的关闭操作实际结束。这样即使外层等待 future 的任务尚未恢复，此时发生取消也不会关闭已经归还、可能由下一轮复用的连接。已归还 executor 的 isUsable 返回 false，无法继续使用借用的数据库执行消息 SQL。没有通过取消任务提前归还活动事务。

### 结果及连接归还

scheduledConnection 回调直接返回 V2ScheduledSendOutcome，携带业务结果、提交后动作及房间完成回调。移除正常路径归还前的 Batcher.connectionExecuted Actor 调用及 connectedOutcomes 字典。每次借用只保留一个短同步异常恢复槽；若回调已经产生结果但外围连接收尾抛错，仍能完成该已选房间，避免遗失结果和永久占用房间。

V2OwnerPostCommitWork 改为只存动作的短 Mutex 容器；append 不再等待 Actor，finish 在锁外执行提取出的异步动作。结果包只捕获 executor.finalize，不能把包含借用数据库的 execute 一起带出连接回调。真实连接归还后才释放 Batcher 资源计数、推进内存和通知，再解除同房间占用并返回结果；不同房间仍使用独立事务。

V2EventLoopBalancedDatabase.withScheduledConnection 的资源归还与 pool_returned 计时移到实际借用 future 完成时，随后才 hop 到入口 EventLoop。减少入口 EventLoop 排队对资源归还的拖延，外部 API 的返回 EventLoop 仍保持原约定。

### 执行器与复用连接

V2DatabaseEventLoopTaskExecutor 将连接任务的作业提交到 physical.eventLoop。SQL Future 成功或失败后，非隔离事务任务使用同一执行器恢复；TaskExecutor 不提供或绕过 Actor 隔离。保留 Task 的异步启动，不把所有入口批量替换成 Task.immediate；本轮先解决已证实较大的持连接等待与重复桥接。

V2BorrowedRoomConnection 显式传给已固定连接的事务路径。每笔事务继续建立独立的超时及提交状态，但直接调用事务核心，复用当前物理连接，不再嵌套 withConnection / makeFutureWithTask。非固定连接调用仍使用常规借用入口。TaskLocal 只在借用回调作用域中提供该上下文，执行前同时检查 loan 的有效性。没有全局开启新的默认隔离语义，也没有把房间 Actor 或整个通知链路绑定到一个数据库线程。

### 验证

新增覆盖 SQL Future 成功/失败恢复位置、迟到定时器失效、提交后动作在锁外执行、同一物理连接回滚后继续独立事务、已完成房间结果遇到连接收尾失败，以及归还后拒绝复用 executor。真实 PostgreSQL 回归同时覆盖总截止时间、取消、COMMIT 结果不明、幂等及同房间顺序。

## 数据库恢复作业诊断与执行器对照入口（2026-10-07，R55 后）

本次落地诊断能力，不运行新的压测，也不根据 R54/R55 直接回退执行器。`IMV2_DIAGNOSTIC_DB_SCHEDULING=1` 启用诊断，默认关闭；`IMV2_DB_TASK_EXECUTOR=default` 将物理连接回调任务改用默认 Swift 执行器，默认仍为 `event_loop`。两项在进程中首次使用时读取，不支持热切换；只有重启进程才能进行对照。开关不改变 SQL、连接预算、事务及超时语义，也不改变 Actor 隔离规则。作用域是使用房间物理连接辅助函数的回调任务，不修改整个服务的全局执行器。

### 关联及时间边界

每次物理借用创建独立诊断对象，显式交给执行器及 Owner Timeline，不能在 enqueue 中依赖 TaskLocal 查找。日志包含 loanID、loopID、关联的 operation UUID、SQL 序号、作业序号及原生线程 ID；不包含账号、房间 ID、消息正文或凭据。这些身份只出现在有界诊断日志，不作为指标标签。

记录每个作业的 enqueue、run start、run end；SQL 记录 API 调用、实际 Future 完成、Future.get 返回后的源恢复点，以及既有 Owner resume 点。BEGIN/COMMIT 的源恢复点位于 withValue 内，Owner 点位于其外，写入源恢复点位于借用数据库 async execute 内。因此可以发现包装函数返回、执行器再次切换或后续同步处理带来的额外耗时，而不是把全部 owner_begin_resume 当作 Future.get 的等待。

源恢复和 Owner 恢复分别读取该诊断执行器当前正在物理 EventLoop 上运行的作业栈。读取前必须确认处于实际物理 EventLoop；默认执行器或其他线程上的恢复不冒用正在另一线程运行的作业。并发同阶段 SQL 无法唯一关联时记录 ambiguousResumptions，不按“最近完成”猜测。若 Future 已经完成并在原作业内直接返回，enqueue 早于 Future 完成，分析器标为 inline_or_nonpartitionable，不生成负数的运行时等待。

对可分解的源恢复，输出 Future 完成到对应 enqueue、enqueue 到作业开始、作业开始到源恢复；额外单独输出源恢复到 Owner 返回。完整作业列表保留包装函数返回途中多个作业的切换，不能简单选最后一次 enqueue 代表全过程。job_execution_wall 是连续运行段的墙钟时间，可能包含锁和系统抢占，不是 CPU 时间。Future 完成是现有驱动观察回调被执行的时刻；完成回调后的观察工作也可能包含在唤醒区间内。

每借用最多保留 256 个作业、64 条 SQL，超出记录 droppedJobs / droppedSQL。SQL 异常完成也记录源恢复；Owner 成功返回点没有执行时保持缺失，不伪造时间。最后一个作业结束可能晚于外层 Future 的返回与快照，缺少 endedMilliseconds 时不计作业执行时间。

### EventLoop 探针及日志

同一个有诊断借用的物理 EventLoop 共用一条 100 ms NIO Scheduled 探针，记录应触发时间到实际执行的延迟、待执行自定义作业数及线程 ID。只保留最近 64 个样本。最后一个诊断借用在物理 Future 收尾后的 emit/close 中释放探针并取消定时器；即使诊断对象仍被外部保留，也不继续后台探测。迟到定时回调检查 active 状态。没有创建每借用一个 sleep Task，也没有进程常驻轮询任务。

queuedJobs 只涵盖本诊断自定义执行器提交的作业，不能解释成 NIO 全部内部任务队列长度；默认执行器对照没有这份作业计数，仍可以观察实际数据库 EventLoop 延迟。短借用期间未碰到探针触发点时没有样本，不能把缺失理解为零延迟。

调度或恢复等待、单个作业连续运行至少 20 ms 的借用，及约 1/64 的借用样本输出 `db_scheduling` JSON。macOS 同时输出 executor enqueue 的 signpost 事件和作业运行区间，可结合 Time Profiler / System Trace / Swift Concurrency 查看对应线程。日志写出在物理连接回调外，诊断关闭时不创建诊断对象、探针或 signpost。结构化 JSON 的分布是慢请求偏置样本，不可称为全量 P95/P99。仍在运行的最后一个作业仅提供 capturedMilliseconds 对应的执行时间下界，不进入完整作业执行耗时分布；分析器另外列出最长 30 个排队/运行作业。

### 已定位：权限执行包装器丢失执行器偏好

实际正常发送路径为：物理借用回调的 preferred Task → withScheduledSendConnection → executePreparedOwnerBatchPreborrowing → withPreparedPolicies → policy.runtime.executePreparedBatch → Task.detached → BEGIN / 写入 / COMMIT。

### 策略快照的代码解释与定位边界

正常路径：PostgresV2RoomPolicyAuthorizationRuntime.prepareBatch → preparationSnapshot → 创建 detached Task → 带截止时间调用 currentLoader → v2CurrentPolicySnapshot → V2NodePolicyStateCache.cachedSnapshots。双方账号和关系命中时使用内存；非好友另取陌生人设置。命中后的快照读取不续租、不读 SQL。当前实现即使命中仍建立准备 Task，结果还要回到 runtime 执行 currentLoadFinished，再返回上层，存在可削减的交接，但本轮没有单独测量这些内部交接的占比。

### 1. 几百毫秒的快照长尾明确在冷路径

采集到的快照最大 439.363 ms，operation 07B77644-6C4C-4755-AB39-F29338D2BA90（Gateway 4）。同一条记录中：

* 账号/关系依赖缺失，第一段读取 133.645 ms。其中路由解析 82.870 ms，两个并发 Policy RPC 为 13.656 / 50.142 ms。
* 确认非好友后，陌生人设置也缺失，随后串行读取 305.497 ms。新 flight 启动先等 42.022 ms，再路由解析 95.234 ms，Policy RPC 167.996 ms；RPC Client 派发 Task 登记到入口另有 55.632 ms，包含在 RPC 总时长内。
* runtime 准备 Task 启动仅约 0.183 ms，加载返回后的收尾及等待方恢复很短。

因此这条 439 ms 记录不是一次 SQL 慢，也不是 runtime 收尾慢。它被两段必要依赖加载和多次执行交接叠加。冷路径的 snapshot_rpc 最大 258.205 ms、route_resolve 最大 146.518 ms、flight 启动最大 60.985 ms；这些最大值来自不同记录，不能拼成一条请求。

其他已缩小的边界：flight 安装最大 3.601 ms、runtime 的 currentLoadFinished 交接最大 0.014 ms、runtime 收尾后等待方恢复最大 29.771 ms。本轮没有证据支持优先优化收尾或缓存安装。

### 2. 路由解析是共享 Client 的内存查询交接

fetchSnapshots 对每个 remote scope 顺序 await resolve(scope.key)。GatewayPolicyAssembly 中 resolve 每次重新取得 binding.client，然后 PostgresV2PolicyDeploymentRoutes.resolveScope 根据稳定 placement 分配找目标，await Client.resolvePolicyHost。

resolvePolicyHost 只检查 accepting、内存 descriptors、健康/挂起状态及 endpoint，没有 SQL，也没有网络查找。该顺序路径仍出现 146.518 ms 的慢样本。计时包含调用前后的执行交接，不能宣布内存字典扫描本身花了 147 ms。结构上每 scope 一次 Client Actor 交接，多个 scope 串行；可优先改为一次取得 Client、一次批量解析本轮涉及的目标，继续在 Client 内核对健康、incarnation 和唯一匹配，不能长期缓存失效路由。

### 3. RPC 返回后，恢复 Client 结算是真实热点

operation 40A500C8-9D6A-4B16-91C5-CE89CA0E94F6（Gateway 5）账号/关系命中、陌生人设置缺失。其 Policy RPC 共 180.569 ms：远程 reply 已返回后，到 Client dispatch_settle 等 123.042 ms，结算后等待方恢复约 0.088 ms。该 123 ms 不含远程数据库或房间业务，发生在 RPC 返回到 Client 的执行上下文交接范围内。另一个样本 2130027D-E918-40E3-9C3F-C5BFC5581107 有 104.926 ms 同类等待。

Client 的实际派发 Task 在 Client Actor 内由 Task { [self] in ... } 创建，启动以及 await operation 后的结算均回到这个共享隔离域。消息 RPC 和权限冷加载 RPC 共用 Client。消息 RPC 返回后到结算本轮仍采集到 162.872 ms，证明不是权限专有问题。应检查如何减少共享 Client 中的串行工作及返回结算竞争；改为 detached 只会移动执行边界，生命周期登记、迟到返回、取消、超时和准确一次结算仍需保留，不能仅换 Task 类型就宣称解决。

### 4. 全命中仍有可省的准备 Task，但不是几百毫秒主因

全命中操作 3A8CC65C-3741-457F-B379-B1030B71DE8D 快照准备 92.451 ms，创建准备 Task 后等待入口 91.150 ms，实际权限状态获取约 1.239 ms。说明完全命中时额外启动 Task 会放大偶发调度等待，可考虑由 runtime 直接 await 只读缓存命中分支，冷 miss 才保留受跟踪的加载任务。

另一条全命中操作 7E21A6A2-8B08-494D-8E86-CF2A98C83865 准备 93.791 ms，实际内存状态阶段仅 0.131 ms，但阶段结束到 loader_return 又有约 85.47 ms，说明不止 Task 启动一处可能等待。当前未将这段纯快照构造与 async helper 返回交接继续分开，也没有系统线程采样；不能解释为权限规则计算用了 85 ms。

后续实现优先级：冷路径先合并本轮 scope 的路由解析交接；随后处理共享 RPC Client 派发/返回结算竞争；全命中分支移除额外准备 Task 可作为独立优化。非好友设置确实是第二段依赖，是否合并首次加载要权衡好友场景的额外读取，不能为省一轮等待无条件扩大每次加载范围。本轮已经完成定位，没有实施这些业务优化或承诺性能提升。

## R63：按目标节点拆分通信状态并移除路由 Actor 等待（2026-10-07）

### 实现边界

`V2RoomClusterClient` 改为 Sendable 门面，正常调用同步读取目录快照、选择目标稳定 host 的 `V2RoomClusterPeer`。目录仅在短 Mutex 临界区捕获/发布不可变值；查询不再排队进入共享 Client Actor。权限 binding 也改为同步捕获，当前权限快照路径一次解析本轮所有 scope 的路由。数据库位置、连接数与房间事务独立性保持原有配置。

每个 Peer 独立持有目标节点的会话、握手、调用序号、恢复和派发记录。节点的并发预算、会话总预算、预留预算和物理房间引用缓存由所有 Peer 共享；没有将原有上限乘以 Peer 数。签名和回复校验通过 `@concurrent` helper 移出 Peer 串行执行；签名完成后重新核对描述符版本和暂停状态。

每条 RPC 的 `V2RoomRPCCompletion` 独立处理回复、超时和取消，只完成调用者一次，并在 Mutex 外恢复 continuation。远端操作实际返回后直接完成调用者，再由 Peer 清理派发记录。调用者取消不会释放尚未结束的物理调用名额；旧 incarnation 的已派发回复仍使用原来的签名身份和引用快照校验。

最后审查修正了发现更新与暂停交错时的目录发布竞态：目录发布与对应 Peer 的状态修改在同一个 Peer 执行段完成，不在控制 Actor 两次 await 之间再次读取并发布状态。没有把网络/SQL 操作放进 Mutex。

## R64–R66：Host 入口与数据库 ready 等待的精确归因（2026-10-07）

### 结论与证据强度

两个必经共享隔离域会放大运行时交接长尾：消息先 await 节点的 `V2RoomActivationHost.invoke`，房间轮次执行时还 await 同一 Host 的 `executionAuthorityDeadline`；物理连接归还后又必须 await 物理 Owner 调度 Actor 的 `connectionLoanReturned`，才能释放逻辑执行名额并创建下一条连接需求。房间 Lane 独立没有消除这些节点级共享入口。

数据库侧已证实主要不是四条连接持续繁忙：两轮不做系统采样的复核中，长等待样本累计等待时间的约 55%–57% 处于至少一条连接已经实际归还、四个逻辑 ticket 名额仍被视为占用的状态。Host 侧已证实等待在调用入口/执行交接，且同一 Host 在某请求等待期间继续处理其他消息；没有找到一次持续数百毫秒的正常消息计算或维护计算。底层线程为何停顿，仍不能精确归因到某把 Swift runtime Mutex，也不能断言机器 CPU 饱和。

### 有界诊断实现

`V2OwnerConnectionTimeline.resourceWindow` 提供创建 ticket、driver 进入、实际 pool 归还和调度 Actor 登记归还的单调时钟点。调度器保留实际在途记录与最近 64 条完成记录，仅为 ready 等待至少 20 ms 的请求计算分类；历史不足显式标记，不伪造已有数据。分类按时间边界划分为互斥区间，`*_sum` 是可能不连续区间的累计时长，不是实际连续 span、连接利用率或 SQL CPU 时间。

四种分类：四条连接均已进入 driver 且未归还；四个 ticket 名额都占用且至少一个连接已实际归还；四个名额占用但尚未全部进入 driver（包含 Task 启动、pool/driver 获取等待）；逻辑名额尚有空余。前一种状态属于真实连接占用，第二种属于归还后交接，第三种不能解释成 SQL 执行。

`V2SynchronousActorTurnProbe` 仅对 Host 的同步资格扫描、状态扫描、ready token 扫描、Watchdog 更新和 idle 扫描记录超过 10 ms 的片段。Darwin 读取当前线程 CPU 时间，Glibc 使用 thread CPU clock；它不跨 await，idle 扫描遇到 await 时会结束并重新开始计时。计时不修改连接预算、Actor 生命周期或调度策略。

### R64 系统采样的限制

已确认的是共享 Host 隔离域与运行时调度形成了跨房间交接等待；正常消息在 Host 中实际做 readyEntry、安全检查、可选 JSON pull 判别、维护 inFlightCalls，然后转发 Lane。SQL 在 await 后执行，入口等待不是数据库事务锁一直持有 Host。下一步结构优化应减少正常消息对全局 Host 的反复进入，使用绑定精确 activation 的房间执行句柄/权威状态；维护仍由 Host 管理。具体方案必须保留资格撤销、租约失效、退役和已开始执行工作的边界，不能简单删去检查。

数据库侧优先消除实际归还与可用名额发布之间的 Actor 交接依赖，并由实际连接容量推动后续 ready 工作。本轮没有实施这些业务结构优化。

## 认证正常路径改为同步入口，防重放按会话保护

状态：此改造已在 R70 压测后按用户要求撤销，以下内容仅保留为实验记录。当前认证实现恢复 R69 的 Actor 路径。

`V2ActorSessionAuthenticator` 保留 Actor 管理会话创建、hello 重试合并、容量及过期清理。`accept` / `acceptLocal` 改为同步 nonisolated 方法；Inbound Service 不再 await 认证管理 Actor，也没有为每次短认证新建 detached task。

已发布会话通过独立 Mutex 目录查询，取得强引用后立即释放目录锁。验签、JSON 解码、请求身份和权限核对均在目录锁及重放锁外执行。每个会话持有自己的 Mutex 重放窗口，同一会话的本地与远程请求共用该窗口，不同会话独立。检查序号、attempt ID 和更新窗口保留原规则。

正常认证不再扫描和清理全体会话；目录规模仍由原会话容量限制约束，下一次会话管理操作负责清理。认证无需等清理执行：查找后核对到期时间，并在真正更新重放窗口前再次按当前时钟检查会话有效性及到期时间，避免验签或锁等待跨过到期边界。清理移除已发布目录项并使旧会话对象失效，因此已取得的对象引用不能绕过失效检查。

保留签名、服务/用户权限、接收方、incarnation、进程内 capability、generation、包大小和相对截止时间等认证边界。诊断中的 `receiver_auth_actor_entry_wait` 更名为 `receiver_auth_entry_gap`；改造后的正常认证没有该跨 Actor 排队边界，不能直接以新旧标签差异推断性能提升。Inbound Service 自身的隔离、运行时执行资源及其他异步路径仍存在，本次没有重构这些边界。

新增四项行为回归：管理 Actor 被占用时认证仍可执行；64 个本地/远程并发重复请求仅一次通过；不同会话的相同序号及 attempt ID 各自有效；不执行会话清理也能拒绝两个传输上的过期请求。

验证：74 项认证、集群、本地能力及订阅/实时权限相关测试全部通过，Gateway Release 构建通过（196.86 秒）。没有运行新一轮压测，没有调整连接预算、数据库或发送调度策略；性能收益待同配置复测。日志 `/tmp/imv2-auth-sync-tests.log`、`/tmp/imv2-auth-sync-release.log`。
