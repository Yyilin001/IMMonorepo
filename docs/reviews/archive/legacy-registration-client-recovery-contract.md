# 旧注册档案的客户端与 App 恢复

> 2026-09-20 当前范围：项目未上线，不保留历史兼容。本文记录旧客户端流程；其旧服务端取消入口已删除。客户端本轮未改动，本文不代表当前联调结果。 以下内容仅保留为历史记录。

日期：2026-09-07，对应 B08，继续实施中。服务端权限与状态合同见[旧注册 HTTP](legacy-registration-http-contract.md)。

App 登录使用本次 `V2PreparedDeviceRegistration` 包装一次性账号因子 provider。包装器先读取同一账号摘要范围内的旧档案，再获得绑定到新设备的账号证明，确认注册尝试仍有效，随后调用旧注册取消 HTTP；完整确认落盘后才把同一证明交给新设备签发。没有旧档案时直接继续正常登录。密码仍由一次性 provider 消费，证明只在这次调用中流转，不写入 Keychain 或日志，也不建立自动重复使用证明的后台任务。

`V2HTTPLegacyRegistrationCancellationClient` 限制 HTTPS 且拒绝 URL 用户信息、查询与片段，使用无缓存请求和既有无 Cookie/凭据存储/重定向的默认传输。请求严格发送证明、新设备、旧设备和原操作四字段；设备是规范 UUID 字符串。仅空 204 返回成功。401 要求重新验证，404/409 保留待核实档案，507 保留容量问题，429 保留合法 Retry-After；410、其他状态、异常完成体和网络错误均不能清除记录。取消在发送前后检查，并保留 URLSession 取消语义。

本地确认在一个 actor 的同步 Keychain 操作中同时核对原 pending 注册尝试、账号摘要范围和旧档案的 device/operation。退出使原租约失效，更新过的档案不被旧响应删除。HTTP 成功而本地保存失败时仍保留旧档案；重新创建 owner 后用新验证结果重放原操作。其他账号的档案与当前 pending 不受影响。签发 provider 保留这类具体错误，App 显示需要重新验证、记录待核实、容量满或清理待重试；失败不会继续请求新凭据。

旧 format 1 的 256 条档案可能占满普通注册预算。为避免“必须创建新注册才能清理，却因档案满额无法创建”的死锁，format 3 允许一个恢复专用位置，持久总数最多 257。只有当前账号确有旧档案且总数恰为 256 时才能占用；普通注册仍限制为 256。该位置中的尝试即使被遗弃也可由既有证明取消队列收敛，读取不能把它误判为损坏。没有重新解释旧 ID 为独立权限，也不丢弃旧档案换取空间。

新增客户端测试覆盖状态与请求边界、同账号清理/另一账号保留、清理失败时不签发、保存失败后重建重放、取消/退出/档案替换后的迟到确认，以及满档案恢复。签名模拟器测试从真实旧格式 Keychain 数据冷启动 App，验证保护等级、旧 ID 保留、网络失败重试与确认后的精确删除。

真实 HTTPS 测试使用生产 ClientKit 传输、一次性密码因子、注册 owner 和签发器。先对实际已签发设备种入旧档案引用；清理提交后由客户端适配器丢弃首个确认，重建 owner 再取得新证明，重放原操作后签发新设备。此处的档案持久适配器在内存中模拟 owner 重建；真实 Keychain 单独由上述签名 App 测试验证。它不等同于旧二进制升级、App 跨进程 legacy 恢复或物理断包验收。

原生验收新增第三个密码套件后，首轮三个套件并行触发既有两个密码 worker 的忙碌 503。服务端限制保持不变，首次调整过滤器仍带入同文件的新套件；最终移到独立文件，先执行原两套件，再执行新增套件。两轮失败日志保留。完整范围、计数与当前源码哈希见[证据清单](../verification-records.md#20260907-legacy-registration-client)。
