# 客户端会话排序与房间恢复实施方案

当前实现与尚未完成的验收见 [验收状态](client-owned-conversation-sync-acceptance.md)。本文件规定目标设计；[历史实施证据](archive/client-owned-conversation-sync-progress-2026-09-13.md) 保留各阶段日志，其中早期的待办描述不代表当前状态。目标尚未完成，不能以单元测试或分层基线替代完整系统验收。

## 1. 范围与设计决定

客户端根据已验证的有效活动维护会话排序；服务端提供成员授权、房间状态、个人事件与公共日志。删除恢复链路对全局活动排行的依赖。公共消息继续只写房间日志，账号级在线提示不形成逐用户持久公共事件。

选择“稳定分页核对自己的房间 + 在线变化通知 + 持久补拉队列”。重连总读取随用户房间数 R 增长，正文下载随实际缺口增长；每次请求和调度有预算。没有房间数量配额，也不宣称恢复是单次请求或恒定成本。第一次安装、长时间离线和高房间数用户允许渐进完成，并向 UI 区分本地可展示、恢复中、当前目标已追平。

不建设逐用户活动排行榜、逐消息用户 dirty 行或全局变化日志过滤服务。它们需要额外写放大或无关事件扫描，当前没有证据证明值得引入。账号在线索引的内存与网络成本单独计量。

## 3. 协议与服务端读接口

在 Protocol/im_realtime/v2/im_v2.proto 定义新消息并更新当前协议版本，使用 scripts/generate_v2_protobuf.sh 生成两端代码。当前协议版本为 30；接口名称已落实到协议与两端生成代码。

### UserRoomDirectoryList / Page

认证身份由连接上下文取得，客户端不得指定任意 user_id。每页上限 100，按 room_id 稳定排序，返回 room_id、当前用户成员修订、房间类型、归属信息及继续游标；允许顺带返回同一查询取得的轻量状态，避免逐房间请求。初始展示所需资料按现有个人快照/资料接口恢复，不能只返回 ID 就认为首次安装完成。

SQL 从 room_memberships_current_user_rooms_idx 的 user_id 前缀开始，过滤当前成员并关联 rooms；不再 ORDER BY rooms.last_event_at。先限制成员候选页，再验证归属与合法性。被过滤候选仍推进内部扫描游标；允许空结果页带继续游标，客户端不得据空页判断结束。

第一版沿已配置的物理房间存储逐个分页，避免每页同时请求全部分片。游标由服务端认证编码，绑定用户、格式版本、存储拓扑代际、当前存储位置和最后扫描的 room_id。数据库调用并发有上限。跨页不持有长事务或全库快照。

新成员加入到已经扫描过的位置，由源事务提交的个人成员事件补偿；相关用户流尚未追平或授权仍待验证时，不报告覆盖完成。个人事件延迟/暂停是明确的恢复健康状态，不承诺跨库瞬时一致。拓扑变化或跨已扫描边界的房间迁移使本轮目录游标失效并重扫；全轮预算到期保存进度，不悄悄跳过分片。

### RoomSyncStateBatch / Result

请求为有界 room_id 集合，上限初定 100；按实际房间归属分组路由。返回每个请求 ID 的明确结果：state、unavailable、retryable/owner_changed，不能省略失败项后误认为已同步。

成功状态至少包含 room_head、trimmed_through、viewer_membership_revision、read_through、latest_own_message_sequence、unread_count。保持当前未读产品公式，不在本次迁移中改变非消息事件计数语义。结果不包含排名；跨房间没有全局事务承诺，单个状态的权限、head 和未读必须来自一致数据库快照。

版本比较使用有类型的状态结构：成员修订先确定授权区间，区间内 head/read_through/latest_own_sequence 单调。不同响应互有领先时不能直接 max 合并 unread_count；丢弃过时计数并重新核对。负面成员事件优先于旧正面响应。每次客户端请求还绑定本地账号代际，旧账号和旧连接完成回调不能写入新账号状态。

### RoomLatestVisibleBatch（或状态响应的有界可选摘要）

按明确 ID 返回最新有效消息及必要排序元数据，复用现有历史成员与当前成员交集授权。只为首次恢复、可见列表或活动候选失效请求，不为每页目录强制加载正文。摘要固定到所附 head；返回载荷受总字节限制，未返回的项明确标记继续读取。摘要不能推进公共日志 applied cursor。

最新候选先沿 messages_latest_visible_idx 读取一条未撤回消息并校验接受时的成员权限；有权限即返回，否则进入授权区间补充查询。message_row 使用 messages_visible_membership_idx，room_event 使用 room_events_accepted_membership_idx，再关联匹配消息身份的当前投影。补充分支仅在快速候选不可用时执行，两条路径处于同一 SQL 快照，保留当前成员校验、head 边界与媒体计数。开区间上界按 bigint 最大值处理，关闭区间按 left_revision - 1 包含式比较。补充查询仍需排序授权候选，成本随该用户可见历史增长；它消除了逐条扫描长不可见尾部的特定瓶颈，不承诺任意历史分布下固定成本。

## 4. 全房间在线变化通知

新增账号级变化监听 Start/Ready/Changed/ResyncRequired，与详细 GroupEventSubscribe 分离。房间变更仍只产生一份房间 wake，Gateway 用进程内 room_id → 在线账号/连接索引分发元数据，同一房间、同一连接只保留最高目标水位。单侧 timeline_activity 仍走个人流，不广播给其他成员。

在线索引按账号共享成员集合，多个设备复用集合但保留各自连接代际；成员分页装载不构造一个巨大的单次响应。索引空间随在线账号的成员总量增长，必须测量，不称为 O(1)。第一版不人为限制账号可加入房间数量；资源不足时明确拒绝/中止在线覆盖建立并保持恢复状态，不能静默只订阅前 128 个房间。

启动覆盖的顺序：先建立带代际的监听入口；对每页房间先安装通知路由，再查询水位，将期间变化合并。已安装页面不能因为后续页加载而被覆盖；新加入房间也遵循先监听再读 head。已离开房间立即撤销路由。发布端授权缓存必须有成员修订和失效机制；权限不确定时回源检查或抑制提示并触发授权恢复，不能基于过期缓存发送正文。元数据也不豁免权限检查。

覆盖登记只证明通知路由建立，不代表 NATS 到客户端绝不丢失。Ready 返回 connection_epoch，批量变化带该 epoch 和 notification_sequence；序号只检查通知通道内部的缺口，不替代源数据库完整性核对。慢消费者按房间合并；超过内存/帧预算发出 ResyncRequired，连该控制帧也无法可靠入队时关闭连接触发恢复。发送完成不等于客户端落库完成。

Ready 的协议语义固定为监听入口可用，不代表全部成员房间覆盖完成。服务端须在目录页响应前，为该连接安装此页经授权的房间路由；客户端随后读取这些 ID 的状态。需要把目录业务服务与连接级覆盖登记通过窄接口接通，单独调用数据库目录服务不能产生“已覆盖”的结论。通知合并发生在分配发送序号之前，序号针对实际发出的通知帧，避免合法合并被客户端误判成丢帧。完整覆盖仅在目录结束、成员变化补偿完成且期间没有覆盖失效时成立。

跨 Gateway 继续使用现有房间 broker/wake；不为每个成员创建持久 broker consumer。重复提示、broker 重连、节点切换由幂等合并与恢复处理。在线 payload fast path 保留，但必须与后台拉取走同一投影入口。

## 5. 客户端持久化与状态归属

新增 V2RoomRecoveryEngine actor，统一拥有目录核对、状态批量刷新、补拉调度和账号级通知合并；可见会话与后台任务只向该引擎提交需求。认证生命周期继续由已有 coordinator 管理。复用 V2GroupEventSyncEngine 的单页拉取与事务应用，移除多个引擎各自全房间轮转的重复职责。

在当前新库 schema 中直接定义三类持久状态（无需历史迁移）：

| 状态 | 必需内容 | 写入要求 |
| --- | --- | --- |
| room_sync_states | 房间状态、成员修订、服务端计数版本、核对时间 | 只接受当前账号及可比较的新状态 |
| room_recovery_work | room_id、目标 head、请求代际、原因、重试时间、状态 | 同房间唯一；通知提高目标；失败不丢待办 |
| room_recovery_scan | 本轮 ID、目录游标、拓扑代际、扫描状态 | 应用目录页、排队待办与推进游标在一个 SQLite 事务内 |

已有 group_event_cursors 继续保存实际已应用位置，不另造第二份正文游标。房间页落库、投影更新、游标推进与本轮待办完成条件检查同事务；拉取期间若新目标到达，不得用旧任务完成状态删除新待办。待办增加 request_revision，删除/完成采用条件更新。

明确状态：idle、establishingCoverage、reconciling、catchingUp、live、retryWaiting。live 表示本轮已知目标追平且覆盖已建立，不声称全系统永远没有尚未发布的提交。后台预算结束是暂停；协议缺口和无权限是不同结果。恢复所用任务由运行时持有，取消后可等待退出；不在 View 中启动游离任务。

## 6. 一轮恢复与持续核对

触发：首次安装、重连、前台恢复、服务端 ResyncRequired、通知/用户流缺口、打开房间，以及低频完整性核对。

1. 校验账号代际并读取本地进度，建立监听入口，开始个人流恢复。
2. 从自己的房间目录稳定分页；每页安装监听并核对状态，落库和入队原子提交。首屏可展示本地缓存，无需等待全轮完成。
3. 按优先级处理可见房间、刚通知房间、普通恢复房间，但普通队列要有公平配额和最大等待年龄，避免热房间饿死冷房间。
4. 一次只补到该任务抓取的目标水位；新变化下一轮继续，不能追逐不断增长的 head 导致整轮永不结束。
5. 对齐个人流的已知目标与本轮目录进度，处理期间加入/退出/迁移和合并提示，标记本轮完成。

不能用客户端整数 +1 推断所有授权房间都存在可见事件：服务端可能过滤成员区间或返回裁剪下界。沿用服务端 nextRoomSequence/授权证明的游标规则；对明确缺口补拉，裁剪缺口永久标记历史不完整。

低频核对仍按自己的目录/状态批量读取，不读取活动排行。初始建议每个前台连接 10–15 分钟安排一轮、加随机抖动，仅作待测默认；一轮未结束不启动第二轮，后台由系统允许的工作预算驱动，不常驻定时器。需分别记录目标周期与实际核对延迟，大账号不承诺固定时间全量收敛。打开会话立即核对单房间。socket 心跳不替代该机制。

目录没有出现某房间，不直接删除本地内容。旧本地房间在完整一轮后按 ID 验证；明确撤销按成员修订清理。分片不可用、空页或超时不能被解释成退出。

## 7. 有效活动与未读

客户端维护唯一有效活动 reducer，不使用收到同步包的本机时间，不使用 rooms.last_event_at 直接决定列表排名。

| 事件 | 默认规则 |
| --- | --- |
| 新消息 | 按服务端确认的事件位置与时间更新活动 |
| 编辑、反应、已读、偏好、资料变化 | 不推进列表活动时间 |
| 最新消息撤回/擦除 | 重算最后一条有效活动，允许活动时间回退 |
| 单侧系统提示 | 当前两种发送拒绝提示只在时间线展示，不默认抬升列表；未来提示类型显式声明规则 |
| 成员管理事件 | 不默认置顶；空会话使用创建时间作为兜底 |
| 未确认本地发送 | 独立临时展示状态，ACK 后归并；失败不冒充已确认活动 |
| 置顶、归档 | 个人状态独立处理，置顶优先于有效活动时间 |

同房间事件按 timeline_sequence 排序，跨房间列表用有效活动时间加稳定 room_id 作并列键；不同房间的序号不能直接比较。撤回后有效候选不在本地窗口时请求该房间最新摘要，不取本地旧值当完整事实。摘要带来源身份与状态位置，旧摘要不能覆盖较新的本地投影。

未读保留服务端权威值，改为按 ID 状态刷新。个人 own_read_watermark 到达后更新同一状态仓储；本地乐观已读继续仅减少展示计数。未知计数与零分开；成员授权区间变化时重新校准。该规则独立于客户端排序。

## 8. 实施批次与文件边界

| 批次 | 主要文件/模块 | 交付与门禁 |
| --- | --- | --- |
| A 合同与类型 | im_v2.proto、Core 状态类型、新库 schema、schema/readiness 与协议生成物 | 目录游标、状态比较、授权失败结果、恢复完成语义；解析/越界/生成物一致性测试 |
| B 服务端读取 | 新 UserRoomDirectoryStore/Service、RoomSyncStateStore/Service；现有 SummaryStore 拆解；GatewayDomainCommandHandler 与 main.swift | 独立分片目录、状态批量路由、按 ID 摘要；真实 DB 测试与执行计划 |
| C 在线覆盖 | GroupEventWake、NATS broker、Gateway 会话与新账号变化路由 | 大于 128 房间、多 Gateway、安装监听期间写入、撤销、慢消费者与重连测试 |
| D 客户端恢复 | 新 RoomRecoveryEngine、GRDB 新状态扩展、GroupEventSync、BackgroundSyncRunner、AvailabilityDrivenSyncRunner | 单一调度所有者、持久任务和公平预算；崩溃/竞态/取消/续传测试 |
| E UI 投影接入 | V2AppRealtimeRuntime、ConversationDetailStore、本地列表与未读 reducer | 排序、未读、撤回回退、单侧提示、前后台和账号切换的 App 测试 |
| F 删除与总验收 | 删除 RoomSummaryList/Page 活动接口、SummaryCursorCodec、RoutedRoomSummaryStore 排名聚合、旧 unread rotation/cycle prune；清理专用测试和配置 | 单一新协议/新库启动，全量回归、实际网关与 App E2E、故障负载、资源清理 |

各批次在同一开发分支有序完成；中间实现可暂时同时存在于源码，但最终不保留双路径选择、旧协议解码或历史升级。删除接口前列出全部调用点并完成替换，最后以旧符号搜索、构建与端到端行为共同验收。

执行依赖固定为 A → B → C → D → E → F。B 的完成条件包括实际物理存储去重、当前 owner 过滤、路由切换与拓扑代际的原子联动，以及网关真实请求测试。拓扑代际不能仅取启动配置的哈希；仅迁移准备或复制完成也不能视作路由已切换。读取遇到归属不确定时返回可重试，不把迁移副本当权威成员状态。C 未完成前不能声称取消周期排行后仍具备全房间实时覆盖；D 未完成前不能取消现有恢复调度；F 完成后不保留任何旧模式开关。

新类型按边界拆文件。不要继续把恢复实现堆进 GRDBV2LocalSyncStore.swift、GatewayDomainCommandHandler 或已有三万行集成测试文件；采用 extension/窄服务和独立测试套件。测试注入时钟与受控挂起点，避免靠固定 sleep 判断正确性。

## 9. 必须通过的验收

1. 用户拥有 0、50、129、1000、10000 房间；第 129 个及后续房间的变化可见，不因详细订阅上限漏更新。
2. 热、冷、冷热偏斜成员分布，首屏和中间分页；计划不再沿全局活动索引筛成员。测 rows/buffers、实际查询数和分片并发，不只测返回行数。
3. 监听前提交、安装监听期间提交、扫描后提交、通知先于目录、重复/乱序/最后一条丢失；最终水位一致。
4. 新成员加入已扫描区间、扫描中移除/重入、房间与用户迁移、单分片不可用；无错误授权复活或误清理。
5. SQLite 每个提交边界强杀，后台期限耗尽，旧请求晚于新目标完成；重启继续且无游标越过未落库内容。
6. 快照重置、历史裁剪、首次安装；摘要不能掩盖正文缺口，裁剪标记不消失。
7. 实时与恢复并发写同一房间、跨设备已读、旧状态晚到；计数和排序最终一致。
8. 最新消息撤回、编辑旧消息、单侧提示及本地失败发送；有效活动规则准确，多设备排序确定。
9. 通知队列溢出、broker 断连、Gateway 换节点、账号切换；明确恢复或断开，禁止静默失去覆盖。
10. 当前服务器/Core/ClientKit/App 全量、独立 PostgreSQL、真实 TLS/App E2E、配置/协议/schema/文档门禁全部通过；不以测试跳过或旧二进制替代。

测量目标是恢复成本随自身 R、实际缺口和分片数解释得通，公共发送不新增逐成员持久工作；具体延迟 SLO 在代表性负载测量后确定，不预先承诺任意房间数都毫秒完成。

## 10. 依据

- [Telegram Updates](https://core.telegram.org/api/updates)：借鉴序号、缺口恢复与恢复触发；不推断其内部存储成本，也不照搬频道特殊语义。
- [Matrix Sync](https://spec.matrix.org/v1.14/client-server-api/#get_matrixclientv3sync)：借鉴初始/增量同步、显式时间线缺口；本项目继续沿用自己的房间和个人序号。
- [当前分片与摘要实测](room-log-shard-followup.md)：冷成员场景返回 51 条扫描 90052 个房间，是替换活动排行恢复入口的直接项目证据。
