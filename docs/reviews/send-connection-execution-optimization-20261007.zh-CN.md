# 消息写连接执行路径优化：前三项落地与 R75 验证

## 实现

1. `V2PhysicalDatabasePoolBorrower` 在获胜 gate 的循环上直接交付 scheduled assignment，`V2EventLoopBalancedDatabase` 在对应数据库上借用和执行。终态 Sendable 结果仍通过稳定 facade Future 返回；普通 Fluent 泛型结果隔离不变。
2. 借用轮次明确指定数据库 TaskExecutor，并按独立游标分散启动。实际事务继续固定在物理连接的循环上。提交后动作通过由该轮次持有、等待的普通 detached task 执行；shutdown 仍等待收尾，同房间不提前执行下一轮。仅清除偏好不能保证第一段同步代码离开数据库线程，新增回归先发现该问题，再修正验证通过。
3. 不可变命令的 UUID、操作/排序/授权索引键和成功记录指纹解码、十六进制格式化，在调度入队前准备一次。权限上下文仍在执行时读取；时间戳、房间序号及结果在原事务边界生成。消息协议、事务独立性、连接容量与超时参数不变。

## 2026-10-08：进一步收敛执行器与传输边界

R75 的数据是上述版本的历史结果，不能当作本节改动的性能结果。

- 获取连接根任务使用普通全局执行器；删除预先轮询选择数据库 Executor 的独立游标与接口。只有实际物理连接回调内的事务任务绑定数据库 EventLoop，保留获胜 gate 直接交付。
- 连接归还后，由同一个被调度器持有的根任务等待内存更新、结果收尾；删除额外的收尾 detached task。物理资源先释放，同房间占用在收尾结束后释放。
- NIO 通道处理器持有有界 `V2FrameDecoder`，在 EventLoop 上完成包头、版本、长度校验与拆包；只把完整帧交给业务 Actor。半帧不再单独创建业务处理任务。保留 Data 接口的原解码器，复用完整帧业务分发。

当前获取连接根任务运行在全局执行器。Gate 在 Mutex 下立即占用额度，随后调用绑定实际数据库 EventLoop 的 `promise.succeed`；借用器再对该 Future 注册 `whenComplete`。本地 SwiftNIO 的 `EventLoopFuture.swift` 中，`_resolve` 和 `_internalWhenComplete` 在 EventLoop 外调用时都通过 `eventLoop.execute` 入队。因此这条路径包含完成 Promise、注册回调两次向实际 EventLoop 的交付，分配结果要等它们推进后才能发布。诊断没有增加 Future 回调，测到的是这段交付的合计等待，尚不能分别归因给两个 EventLoop 作业，也没有证明 CPU 饱和或操作系统调度是最终原因。

这解释了当前连接已经获批却尚未开始事务的等待位置，与 R76 将获取根任务移到全局执行器后的变化一致。R75→R76 同时调整了获取根任务、收尾任务和 TCP 拆包；本轮没有单变量 A/B，不能将历史增加的 0.518 ms 全部确定归因给某一项。

## R78：合并立即授予的 EventLoop 交付

消息借用器在首次选池及 peer 转交的立即授予路径，先安装 Pending，再登记交付。Gate 已批准的 lease 随请求携带；单个实际池 EventLoop 作业完成 Gate Promise 并直接调用借用器，替代原先独立投递 Promise 完成与 Future 回调登记。该作业始终异步提交，避免选择栈上的锁重入。重复登记只在已存在的 Promise 上观察，既不重复完成 Promise，也不增加 grant。

真正容量排队及通用数据库借用保留原 Future 路径；授予后仍由实际操作持有 lease，取消只移除未授予请求。获胜发布、败选归还、截止时间检查、同房间串行及关闭排空边界保留。没有增加写连接或更换执行器。现有诊断沿用原区间：合并路径的 delivery 表示交付准备到回调运行，不能再描述成两次 Future 投递。

相关 26 项测试（4 个 suite）通过，0.445 秒，包括实际 EventLoop 归属、合并交付只授予一次、授予后取消、重复归还、排队公平性、peer 竞态及关闭。日志：`/tmp/imv2-r78-tests.log`。

## R79：消息数据库执行资源隔离

启用 workload pool isolation 时，新增 `V2DatabaseWorkloadResources` 持有两套数据库资源容器；每套拥有各自的 Fluent Databases、NIOThreadPool 和 EventLoopGroup。Gateway 基础设施、Composition、PreparedAssembly 和 DatabaseTopology 统一传递该所有权，消息 role 只注册在消息容器，其他工作 role 及独立路由／权限控制注册在控制容器。配置的循环数在拓扑组装时核对，不通过共同数组的 prefix 假装隔离。显式关闭 workload isolation 的共享模式保留原池和 handle 分布。

R79 每 Gateway 消息组仍为两条循环、四条写连接；控制组一条循环。相比 R78 数据库循环总数从两条增加到三条，六节点增加六条；连接预算不变。两套资源各有两线程 NIOThreadPool，不能将数据库循环数当作进程总线程数。两组仍共享机器 CPU、内存、PostgreSQL 和 Swift 全局执行器。

消息执行边界核对：不可变命令指纹、身份及排序已有借用前 command plan；公平调度和实际池 Gate 不增加中间队列，R78 的单次立即交付保留；事务只偏好实际物理连接所属消息循环，必要 SQL 参数构建和依赖数据库结果的计算仍在事务内；归还实际连接后，全局获取根任务再等待内存、结果收尾和同房间释放，没有额外收尾 Task。未机械地把事务任务移回全局执行器，也不宣称消息循环只运行裸网络 I/O。

两组在上层工作排空后分别关闭驱动、线程池及循环；资源关闭幂等，一套关闭失败仍会尝试关闭另一套，启动失败同样清理两套。新增测试验证驱动容器及循环不重叠、控制循环被人为阻塞时两条消息循环仍推进、并发关闭和显式共享模式。

验证：86 项相关测试（8 个 suite）通过，0.439 秒；真实 PostgreSQL 25 项回归通过，43.485 秒，覆盖真实执行器归属、同房间与不同房间边界、提交不确定、连接归还与结果收尾。临时 PostgreSQL 已关闭。日志：`/tmp/imv2-r79-tests-final.log`、`/tmp/imv2-r79-postgres-tests.log`、`/tmp/imv2-r79-postgres-run.log`。

### R81：一条消息循环加一条控制循环，未通过
