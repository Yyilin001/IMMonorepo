# 发送准备内存化及房间接纳边界

2026-10-06，在当前工作树普通单聊 Owner SQL 合并的基础上继续改造。

## 实际实现

- Current policy 模式的 `readOwnerPreparationInputs` 不再执行 `readBudgetSnapshot`，也不再获取发送准备 SQL 准入许可。它只检查请求边界、读取有界近期最终结果缓存、确定需要权限准备的消息。
- 房间权限 directory 继续按 activation 初始化房间类型及双方身份；已有内存权限事实准备流程保持不变。
- 普通好友、双方普通且活跃的单聊，在房间侧创建绑定消息和 activation 的 `V2AcceptedDirectSend`。房间成员、冻结、禁言及本地状态按 activation 首次初始化并复用；并发初始化合并。非发送房间操作使本地状态失效，下次发送重新初始化。
- Owner 对已接纳消息复用权限决定，检查成员版本、接收者绑定及执行围栏。序号、额度持久化一致性及副作用投影仍由事务处理。当前投影状态仍从事务读取，避免解除好友后的发送能力恢复被旧缓存遗漏。
- 普通已接纳消息采用 insert-first，Owner 合并预检中的最终回执读取分支被 SQL 恒假条件消除。唯一键或永久关闭冲突使整个事务回滚，再进入已有 scalar 恢复路径，保持历史结果和指纹冲突语义。
- 已确认提交的最终结果进入最多 8192 项缓存。回放不进入 Owner 事务；缓存缺失不被当成“尚未发送”的持久事实。COMMIT unknown 不产生缓存结果。
- shard 额度池自行按 shard/profile 初始化状态并合并并发加载；有效状态及已预留额度从内存消费。已有低水位批量预留机制保留，耗尽及租约更新可能访问数据库，不是逐条发送查询。

## 范围与约束

陌生人窗口额度、特殊账号、群聊、复杂消息及历史授权流程保留兼容路径。它们的准备输入在 current 模式下同样取消了逐条预算预读，但不全部使用普通好友的已接纳快速路径。

房间本地状态变更经房间执行边界失效；权限事实仍由原 Policy Owner 更新流程提供。直接绕过应用边界修改数据库并主动广播缓存的真实环境闭环不属于本次范围。

同房间仍按 turn 保持顺序，不同房间独立准备。数据库写入、冷初始化和额度补充仍共享实际数据库资源。没有取消物理资源准入和写入围栏。

## 验证

8 项集成测试（含参数组合）通过：核心 6 项耗时 30.368 秒，额度及陌生人回复权限兼容 2 项耗时 5.660 秒；Release 构建通过，耗时 223.25 秒。覆盖：隐藏原预读涉及的房间、单聊、额度、最终结果表后，温热准备仍成功；新 store 缓存未命中时恢复既有接受和拒绝结果；并发相同消息只写一条；失败回滚不推进序号；策略变更与发送能力投影保持一致；旧 Owner 和提交未知语义。

## R29 实测（首次版本）

同一 fixture、场景、6 Gateway / 12 loader / 10,000 连接，配置注入 1000 msg/s。12 份报告完整返回，共同测量窗口 60.008 秒，随后排空。

- 发送 59,988，最终确认 59,987，失败 1；测量阶段确认 58,462，runner 统计确认速率 974.22 msg/s，余下确认在排空阶段完成。
- capacityCompleted、steadyStateCompleted、steadyStateCommonWindowPassed、drained 为 true。qualityPassed 为 false；foregroundDelivery 有 1,495 个查看者落后于已提交 head，coverageProofPassed 为 false。
- 各客户端最终报告 P50 1,584–1,749 ms，P95 3,050–3,275 ms，P99 3,896–4,077 ms。这是客户端百分位范围，不是全局合并百分位。
- 6 节点共同有效采样 51.617 秒：preparation_owner_read 次数 0；发送准备准入等待仅 96 次，均值 35 ms；Owner 借连接 4.635 ms，正文 22.758 ms；普通读准入等待仍约 293.064 ms。
- 所有服务及 loader 正常退出，cleanup settled=true、forcedKillCount=0、exitFailureCount=0。

此前 R28 只有约 20 秒、5/12 客户端报告，P95 为 5,691–6,110 ms。两轮窗口及覆盖不同，不能据此给出严格的整体提升百分比；可以确认本轮完整完成了配置负载窗口，发送准备的逐次预读已消失。

R29 后另将缓存失效范围从所有非发送 turn 收窄到可能修改房间状态的 turn，读请求、回执及订阅进度保留温热状态；禁言判断统一使用 Store 的注入时钟。修正后重新执行发送回放及温热房间策略变更的 2 项参数化测试，全部通过，耗时 11.276 秒。最终 Release 再构建成功，耗时 202.76 秒。复测记录见后文。

## R30 最终版本复测

12/12 客户端报告返回，共同负载窗口 60.003 秒，在线 10,000，配置发送 1000 msg/s。

- 发送 59,988，最终确认 59,969，失败计数 19；负载窗口内确认 58,489，统计确认速率 974.76 msg/s。
- 各客户端报告 P50 1,367–1,573 ms，P95 3,029–3,331 ms，P99 3,918–4,353 ms。R28 是失败的短窗口，不能据此推导严格的提升百分比。
- steadyStateCompleted 和共同 60 秒窗口通过；capacityCompleted、drained、qualityPassed 未通过。客户端 2、3 在完成排空时各残留 2 个在途请求。
- 失败计数包括 11 个 TCP_DEFERRED_RETRY_EXHAUSTED、4 个 TCP_OUTCOME_UNKNOWN_UNRESOLVED、4 个 TCP_OUTCOME_UNKNOWN_CONNECTION_CLOSED。1130 个 SERVER_BUSY 是可重试事件，不是 1130 条最终失败。
- 前台投递检查：查看者 10,000，缺失 0，落后 committed head 1,150；coverageProofPassed=false。未将消息接受成功当成投递质量验收成功。
- 有效共同指标采样 51.663 秒：preparation_owner_read=0；发送准备准入等待仅 91 次（初始化仍可能需要 SQL）；Owner 借连接 4.399 ms、设置 7.879 ms、正文 22.311 ms、提交 4.880 ms。普通读准入等待仍约 292.434 ms，前台写约 24.990 ms。
- 清理已结束，forcedKillCount=2，exitFailureCount=4：两个压测客户端非零退出，两个进程被强制终止。测试 PG 24564 和压测 PG 24533 均已停止。

实现和相关集成检查通过，但最终压测仍未通过完整验收。未决恢复及前台投递滞后尚未定位为单一根因，不宣称吞吐、稳定性、投递已全部达标。
