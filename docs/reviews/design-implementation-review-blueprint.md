## 1. 审核目标与范围

逐项回答四个问题：

1. **设计是否值得保留？** 需求真实、边界清楚、权威状态唯一，复杂度与当前目标相称。
2. **代码是否兑现设计？** 实际生产入口贯通，权限、事务、版本、取消和错误语义没有在层间丢失。
3. **异常后是否能收敛？** 断网、重复、乱序、重启、撤权或资源紧张后，既不越权也不丢失已确认事实。
4. **用户是否能理解和完成任务？** 界面如实表达持久保存、受理、同步、失败与恢复，主要流程可操作、可访问。

覆盖 `IMApp`、`IMV2ClientKit`、`IMV2Core`、`IMV2Compression`、Server 内部 Actor/HTTP/应用目标、协议、PostgreSQL schema、测试、脚本、依赖补丁和部署运维。

范围控制：

- 全仓纳入审核目录，执行顺序优先基础边界与服务端正确性。现有状态表中的客户端实现、真机与性能暂缓项保留；本蓝图不自动启动那些实施或高成本验收。
- 沿用尚未上线、当前协议、当前服务端 schema、全新 PostgreSQL 建库的边界，不默认增加历史兼容、在线房间搬迁或用户分片在线迁移。客户端已经承诺的本地数据迁移与恢复另行审核。
- Actor 在 Host 之间接管与数据库在线搬迁是两个范围；前者的持久写入隔离仍必须核验。
- 审核可以提出删除、合并或简化方案。不能把模块越多、抽象越多、测试越多直接算作质量越高。
- 先给出有证据的判断和最小整改建议。审核计划本身不等同于全仓重构、生产接入或上线授权。

## 3. 审核组织方式

以一条业务链路或一个基础合同为单元，沿调用关系阅读，避免仅按目录逐文件挑问题。

```mermaid
flowchart LR
    A[范围与合同] --> B[状态及数据所有权]
    B --> C[真实入口与提交边界]
    C --> D[异常与恢复]
    D --> E[用户可见结果]
    E --> F[结论与证据]
```

每个单元固定执行六步：

1. **冻结范围。** 记录 commit、工作区差异、实际入口、当前合同、既有问题及本轮不审部分。
2. **先审设计。** 写明解决什么需求，状态归谁所有，为什么需要每个持久状态、协议与异步队列；比较更简单的可行方案。
3. **追踪实现。** 从 UI/HTTP/协议入口追到提交和最终读取，列出所有同类入口、后台写者、实际依赖注入及旁路。
4. **挑战边界。** 从挂起点、提交点、权限变化点和清理点推导失效场景；只选择与本不变量有关的组合。
5. **核验证据。** 检查测试断言是否验证真实结果；需要时复用现有测试，补最小有意义的复现，不以测试名或数量代替证明。
6. **形成结论。** 分开交付设计判断、实现问题、简化机会和未验证限制；新增发现去重关联原问题，不重复建账。

每项重要状态至少说明：`所有者 → 写入者 → 持久边界 → 读取者 → 版本/代次 → 恢复者 → 清理条件`。

每条变更命令至少说明：`认证身份 → 授权依据 → 幂等身份 → 线性化/提交点 → 回执含义 → 重试结果 → 用户最终看到什么`。

## 4. 分轮执行目录

编号用于后续直接指定审核主题，不代表每轮固定同样工作量。R00–R03 建立基础；R04–R13 优先核对服务端；R14–R20 完成客户端及体验链路；R21–R23 在环境和范围具备后验收。跨层问题可提前只读追踪依赖，避免等到末轮才发现合同冲突。

### R00 — 范围、版本与证据基线

- **入口：** 上述三份状态文档、合同索引、Git 差异、协议版本源、schema 与验证脚本。
- **审核：** 旧能力是否已删除；已关闭缺陷是否有对应版本与可访问证据；失败、跳过、暂缓是否被“通过”覆盖；首版范围和未来能力是否混写。
- **验证与交付：** 建立“能力 → 合同 → 当前入口 → 测试/工件 → 版本 → 缺口”清单；校对状态和实际代码。通过标准是每个结论可定位、范围无歧义，无法继承的证据明确列为待重验。

### R01 — 模块边界与复杂度

- **入口：** 各 `Package.swift`、App 组合根、Account/Gateway/Operator 的 `main.swift`、Actor Application。
- **审核：** Core 是否混入基础设施；UI 是否知道协议/SQL；是否存在只有转发作用的包装、同规则多份实现、互相回调的状态所有者、没有当前调用方的抽象；配置是否产生过多运行模式。
- **验证与交付：** 依赖图、状态所有权表、重复机制清单及“保留/合并/删除/等待证据”建议。通过标准是关键职责与副作用归属明确；不能仅为了减行数拆文件或合并事务。

### R02 — 领域类型、协议与输入边界

- **入口：** [Core](../../IMV2Core/Sources/IMV2Core)、[protobuf](../../Protocol/im_realtime/v2/im_v2.proto)、两端 codec、[Compression](../../IMV2Compression/Sources/IMV2Compression)。
- **审核：** ID、revision、sequence、时间单位、范围和空值语义；输入转换是否可触发 trap/溢出；DTO 到领域类型是否丢失约束；错误与未知结果是否准确表达；解压及帧大小是否有界。
- **验证与交付：** wire/Swift/SQL 边界矩阵，覆盖合法极值、负数或超界、未知枚举、畸形及压缩输入。通过标准是非法外部数据可控拒绝，合法边界往返无损。关联 B01、B29。

### R03 — 数据所有权、Schema 与事务设计

- **入口：** [schema.sql](../../IMV2/sql/schema.sql)、`V2SchemaReadiness`、主要 Postgres store、control/room/user shard 组装。
- **审核：** 主键/唯一约束/外键是否表达真实合同；同库可原子完成的流程是否被拆成恢复状态机；跨库是否错误假定原子性；锁顺序、查询索引、隔离和清理条件是否明确。
- **验证与交付：** 表与写者映射、关键事务图、clean bootstrap/drift 证据、必要查询计划。通过标准是重复或竞争不能突破持久约束，部分提交可被明确识别和恢复；不新增已排除的在线迁移要求。

### R04 — 账号、凭据与设备生命周期

- **入口：** `V2DeviceCredentialService`、`V2DeviceSessionService`、账号 HTTP 路由；客户端 `V2AuthSession` 与凭据交接接口。
- **审核：** 注册、刷新、密码变更、撤销、过期与退出的状态机；401/403 与临时故障；刷新和撤销竞争；已收到凭据后的持久交接；限流、哈希成本及日志脱敏。
- **验证与交付：** 生命周期/权限矩阵和真实 HTTP/PostgreSQL 专项。通过标准是撤销后旧结果不能恢复有效会话，临时不可用不会误删有效凭据，重复操作不增发独立会话。服务端与 Keychain/真机证据分别结论。关联 B05、B08、B09。

### R05 — Gateway、TLS/HTTP 与连接生命周期

- **入口：** `V2GatewaySession`、`V2NIOGatewayChannelHandler`、HTTP handler、客户端 TLS connection 与 sync transport。
- **审核：** 认证到业务入口的身份绑定；请求超时、取消、迟到响应、断线重连与 generation；帧/请求/发送队列上限；慢客户端；事件循环上的阻塞工作。
- **验证与交付：** 连接状态图及断连、背压、迟到响应专项。通过标准是旧连接不能关闭或污染新连接，单请求取消不误伤会话，缓冲有可执行上限。关联 B14、B17、D01。

### R06 — Room Virtual Actor 与后台写者

- **入口：** [Actor Runtime](../../IMV2Server/Sources/IMV2ActorRuntime)、[Cluster](../../IMV2Server/Sources/IMV2ActorCluster)、[Application](../../IMV2Server/Sources/IMV2ActorApplication)、`PostgresV2RoomActivationStore`、写者台账。
- **审核：** RoomID 与物理 Host 分离；ownerEpoch 与 activationEpoch；FIFO、租约、回收、任务取消和停机；认证集群调用；后台 maintenance/import/review 是否执行相同持久 fence。
- **验证与交付：** 所有生产写者覆盖矩阵；双 Host 分区、旧 Host 恢复、COMMIT 丢 ACK、停机在途事务专项。通过标准是旧激活不能提交，不以内存 Actor 存活证明持久所有权，outcomeUnknown 有稳定重试依据。既有证据先做差异复用，性能另列 R21。

### R07 — 发送、准入与幂等

- **入口：** `V2RoomRefMessagingClient`、`V2SendMessageService`、admission batcher、`PostgresV2RoomWriteStore`、`PostgresV2SendCompletion`、持久控制授权。
- **审核：** 普通发送、批量和特殊入口是否遵循相同政策；接受事实是否不可变；重放是否错误重复扣额或产生消息；撤权与提交的先后；回执及指纹保留策略。
- **验证与交付：** 提交边界图和少量高价值故障用例：提交前中止、提交后丢响应、编辑/撤回后重放、并发相同 ID/不同内容、撤权先完成。通过标准是同一操作只有一个持久业务效果，重放保持原接受结果，清理不重新开放旧 ID。关联 B11、D07。

### R08 — 消息变更、可见性与已读

- **入口：** edit/withdraw/reaction/read-receipt service/store、房间日志读取、Core 变更类型、客户端 reducer。
- **审核：** 当前权限与消息接受/编辑时可见性；编辑完整替换语义；终态优先级；源序号、成员代次与读游标；实时、pull、snapshot 三路效果是否一致。
- **验证与交付：** 授权/版本矩阵，重复、乱序、版本缺口、离群重入及不可见尾部扫描用例。通过标准是不能凭当前成员身份获得不应可见的历史，乱序不复活终态，合法 continuation 可推进而不泄漏内容。关联 B02、B03、B06。

### R09 — 转发与跨 owner 持久工作

- **入口：** [Forwarding](../../IMV2Server/Sources/IMV2Server/RoomCoordination/Forwarding)、export/import/delivery worker、receipt、operator replay；媒体端口与 R19 联审。
- **审核：** 来源授权、目标授权与媒体引用在何时冻结/复验；跨库部分成功如何交接；暂时失败/确定失败的分类；终态保留与清理；手工重放的权限和审计。
- **验证与交付：** 每段 durable handoff 表及断连、媒体状态变化、owner 不可用、重复领取、清理后重试专项。通过标准是不越权复制、不重发已完成效果、不靠跳过事件或手工推进序号恢复。关联 B04、D07。

### R10 — 群成员、权限与管理状态

- **入口：** membership/capabilities/moderation service/store，角色基线、公告和置顶合同，ClientKit 对应投影。
- **审核：** owner/admin/member 权限矩阵；成员 revision 与离开/重入；空权限与缺失基线区别；公告、置顶、禁言与移除的效果身份；恢复入口是否真实接入。
- **验证与交付：** 操作人 × 目标人 × 状态转换矩阵，权限变化并发、乱序和 snapshot 重建专项。通过标准是旧代次效果不能覆盖新状态，权限撤销可及时执行，服务端与页面能力一致。关联 B06 及相关当前合同。

### R11 — 建群、邀请、申请与审批

- **入口：** [Creation](../../IMV2Server/Sources/IMV2Server/RoomCoordination/Creation)、[Invitations](../../IMV2Server/Sources/IMV2Server/RoomCoordination/Invitations)、邀请目录、全局申请配额与 HTTP。
- **审核：** token 与预览绑定；创建/补目录/重放；申请、取消、审批、拒绝竞争；control 与 owner 路由；额度释放；稳定 seek pagination。
- **验证与交付：** 生命周期与路由矩阵，独立 control/双 owner PostgreSQL 定向证据。通过标准是成员变化、申请终态和额度一致，重复审批不重复生效，分页不因审核变化失效。B27 按原路由范围复核，不重新附加在线搬迁。关联 B10、B23–B27、D05、D06。

### R12 — 公开身份、联系人与接收策略

- **入口：** public identity/profile/social/direct messaging 相关 service，ClientKit social outbox/projection，`V2ContactsUI`。
- **审核：** 精确 handle 发现与资料读取授权；好友状态转换；拉黑和陌生人额度；profile 传播；多设备修改；名称搜索、分页和资料 hydration 的范围。
- **验证与交付：** 发现权限与关系转换矩阵，离线操作、并发拉黑、重复同步和分页更新专项。通过标准是不泄漏隐藏关系或内部 ID，不以 ACK 伪造同步完成，资料读取不隐含全量抓取。

### R13 — 服务端 Sync、Snapshot 与保留

- **入口：** `PostgresV2SyncStore`、projection worker/store、snapshot artifact builder、log compaction、housekeeping。
- **审核：** 个人流与公共房间日志职责；checkpoint、固定 base、稳定分页；ACK-before-activate 合同；retained floor 与 token/receipt 的关系；GC 后去重依据是否仍成立。
- **验证与交付：** 增量/重建/裁剪状态图，跨页崩溃、ACK 丢失、过期重启、清理竞争和撤销设备专项。通过标准是任何已确认游标都有完整持久投影支撑，合法恢复路径不会因裁剪丢失。关联 B03、B06、D08。

### R14 — 客户端命令 Outbox 与重试

- **入口：** `V2CommandOutbox`、各领域 outbox、`GRDBV2LocalCommandStore`、retry runner、认证 epoch。
- **审核：** 先持久化再发送；并发 flush 的领取所有权；到期唤醒；退避、暂停与显式重试；取消/退出/切账号后旧任务行为；重复 outbox 机制能否安全复用。
- **验证与交付：** 命令全生命周期矩阵及确定性时钟/进程恢复测试。通过标准是待办不会无唤醒地停留，重试复用原操作身份，账号间隔离明确，持久保存与服务端确认区别可追踪。关联 B07、B13。

### R15 — 客户端房间恢复与投影一致性

- **入口：** `V2RoomRecoveryRunner/Engine`、`GRDBV2RoomRecoveryStore`、group event sync、account room change inbox、会话恢复验收矩阵。
- **审核：** 目录、通知、订阅、正文与摘要的关系；分页预算后的继续调度；通知覆盖失效；成员授予与恢复待办原子性；撤权清理；真实“追平”的定义。
- **验证与交付：** 实时/pull/reset 等价性与恢复矩阵；重连、漏提示、多设备、冷热启动和规模专项。通过标准是摘要不推进正文游标，预算耗尽后有后继调度，提示全丢仍可恢复，过期任务不能污染新账号。关联 B03、B06、B12、B17、D08。

### R16 — 本地数据库、搜索与文件生命周期

- **入口：** `GRDBV2LocalSyncStore`、`V2LocalSchema`、`V2MessageSearch`、安装/账号存储路径、媒体与缩略图缓存。
- **审核：** 主库与派生库边界；已有本地迁移的原子性；搜索结果与消息可见性；稳定排序、历史定位和分页；退出、擦除、重装、锁屏的不同语义。
- **验证与交付：** 本地资产生命周期表，迁移中断/搜索重建/账号切换及文件实际删除证据。通过标准是不跨账号读取内容、不以退出冒充擦除，搜索不会展示已失去权限的结果，查询与内存消耗有界。关联 B15、B18–B20、D04。

### R17 — App 状态、导航与任务生命周期

- **入口：** `V2AppStore`、`V2AppRealtimeRuntime`、`V2ConversationDetailStore`、root view、feature environment、session restoration。
- **审核：** App/feature/页面状态所有权；登录、退出、深链接、弹窗及恢复；generation 与 Task 取消；MainActor 工作量；View 是否承担业务流程；依赖是否有静默伪默认值。
- **验证与交付：** 状态/导航图及登录竞争、快速页面切换、前后台、关闭页面后的迟到结果专项。通过标准是一个事实有明确所有者，任务随生命周期终止或持久交接，无旧状态覆写和重复导航。遵循 [IMApp 规则](../../IMApp/AGENTS.md)，不机械增加 ViewModel/Repository 层。

### R18 — 产品流程、视觉与可访问性

- **入口：** 登录/恢复、会话列表与详情、联系人、群管理/邀请、搜索、媒体、隐私与设备设置的实际页面。
- **审核：** 信息层级与主要动作是否清楚；空、加载、离线、等待同步、失败、无权限、过期状态；确认/撤销与错误恢复；长文本、键盘遮挡、安全区、深色、Dynamic Type、VoiceOver、Reduce Motion、对比度和语言变化。
- **验证与交付：** 逐页状态表和关键用户旅程的截图/操作证据；设计问题应有具体任务、受影响状态和可比较方案。通过标准是主要任务可完成，反馈与持久事实一致，离线重试与暂停有出口，辅助功能不朗读内部 ID。模拟器证据与真机人工验收分开。关联 B21、B22、B28、E04。

### R19 — 媒体上传、授权与清理

- **入口：** `V2MediaTransfer`、App attachment/download service，media edge/provider session、scan/review/purge/retention worker。
- **审核：** 上传 grant、设备绑定、扫描就绪、引用、下载与删除的状态机；取消与部分上传；源消息变更/撤权后的授权；临时文件、流式处理和 orphan 清理。
- **验证与交付：** 媒体生命周期表及扫描失败、过期、断点中止、并发引用/删除、迟到下载专项。通过标准是不引用未就绪或无权媒体，删除条件不破坏仍合法的引用，文件与内存增长有界。本地 provider 证据不能替代生产供应商验收。关联 B04、D04、E03。

### R20 — Push、实时提示与后台预算

- **入口：** push intent/reconciler、APNs wake worker、App headless 入口、NATS/typing/presence、账号房间通知。
- **审核：** opt-in/out 版本；迟到 token 注册；退出与账号切换；无 scene 冷启动；后台总时间和资源预算；提示层是否参与持久正确性或暴露内容。
- **验证与交付：** 用户意图/服务端端点/系统权限矩阵及 token 轮换、开关竞态、提示丢失/重复、broker 不可用专项。通过标准是旧意图不能重新启用推送，提示全部丢失仍能恢复，后台可安全到期退出。真实 APNs 单列外部条件。关联 B16、D02、D03、E05、E06。

### R21 — 资源上限、性能与容量

- **入口：** 热路径、DB pool、admission/credit、Actor mailbox、snapshot/GC、客户端查询/渲染、现有负载与测量脚本。
- **审核：** 每个队列、批次、缓存、任务组与分页是否有上限/驱逐/拒绝行为；热点是否拖垮其他房间；CPU/阻塞工作隔离；限流是否掩盖错误或饥饿。
- **验证与交付：** 先做静态有界性审查；恢复性能验收时固定硬件、版本、拓扑、数据规模与负载，再比较 p50/p95/p99、可见延迟、CPU/RSS、WAL、pool wait、sync lag 和拒绝比例。通过标准按实际产品 SLO 与基线预先确定，不临时放宽阈值，不引用旧 50k 报告批准当前架构。关联 E09、E10。

### R22 — 配置、依赖、安全与运维

- **入口：** runtime configuration、Docker/Compose、两个 vendor 补丁、锁文件、metrics/alert、operator、备份恢复与发布脚本。
- **审核：** 本地与发布配置边界；Vapor/Swift/本地补丁的固定版本与可重现构建；secret/TLS 轮换；operator 最小权限；日志脱敏与低基数；readiness、shutdown、恢复和回滚的可执行性。
- **验证与交付：** 分为“依赖与构建”“访问与观测”“恢复与发布”三个可独立核验的子项。通过标准是有效告警有处理入口、补丁有来源与回归、恢复演练验证业务事实而非仅进程启动。生产凭据、供应商、WAL/PITR/RPO/RTO 与真实部署缺口继续登记外部风险。关联 E01–E03、E06–E08、E10。

### R23 — 测试质量与最终同版验收

- **入口：** 各模块测试、SQL/Actor/本地 TLS/Simulator 脚本、总门禁与运行记录。
- **审核：** 测试是否只验证 mock；是否遗漏实际组装、后台写者与失败窗口；错误是否被吞掉；必需测试有没有被过滤或跳过；超大夹具/重复参数矩阵的维护成本；历史 flaky 是否仍被掩盖。
- **验证与交付：** 合同到测试的覆盖清单，最终版本适用门禁及已知限制。通过标准是必需套件实际运行，退出码和工件完整，最后修改后受影响检查已重跑；每个未关项都有明确后续条件。全仓结论必须包含客户端门禁，服务端专项只能给服务端范围结论。

## 5. 每轮都要追问的设计问题

| 维度 | 必须回答的问题 | 不充分的回答 |
| --- | --- | --- |
| 必要性 | 对应哪个当前需求或已证明的失败模式？ | “未来可能用到” |
| 最小复杂度 | 更简单的同库事务、值类型或直接依赖为什么不够？ | “分层越多越规范” |
| 状态模型 | 谁写、谁读，非法组合在哪里被阻止？ | “调用方会注意” |
| 授权 | 身份、当前资格和历史可见性分别由谁证明？ | “已经登录”“类型名写了 Authenticated” |
| 持久性 | 成功响应前什么必须已经提交？ | “Task 已启动”“已向 broker 发送” |
| 幂等性 | 重复、冲突和结果未知如何区别，记录何时能删？ | “加一个重试即可” |
| 并发 | await 前后的事实是否仍有效，旧代次如何被拒绝？ | “用了 actor 所以安全” |
| 资源 | 队列满、磁盘满、数据库慢时发生什么？ | “正常规模不会达到” |
| 可恢复性 | 谁知道工作未完成，进程重启后谁接手？ | “用户再点一次” |
| 用户体验 | 用户看到的成功/失败对应哪一个事实？ | “接口返回 200” |
| 演进成本 | 改一个规则会影响几处，有无无价值的重复机制？ | “拆成更多文件即可” |

其中 `Task.cancel()` 不能撤销已提交数据库事务。取消后的本地工作应停止，但已提交或结果未知的操作仍需按持久身份对账；不能为了遵守取消语义而丢弃完成事实。

## 6. 故障与状态矩阵的选择方法

不为所有开关生成笛卡尔积。围绕不变量选择最危险的交叉点，并为每个用例写清要排除的故障。

| 轴 | 代表场景 |
| --- | --- |
| 交付 | 正常、重复、乱序、响应丢失、请求是否已提交未知 |
| 生命周期 | 提交前中止、提交后进程强杀、冷启动、退出/切账号、正常停机 |
| 权限 | 操作中撤权、成员离开/重入、设备撤销、版本变化 |
| 拓扑 | 同 owner、静态跨 owner、caller-only Gateway、一个 Host/数据库不可用 |
| 存储 | 空库、大历史、retained floor、snapshot 过期、清理并发、本地受保护数据不可用 |
| 资源 | 慢连接、队列满、连接池不足、单热点、后台时间耗尽 |

优先端到端旅程：

1. 离线发送 → 本地保存 → 关闭 App → 重开重试 → 服务端提交 → ACK 丢失 → 再重试 → 接收方只见一个效果。
2. 收到消息 → 编辑/撤回与 pull 乱序 → 离线恢复/snapshot → 两端展示一致。
3. 转发含媒体消息 → 等待扫描/导入 → 来源撤权或媒体过期 → 恢复后不越权、不重复投递。
4. 入群 → 产生恢复待办 → 被移除 → 旧页迟到 → 重入 → 旧代次不污染新状态。
5. 注册/刷新响应收到 → 持久交接中断 → 冷启动 → 退出/撤销 → 凭据与后台任务无遗留活跃权限。
6. 开启 Push → 关闭 Push/退出 → 旧 token 请求迟到 → 远端端点保持最新意图。
7. 用户 A 退出并显式擦除 → 用户 B 登录 → 主库、搜索库、附件及缩略图均遵守账号隔离与擦除合同。

这些是后续挑选用例的母场景，不表示本轮已全部执行或全部失败。

## 7. 审核交付模板与判定

每轮报告按以下顺序，控制在一个主题内：

```text
审核单元：Rxx / 主题
基线：commit、工作区差异、环境
范围：入口、调用方、写者、合同；未覆盖部分
设计判断：合理 / 需要收敛 / 缺少关键决策，并说明理由
实现判断：已证实问题；未发现问题的实际阅读和验证范围
发现：严重度、触发条件、用户/数据影响、代码位置、违反的不变量
证据：复现步骤或确定的控制流/事务分析；命令、测试名、结果与工件
建议：最小修复或简化、影响范围、必要取舍
关闭条件：具体输入/操作下应出现什么结果
遗留：未验部分、外部条件、下一单元依赖
```

三类发现分开登记：

- **已证实缺陷：** 有可定位的代码路径和失败条件；无法动态复现时标清静态论证范围，不虚构运行结果。
- **设计或维护性问题：** 说明重复状态、依赖扩散或修改成本，给出替代方案及代价；不把个人命名偏好升级为缺陷。
- **验证/外部缺口：** 尚不能证明结论，明确需要什么环境或证据；不把“没测过”写成“必然有 bug”。

严重度规则：P0 为已证实的灾难性越权/不可逆大范围数据破坏等必须立即停止相关发布的情况；P1 为核心数据、授权、恢复或可用性严重错误；P2 为功能、边界或维护风险；P3 为低影响体验、文案与局部简化。严重度取决于真实影响与触发条件，不取决于代码长度。

采用“通过 / 有条件通过 / 不通过 / 未完成”的**审核结论**，它不替代既有问题状态：

- **通过：** 约定范围已审、适用证据充分、无阻断问题。
- **有条件通过：** 已证明的范围可用，限制明确且被接受；不能借此把必要但未验的核心授权/持久性写成通过。
- **不通过：** 有阻断缺陷或关键设计前提不成立。
- **未完成：** 审阅或必要验证尚未结束，列出缺口。

新增问题复用既有 B/D/E 编号关联；真正独立的新问题在 `status.md` 分配稳定编号。不要把 R 编号当缺陷编号，也不把“完成 R07 审核”当作“R07 全部问题已修复”。

- 本机 Server 清单要求 Swift tools 6.4，ClientKit 要求 6.2；在 R00 核对脚本、Xcode 与 Linux 实际工具链。构建失败先区分环境与代码问题。

- 定向通过后只扩大到受影响调用方；无需每发现一个问题就跑全仓、重做所有历史压测或新增完整框架。

- 只使用显式可丢弃的隔离测试资源。现有个人本地库及常用服务不作为故障注入目标。
- 各阶段共享一份覆盖清单和现有合同；不要为每个小问题新增一套状态表、运行器或文档体系。

## 9. 建议的实际推进顺序

| 批次 | 单元 | 阶段交付 |
| --- | --- | --- |
| 第一批 | R00 → R01 → R02 → R03 | 可信范围、实际依赖/状态图、复杂度热点、边界与数据库合同 |
| 第二批 | R04 → R05 → R06 → R07 → R08 → R09 | 身份、连接、Actor、消息与转发的正确性闭环；媒体依赖可提前联审 R19 |
| 第三批 | R10 → R11 → R12 → R13 | 群管理、社交与同步/保留的服务端结论 |
| 第四批 | R14 → R15 → R16 → R17 → R18 → R19 → R20 | 客户端持久状态、生命周期、实际交互和媒体/Push 全链路结论 |
| 第五批 | R21 → R22 → R23 | 容量与运维限制、同版验证和发布前遗留清单 |

前几轮完成后再按实际复杂度细化排期，不按文件数或历史测试数承诺工期。每轮只收敛一个清晰主题；大单元按一条持久链路拆子项，跨模块仍保持同一合同。

建议正式审核从 **R00 + R01** 开始：先确定当前实现究竟有哪些边界、哪些机制值得保留、哪些历史描述需要剔除，再审细节。对已有开放问题，优先复核 B01、B04、B11、D07 的当前服务端范围；B27 只按变化做路由回归，不恢复已取消的迁移目标。

## 10. 整体完成标准

设计与实现审核完成，需要同时满足：

1. 每项在范围内的能力、生产入口与持久写者都归入某个已完成的审核单元；跨层交接有明确负责人和不变量。
2. 设计结论有取舍理由，已证实缺陷有代码/复现证据；没有用功能缺失推测故障或用风格偏好驱动重构。
3. 所有阻断问题已关闭，或对应能力明确不进入本次交付范围；其他遗留有严重度、负责人/下一行动和可验证关闭条件。
4. 适用验证与最终交付版本一致；未运行、暂缓及外部环境限制明确标注，没有“全绿”掩盖跳过。
5. 当前合同、实现与状态文档一致；运行过程进入验证记录/归档，不追加到权威合同中。

**审核完成、整改完成、允许上线是三个独立结论。** 外部生产环境、真机、APNs、供应商、容量或灾备证据不足时，可以完成代码审核报告，但不能据此宣布生产发布就绪。
