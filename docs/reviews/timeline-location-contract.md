# B18 有界历史消息定位

搜索和收藏导航现在按 message ID 直接读取目标窗口，移除了依赖 timeline.count 增长的定位循环。App 一次请求最多 40 条前项、目标和 39 条后项；普通翻页仍保持 800 条滑动上限。位于当前历史窗口之后的消息也可以直接定位。

## 查询与身份

`conversationTimelineWindow(in:for:around:before:after:)` 在同一次 SQLite 读快照中检查账号、房间、已知撤销授权、目标消息和撤回状态，随后读取前后窗口及 reaction、收藏、置顶、已读装饰。未知目标、其他房间/账号及已知无权访问均返回 `.unavailable`，不泄露消息是否存在；已撤回返回 `.withdrawn`。它读取已经同步的本地事实，不会为缺失消息自动申请服务器历史，也不替代 B03/B06 的授权和恢复合同。

查询先按消息主键定位，然后分别使用消息和私有系统活动的房间/时间线索引向两侧 seek，没有 OFFSET 或前页扫描。窗口、普通分页和渲染共享 `(timelineSequence, itemID, kind)` 的完整顺序；kind 只处理消息和活动恰好同序号、同 ID 的边界。游标不进入服务器协议或 SQLite schema。

返回的 olderCursor 用于向前翻页；newerBoundary 是第一条未包含的较新项，用于严格 before 刷新当前历史窗口。边界行即使随后被删除，其排序键仍可使用。置顶装饰查询同时限制 room 和消息 ID，避免 retained pin 负记录增长时扫描整张表。

## App 生命周期和滚动

每次定位获得独立 owner，并使之前的页读取失效。新的定位、返回最新和取消均不能被旧结果覆盖；定位期间收到的刷新在定位完成后执行。未找到或撤回显示明确反馈并保留已有窗口，空页面失败不会停留在 loading。分页失败的迟到反馈也有代次检查。

详情页的 ScrollView 行身份是 `message-<ID>`。滚动现在从当前时间线取得真实 item.id；此前裸消息 ID 即使已加载目标，也无法匹配滚动行。视图保持模块内可见，测试直接挂载生产 SwiftUI 详情页，没有专用替代页面。

## 验收范围

[证据清单](evidence/20260906-timeline-location/manifest.json)保存分层回归、首次测试编译失败和滚动负向实验。验证包括：

- 1,000/100,000 条真实 SQLite 历史的首、中、尾定位，窗口和双向边界正确，刷新结果一致。
- 同样规模的置顶负记录下，实际生产查询约 1,700/3,400/1,700 个 SQLite VM 步骤；历史扩大 100 倍时保持相同。计数通过测试连接的 SQLite progress handler 获取，误差粒度 100 步，不以墙钟时间作性能断言。
- 消息/活动同序号同 ID、装饰、跨房间/账号、撤销授权、撤回、删除和整数溢出/窗口上限。
- App 5,000 条受控历史的单次查询、跳到更新历史、旧读取、取消、刷新延后、不可用反馈；真实 SQLite→生产 data source→Store 的混合 1,000 项定位、刷新、翻页与返回最新。
- 挂载真实 SwiftUI 详情页后，目标窗口中部对应的实际 ScrollView 移离顶部并进入中部区域。临时恢复原裸 ID，唯一滚动回归失败；修复版恢复后再次验证。该断言验证真实滚动位置，不是逐像素或 VoiceOver 焦点验收。

最终 **365 项 ClientKit / 58 套件、182 项 App / 17 套件**通过。protocol 25、PostgreSQL 19、SQLite 173/5 未变；未运行真机手工无障碍、多语言或服务器压力测试，这些不计入 B18 的本地定位验收。
