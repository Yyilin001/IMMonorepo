# 消息终态、版本缺口与快照重放

对应 B03/B06，并包含 B04 的回复引用清理。延续[完整编辑合同](message-edit-replacement-contract.md)，本批处理撤回终态与乱序，protocol 27、PostgreSQL 25、SQLite 173/5 均不变。

## 服务端个人投影

普通作者撤回沿用已验证的原 accepted 受众与变更时刻成员交集。不可变共享状态已经包含原接受身份、当前终态版本及清空后的内容，因此撤回不需要用户获得中间编辑版本。成员从 rev1 直接收到撤回 rev3 时可以终结消息；先收到撤回后收到 accepted 或旧编辑，也不能恢复旧正文。

共享状态通过消息、房间、revision、state ID、source event ID 和原接受身份复核。即使 wire payload 使用 inline 存储，也可按具体消息版本查找已随 fanout 复制的不可变状态；不从 owner 当前正文猜测历史内容。普通撤回在基线缺失、但完整状态存在时可以安装该已授权终态。writer 同时核对接受记录与原投影来源。

旧 inline 记录若没有共享状态，只能基于已有的本用户消息值清空内容。没有本地基线也没有完整状态时继续报错、保持 checkpoint，不能跳过依赖或制造消息。旧文本编辑只接受连续新 revision，同 revision 必须同内容，历史编辑不降低版本，任何编辑不得恢复终态。撤回事件若与更高的活动版本矛盾则失败；房间不符或非整数版本也失败。

审核删文不能借此扩大受众。`message.redacted` 在缺少原投影时继续要求基线，保留独立无正文 `contentRevocation` 的待实现边界；不会用本批新分支为未见过消息的人创建快照记录。本批没有改变审核命令、历史受众或普通撤回的追溯政策。

## ClientKit

快照可以已包含 `[removed]` 和终态 revision，但不含原撤回事件的 effect claim。之后从 personal、room 或 preview 收到该事件时，本地先检查同消息、同房间、同版本，确认正文、附件、mention、entities、转发引用均已清空，再登记该事件并推进对应流。无需再安排搜索任务；同版本但残留矛盾正文仍拒绝并回滚。

所有新撤回/删文会同时移除回复引用。对于旧版已撤回但留下 reply ID 的记录，相同终态重放会清除这一个残留引用；这不是对全库历史行的主动扫描或迁移。未再次重放的旧行清理与其他内容索引/缓存回收仍属于 B04 的后续工作。

消息物化、tombstone、effect claim、引用清理与 durable cursor 保持同一 SQLite 事务。预览不改 durable room cursor。重复消费不产生新的搜索任务，重新打开数据库仍保持终态。

## 证据与未完成范围

服务器负例覆盖共享、inline、有意移除共享状态的旧 inline 三种存储，以及版本缺口、accepted 晚到和旧编辑晚到。客户端负例直接执行快照导入/准备/激活、关闭重开与三个消费入口，不以手工写入正常终态代替快照流程；另对损坏正文和旧回复残留注入受控数据。

最终服务端 **289 项 / 25 套件**、ClientKit **374 项 / 58 套件**、App **182 项 / 17 套件**通过。服务端终态参数覆盖 21 个场景，包含审核删文缺基线与三类损坏/矛盾回滚；ClientKit 另用上一批真实 owner/fanout 编辑载荷完成全套回归。编译失败的初次客户端负例、纠正后的行为负例和中间回归均单独保留，不混入最终通过记录。

最终日志、脚本和源码哈希见[本批证据](../../docs/reviews/verification-records.md#20260906-message-terminal-projection)。B03 的独立撤销、其他内容读取、完整房间恢复、账号/access epoch 与旧缺依赖积压仍开放；B06 的其他实体及完整跨流恢复、B04 的全量历史与缓存清理也未关闭。本机分层回归不能代替真实 App 到 TLS 网关、生产发布或设备验收。
