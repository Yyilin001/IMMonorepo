# 审查清单

在按 AGENS 风格规则审查 Swift/SwiftUI 代码时，使用这份清单。

## 1. 并发与隔离

- 新增异步逻辑是否使用了 `async/await`，而不是继续新增 completion-handler 接口？
- 是否在适合的地方使用了结构化并发，而不是直接创建顶层 `Task {}` 或 `Task.detached`？
- 固定且小规模的并发工作是否优先使用了 `async let`，而不是过早上升到 task group？
- 动态 fan-out、逐步归并或按完成顺序消费结果的场景，是否正确使用了 `withTaskGroup` / `withThrowingTaskGroup`？
- 是否把存在严格顺序依赖的步骤硬拆成了 `async let` 或 task group？
- `async let` 的结果是否在同一作用域内被明确等待和消费？
- task group 中的子任务边界是否清晰，而不是依赖大量共享可变状态相互耦合？
- 共享可变状态是否通过 `actor`、`@MainActor` 或值语义隔离？
- UI 状态变化是否发生在正确的 UI 隔离域？
- `nonisolated` 和 `@unchecked Sendable` 是否有明确理由，而不是仅仅为了压告警？
- 长时间运行或重复执行的异步逻辑是否检查了取消？
- 可抛错的长任务是否在合适的挂起点使用了 `Task.checkCancellation()`？
- 不抛错或局部短路场景是否在合适位置使用 `Task.isCancelled`，并在取消后及时停止后续工作？
- 检测到取消后，代码是否仍继续提交网络请求、状态写入、UI 更新或其他副作用？
- `CancellationError` 是否被错误吞掉，导致上游无法分辨“取消”和“成功”？
- `Task` 的创建者是否清楚，生命周期和取消责任是否明确？

## 2. 旧 API 桥接

- 新业务逻辑是否调用了桥接后的 async API，而不是原始 callback API？
- 如果旧 API 是单次结果，是否桥接成了 `async` 或 `async throws`？
- 如果旧 API 是事件流，是否桥接成了 `AsyncStream` 或 `AsyncThrowingStream`？
- continuation 的使用是否集中、易审查，并且不会漏 resume 或重复 resume？

## 3. SwiftUI 数据流

- 页面是否遵循清晰的状态驱动数据流？
- 页面状态是否存在单一事实来源？
- 是否存在多个异步分支或多个状态源零散驱动同一片 UI？
- 视图是否把副作用、业务保存或网络逻辑直接塞进了 `body`？

## 4. 类型建模

- 业务约束是否通过类型表达，而不是推迟到运行时检查？
- 互斥状态是否用 `enum` 建模，而不是多个 `Bool` 或 `Optional`？
- DTO 或弱类型传输模型是否泄漏到了业务逻辑或 UI 渲染层？
- 已经验证过的信息，是否又被降级回原始 `String`、`Bool`、`Int` 或数组？
- 某个非法状态是否本可以通过调整类型设计消除，而不是继续加防御分支？
- 领域实体是否仍在使用裸 `String`/`Int` 身份，而不是专属 `ID` 类型？
- 领域错误是否被明确建模，还是被隐藏在宽泛 `Error`、日志字符串或静默失败里？
- 解析器和强类型包装是否建立在可信边界，而不是散落在业务流程中段？
- witness 或 proof 类型是否真的难以伪造，并通过非可选参数参与受限 API？

## 5. 函数签名与流程

- 核心业务流程是否能从函数输入输出类型直接读懂？
- 上游函数输出是否自然成为下游函数输入，还是中途频繁降级为弱类型？
- 是否依赖共享可变状态、布尔开关或隐式约定串联流程？

## 6. 测试与验证

- async 改动是否在可行时补了 async 测试？
- 与取消相关的路径是否有测试？
- 迁移改动是否在不改变现有行为的前提下完成验证？
- 当前改动是否需要一个针对 UI 状态顺序、数据流或解析逻辑的回归测试？
- 对强类型封装、解析器、witness 构造路径和领域转换逻辑，是否有针对性的单元测试？

## 7. SwiftUI

- 视图是否由状态驱动，而不是在 `body` 中夹带副作用或业务编排？
- 状态所有权是否清晰，例如本地状态、共享状态和可绑定状态没有混杂？
- 是否优先使用现代 SwiftUI API，而不是继续沿用过时导航、过时预览或旧式状态方案？
- 是否避免在 `body` 中频繁创建复杂 `Binding(get:set:)`、排序、过滤或其他昂贵逻辑？
- 是否过度使用 `AnyView`、类型抹除或额外包装层，导致视图结构和身份变得更难推断？
- 是否把 `body` 重算、`onAppear` 再次触发或布局阶段回调，误当成必须立刻修复的“重复渲染”问题，而没有先确认真实副作用或用户可见回归？
- 是否存在 `onAppear`、`PreferenceKey`、几何测量或布局回调驱动的状态反馈回路，导致重复更新、抖动或布局不稳定？
- 复用组件是否不必要地长期存储 escaping `@ViewBuilder` closure，或同时叠加 closure 存储与类型擦除，使依赖追踪和结构推断变差？
- 界面是否考虑了 Dynamic Type、VoiceOver、点击区大小和自适应布局？
- SwiftUI 依赖注入是否保持轻量且类型明确，而不是为简单场景机械引入协议层、只做转发的中间层或 DI 框架？
- `service/store/view` 的职责是否清晰：service 负责行为，store 负责状态，view 负责渲染？
- store 是否作为单一事实来源存在，并通过 `@MainActor @Observable` 或等价主隔离可观察状态管理 UI 数据？
- 应用级依赖是否合理通过 `Environment` 注入，且必须注入的依赖是否采用显式失败默认值？
- 加载、错误、空态和内容态是否通过明确的枚举型状态模型表达，而不是多个 Bool/Optional 拼装？
- 导航目标是否通过强类型路由建模，而不是依赖字符串、零散 Bool 或临时回调？
- `NavigationStack(path:)` 的 path 是否存在单一事实来源，而不是被多个页面各自维护？
- `navigationDestination` 的映射是否集中管理，而不是散落在多个页面里重复实现？
- 当同一路由可能多次入栈时，导航身份是否与业务路由分离？
- 有载荷的模态是否优先使用 `sheet(item:)` / `fullScreenCover(item:)`？
- 是否避免用多个 Bool 拼装互斥导航和模态状态？

## 8. SwiftData

- SwiftData 是否被明确当作持久化边界，而不是直接扩散成整个业务层和 UI 层的真相来源？
- `@Model` 是否主要承担持久化模型职责，而不是长期横穿 `view`、`store`、`service` 的所有层？
- `@Model` 是否优先使用稳定、基础、可演进的数据类型，而不是直接固化复杂、易变的 `Codable` 结构？
- 若某些值未来需要筛选、迁移或独立演进，是否已拆分为基础字段或独立实体，而不是塞进单个复杂属性？
- 是否避免在 `@Model` 初始化中直接搭建复杂关系图或隐式完成关系写入？
- `service/store/view` 的职责是否清晰：service 负责 SwiftData 读写和副作用边界，store 负责页面状态，view 负责渲染与事件？
- `view` 是否绕过上层边界直接大量操作 `modelContext` 或承担保存逻辑？
- 应用级依赖是否合理通过 `Environment` 注入 `ModelContainer`、`ModelContext` 或上层 service？
- SwiftData 并发访问是否优先通过 `@ModelActor` 或等价明确边界隔离，而不是在多个任务间直接共享 model 实例和 `modelContext`？
- 跨任务或后台持久化访问时，是否优先传递稳定标识或输入值，而不是直接传递 SwiftData model 实例？
- 若使用 SwiftData，schema 变更是否显式声明了迁移方案，而不是依赖默认迁移？

## Findings 输出格式

- 先列 findings，并按严重程度排序。
- 每条 finding 附上文件和行号引用。
- 风险要说具体，说明它会导致什么错误行为、竞态、状态漂移或回归路径。
- 摘要放在次要位置。
