# AGENTS.md

## 项目说明

本仓库是一个 iOS 项目。

最低前提：
- iOS 26
- Swift 6
- 默认假设可使用现代 SwiftUI、Swift Concurrency 与 Observation 相关能力

默认采用：
- Swift Concurrency
- 类型驱动设计
- SwiftUI 状态驱动渲染

仓库级规则只保留默认长期生效的核心约束。审查清单、旧代码迁移步骤和详细 review 工作流已移入 `agens-ios-review` skill。

## 核心规则

### 1. 默认使用 Swift Concurrency

- 新增异步接口优先使用 `async/await`。
- 优先使用结构化并发，例如 `async let`、`withTaskGroup` 和子任务。
- 共享可变状态必须有明确隔离，优先使用 `actor`、`@MainActor` 或不可变值传递。
- 不要把并发告警当作纯粹的编译器噪音；先修正隔离设计。

### 2. 避免继续扩散旧式并发

- 不要为新业务代码继续引入 completion handler 风格接口。
- 不要新增基于 `DispatchQueue`、`OperationQueue` 或手动线程切换的业务编排逻辑，除非是在桥接旧代码或系统接口。
- 不要在同一条功能链路中长期混用 callback、delegate、GCD 和 `Task`，除非迁移过程确有必要。

### 3. UI 相关代码默认在正确隔离域

- 所有 UI 状态、UI 绑定数据和 UI 更新逻辑应位于正确隔离域中，通常是 `@MainActor`。
- store 和页面协调对象若承担 UI 相关状态，应优先整体标记为 `@MainActor`，而不是零散使用 `MainActor.run`。
- 不要在非 UI 隔离上下文中直接修改可观察的 UI 状态。

### 4. SwiftUI 代码规则

- SwiftUI 页面默认应由状态驱动，保持 `View` 声明式，并尽量维护单一事实来源。
- 不要在 SwiftUI `body` 中夹带业务编排、副作用或复杂的临时绑定拼装。
- 优先使用 SwiftUI 原生数据流和现代 API，不要继续扩散过时方案。
- SwiftUI 界面必须兼顾可访问性、自适应布局和稳定身份，不要依赖隐式点击区、固定尺寸或展示顺序充当真相。
- SwiftUI 依赖注入默认优先使用轻量、类型明确的方式；若闭包式 service 已足够表达依赖，不要机械引入协议样板或 DI 框架。
- SwiftUI 页面可直接观察 `@MainActor @Observable` store；当 store 已承担状态和派生状态职责时，不要额外增加只做转发的中间层。
- service 应负责行为与副作用边界，store 应负责状态持有与派生状态，view 应负责渲染；不要让这三者职责互相渗透。
- 应用级依赖可优先通过 `Environment` 注入；对必须注入的依赖，默认值应显式失败，而不是静默降级或偷偷提供伪默认实现。
- 页面状态优先使用枚举型状态模型，例如 `idle/loading/loaded/failed`，不要用多个 Bool 或 Optional 临时拼装加载生命周期。

### 5. SwiftData 规则

- SwiftData 应作为独立持久化边界对待，不要把它和 SwiftUI 页面状态、领域建模或业务编排混成同一层。
- `@Model` 优先承担持久化模型职责，不要让持久化模型直接扩散成整个业务层和 UI 层的长期真相来源。
- `@Model` 建模应优先使用稳定、基础、可演进的数据类型；对复杂或尚未稳定的 `Codable` 结构保持谨慎，不要把易变编码结构直接固化为持久化字段。
- 若某个复杂值未来可能调整结构、又需要参与筛选、迁移或跨版本兼容，优先拆分为基础字段或独立实体，而不是直接塞进单个复杂属性。
- `@Model` 的属性和关系设计应优先考虑演进成本与兼容性；不要为了当前便利把模型设计成高耦合、强约束且难迁移的结构。
- 不要在 `@Model` 初始化方法中直接构造和写入复杂关系图；优先先创建对象，再在明确的持久化上下文中建立关系。
- `service` 负责 SwiftData 的读写、副作用边界和持久化协调；不要让 `view` 到处直接写 `modelContext`。
- `store` 负责页面状态、派生状态和加载状态；不要把原始 SwiftData 对象图直接当作整页状态管理的唯一抽象。
- `view` 只负责渲染和触发事件，不负责直接编排 SwiftData 写入、保存和迁移逻辑。
- 应用级依赖可通过 `Environment` 注入 `ModelContainer`、`ModelContext` 或上层 service。
- SwiftData 并发默认优先使用 `@ModelActor` 隔离读写操作；不要在多个并发上下文中随意共享和传递 model 实例。
- 对后台导入、批量处理、异步写入或跨任务持久化访问，优先在 `@ModelActor` 或明确持久化边界内完成，而不是把 `modelContext` 和 model 对象直接散落到各处任务中。
- 不要假设 SwiftData model 实例天然适合跨并发边界传递；跨任务传递时优先传递稳定标识、输入值或显式可发送的数据。
- 若使用 SwiftData，schema 迁移必须显式声明迁移方案；不要依赖默认或隐式迁移行为。

### 6. 默认用类型表达业务约束

- 能通过类型表达的业务约束，优先放进类型系统，而不是留给运行时分支处理。
- 对输入、DTO、数据库模型和第三方返回值，应在边界尽早解析为更强的领域类型。
- 不要让 DTO、JSON schema 类型、数据库模型直接污染业务层和 UI 层。
- 对互斥状态优先使用 `enum` 建模，不要用多个 `Bool` 或 `Optional` 拼凑。
- 对前置条件、权限态、能力开启状态，优先使用明确类型或 witness 表达，而不是只传 `Bool`。
- 领域建模优先从领域原语开始，例如 `Email`、`Money`、`UserID`、`FeatureFlag`，再用 `struct` 组合 AND 关系、用 `enum` 表达 OR 关系。
- 不要在核心领域模型里长期传播裸 `String`、`Int` 等弱类型身份值；优先定义专属 `ID` 类型，避免跨领域身份混用。
- 业务错误应优先建模为明确的错误类型，不要长期依赖无结构字符串、日志或宽泛 `Error` 掩盖真实失败语义。
- 对理论上不可能失败的路径，优先考虑 `Never`、移除失败分支，或重新调整类型设计。

### 7. 让非法状态不可表示

- 对业务上不应出现的状态，优先修改类型设计，而不是在运行时到处补 `if`、`guard`、日志或兜底分支。
- 对 `nil`、空数组、空字符串、零值这类零元素保持警惕；技术上可表示不等于业务上合法。
- 核心业务 API 应优先接收已解析、已验证的强类型，而不是原始弱类型。
- 能通过展开类型结构发现非法组合时，应优先重新建模，而不是继续往原模型上追加保护性分支。

### 8. Task 与取消语义

- 能用结构化并发时，不要随手创建顶层 `Task {}`。
- 非必要不使用 `Task.detached`；若必须使用，需要在代码中说明原因。
- 当并发子任务数量固定、彼此独立、结果类型明确且需要在当前作用域内一并等待时，优先使用 `async let`。
- 当子任务数量动态变化、需要在运行时决定 fan-out 规模、逐步收集结果或按子任务完成顺序处理结果时，优先使用 `withTaskGroup` 或 `withThrowingTaskGroup`。
- 不要用 `withTaskGroup` 处理固定且很小的一组并发任务；这种场景通常应优先用 `async let` 保持结构更简单。
- 不要为了“并发化”而把本质上存在严格前后依赖的步骤硬拆成 `async let` 或 task group。
- `async let` 的子任务应在同一作用域内被明确等待或消费，不要让其生命周期和数据依赖变得隐式。
- task group 中每个子任务应尽量是同构、可独立取消、可独立失败边界明确的工作单元；不要把大量共享可变状态塞进 group 内部协调。
- 需要部分收集、逐步归并、限于输入集合动态扩展或按完成顺序消费结果时，优先选择 task group；仅为了同时等待固定几个结果时，不要上升到 task group。
- 异步调用链应正确传递取消语义；对耗时任务、循环任务、分页拉取和监听流要在合适位置检查取消状态。
- 对可抛错的异步流程，优先在合适的挂起点使用 `try Task.checkCancellation()`；对不抛错流程，可使用 `Task.isCancelled` 做显式短路。
- 当检测到任务已取消时，应尽快停止后续工作，避免继续发起网络请求、写入状态、提交 UI 更新或落盘副作用。
- 若取消后需要做清理，只做幂等且必要的清理工作；不要在取消路径中继续追加新的业务副作用。
- 不要吞掉 `CancellationError` 并伪装成成功完成；若调用链需要感知取消，应保留取消语义继续向上传递。
- 在循环、批处理、分页、重试和流式消费等长生命周期任务中，应在每轮或每个自然边界检查取消，而不是只在入口检查一次。
- 创建 `Task` 时应明确其所有权和生命周期；谁创建，谁就应负责取消时机、结果消费和资源释放。
- 对与界面绑定的任务，优先让任务生命周期跟随界面状态或明确的状态持有者，而不是悬空运行。

### 9. 共享状态与 Sendable

- 新增共享可变状态时，必须明确其隔离方式。
- 所有跨并发边界传递的类型，都应优先考虑 `Sendable` 设计。
- 非必要不要使用 `@unchecked Sendable`；若必须使用，需在代码中说明安全前提。
- 不要为了消除告警而滥用 `nonisolated`。

### 10. 用函数签名表达业务流程

- 设计核心业务流程时，优先先写清输入和输出类型，再进入实现细节。
- 上游函数输出应尽量直接成为下游函数输入，不要在流程中途把已解析、已验证的数据重新降级成弱类型。
- 不要依赖隐式约定、共享可变状态或分散布尔开关去串联核心流程。

### 11. Witness 构造边界

- witness 应在可信边界构造，例如解码成功、鉴权成功、配置加载成功、持久化确认成功之后。
- witness 初始化应限制可见性，避免被任意伪造；受限 API 应通过非可选 proof 参数表达前置条件。
- 对仅用于证明前置条件成立的参数，可优先使用黑洞参数风格，明确“这是证明，不是业务数据”。

### 12. 类型也是测试

- 当非法状态已被类型消除时，测试重点应转向解析器、构造路径、边界转换和 witness 生成路径。
- 不要为理论上已不可构造的非法状态继续堆积运行时兜底测试；先确认这些状态是否真的已被类型消除。
- 对强类型封装、解析器和领域转换逻辑，应优先补充单元测试，证明弱类型输入无法绕过边界进入核心业务流。

## 旧 API 与旧代码处理原则

- 对旧的 callback/completion handler 接口，优先在桥接层封装为 `async`、`async throws`、`AsyncStream` 或 `AsyncThrowingStream`，再供新业务代码调用。
- 新代码不得继续直接扩散旧式 callback API，除非该模块本身就是兼容层。
- 修改旧代码时优先做渐进式迁移，不要一边保留旧式编排，一边继续在其上叠加新的旧式逻辑。
- continuation 封装必须清晰处理恢复时机、错误传播、取消语义与隔离语义。

## 实现约束

- 与现有命名、目录结构和模块边界保持一致。
- SwiftUI 实现必须保持状态驱动、职责清晰和可访问性；不要让 `view`、`store`、`service` 的边界重新混乱。

## 验证要求

- 修改结束前，优先运行仓库已有的构建、测试、lint 或脚本命令。
- 若无明确说明，选择与改动范围匹配的最小有效验证方式。
- 结果说明中应明确写出：
  - 做了哪些验证
  - 哪些验证无法执行
  - 哪些风险仍需人工确认

## 明确避免的反模式

- 新的 completion handler 风格异步接口
- 新业务代码直接调用旧的 callback API，而不先封装成 async API
- 大量 `DispatchQueue.main.async` 拼接出来的 UI 更新流程
- 没有说明原因的 `Task.detached`
- 没有隔离策略的共享单例可变状态
- 把 `nonisolated` 或 `@unchecked Sendable` 当作消警告工具
- 用 `Bool` 表达复杂业务状态
- 用多个 `Optional` 表达互斥状态
- 把“已验证”数据重新降级成原始弱类型后继续流转
- 在多个领域对象之间共享裸 `String`/`Int` 身份值，导致身份可被误混用
- 在业务层直接传播 DTO、网络模型、数据库模型或第三方模型
- 用宽泛 `Error`、日志字符串或静默失败长期代替明确的领域错误建模
- 把复杂、易变或未来需要筛选与演进的 `Codable` 结构直接固化到 `@Model` 字段中
- 在 `@Model` 初始化中直接搭建复杂关系图或隐式完成持久化关系写入
- 在 SwiftUI `body` 中直接堆叠副作用、业务保存、网络调用或复杂 `Binding(get:set:)`
- 在 SwiftUI 里默认回退到过时导航和状态管理方式，而不是优先采用现代原生 API
- 在 SwiftUI 中机械引入只做转发的中间层、协议层或 DI 框架，导致样板明显多于真实业务边界
- 让 view 直接持有副作用实现，或让 service/store 直接承担视图渲染职责
- 用多个 Bool / Optional 临时拼装加载、错误、空态和内容态，而不是用明确状态模型表达
- 为必须注入的依赖提供静默默认值，导致缺失注入时错误被延后暴露
- 在多个并发上下文之间直接共享 SwiftData model 实例或随意传递 `modelContext`，而不通过 `@ModelActor` 或明确边界隔离
- 在 SwiftData schema 演进时依赖默认迁移，而不是显式声明迁移策略
- 通过任意可构造的 witness/flag 表达前置条件，导致 proof 可被轻易伪造

## 修改原则

- 正确性优先于技巧
- 清晰性优先于炫技
- 显式隔离优先于隐式假设
- 渐进式迁移优先于大面积重写
- 最小安全改动优先于一次性推翻重做
- 修改应尽量保持可验证，并持续推动代码向现代并发与更强类型建模收敛
- 优先通过类型系统表达业务约束，而不是把约束留到运行时分支中处理
- 优先在边界解析数据，而不是让弱类型数据污染整个调用链
- 对 SwiftUI 页面，优先采用单向数据流、状态驱动渲染与清晰的 UI 边界
- 先让类型、函数签名和边界证明正确，再让实现细节填充进去
