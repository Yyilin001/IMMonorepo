# SwiftUI 审查补充

当目标模块使用 SwiftUI 时，在通用审查清单之外补充读取这份文档。这里不重复“状态驱动”“不要在 `body` 放副作用”这类通用规则，只补充更细的实现细则与审查边界。若需要理解这些规则背后的 diff、render loop 和 AttributeGraph 原理，继续读取 [swiftui-internals.md](swiftui-internals.md)。

## 1. 实现细则

- 对共享可观察状态，优先保持明确所有权与隔离；若状态驱动 UI，通常需要明确主隔离语义。
- 避免在 `body` 中构造复杂 `Binding(get:set:)`；若确实需要副作用，优先通过明确事件、方法或状态变化钩子处理。
- 视图结构应便于组合与测试，避免在单个 `View` 中塞入过多分支和布局细节；必要时拆出子 View 或辅助类型。
- 避免在 `body` 中进行排序、过滤、格式化或其他重复高成本工作。
- 对较大列表优先使用惰性容器，并确保元素身份稳定。
- 谨慎使用类型抹除和额外层级；`AnyView`、无必要的 erased wrapper 和过深包装层会削弱 SwiftUI 基于静态类型的 diff 优势，只有在确实必要时才使用。
- 优先保留稳定、可推断的静态视图结构；不要为了抽象或“统一接口”过早把分支压成运行时类型擦除。
- 异步加载优先挂在明确的任务生命周期上，而不是依赖零散的出现时副作用。
- 不要把 `body` 重新求值等同于一次真实渲染；评估问题时应区分“重新计算”“布局更新”和“用户可见的重复副作用”。
- 对 `onAppear`、`PreferenceKey`、几何测量或布局反馈驱动的状态写入保持警惕，避免形成“状态更新 -> 布局变化 -> 再次写状态”的反馈回路。
- 构建可复用 SwiftUI 组件时，若可以在初始化阶段把 `@ViewBuilder` closure 物化为具体视图，就不要把 escaping closure 长期存起来再在 `body` 中调用。
- 对需要插槽内容的组件，优先使用泛型和具体 `View` 类型保持可比较结构；不要同时依赖 escaping closure 和类型擦除去模拟“懒构建”。
- 导航目标优先用强类型路由建模，不要把字符串、零散 Bool 或临时回调当长期导航真相。
- `NavigationStack(path:)` 的 path 必须有单一事实来源，通常应由 store 或明确状态持有者集中维护。
- `navigationDestination` 的映射应集中管理，不要把 destination 分发逻辑散落在多个页面里重复维护。
- 当同一路由可能多次入栈时，导航身份应与业务路由分离，不要假设同一个路由值天然等同于同一个导航实例。
- 有明确载荷的模态优先使用 `sheet(item:)` 或 `fullScreenCover(item:)`，而不是退回多个布尔开关。
- 不要用多个 Bool 拼装互斥导航和模态状态；互斥导航状态应优先通过枚举或带载荷的单一状态表达。

## 2. 审查边界

- 不要把“可以更现代”直接表述成“有 bug”；只有存在明确风险时才上升为 finding。
- 不要仅因个人偏好要求把可工作的实现重写成另一种 SwiftUI 写法；先判断是否真的存在正确性、可维护性或可访问性风险。
- 不要仅凭 `body` 多次求值、`onAppear` 多次触发或调试日志顺序，就草率断定发生了多次真实渲染或用户可见闪烁；应先确认是否真的造成重复副作用、状态漂移或性能问题。
- 不要把所有 `AnyView` 或 closure 存储都一律判为错误；只有当它们确实破坏身份、增加 diff 成本、隐藏依赖追踪，或让组件接口明显复杂化时，才上升为 finding。
