# 直聊 room-log：严格稳态容量复测（2026-08-21）

## 目的

这次复测验证的是已经建立双向会话后的单机直聊热路径，并把“停止注入后才排空”与真正的稳态吞吐明确区分开来。此前的负载工具只报告最终 ACK，可能把本机模拟客户端遗留队列在连接关闭时丢弃的情况误写成成功。

本次工具为场景增加了三个显式契约：

- `requiresSteadyStateDrain`：稳态阶段结束时不能有队列溢出；
- `maximumSteadyStateQueuedMessages`：允许最多 64 条边界 ACK 尾部，避免把最后一个 100ms 调度片中的正常网络往返误判为过载；
- `completionDrainSeconds`：关 TLS 前最多排空 10 秒，并单独记录排空耗时和残留工作。

因此，后续报告不能以“最终 ACK 数”单独宣称吞吐通过。

## 环境与模型

| 项目 | 值 |
| --- | --- |
| Gateway / PostgreSQL | 一台 8 vCPU / 16 GiB ARM ECS，单 PostgreSQL 实例 |
| 客户端 | 本机 Mac，经公网 TLS；1,500 条已认证长连接 |
| 消息 | 128 B 普通私聊消息；每设备 3 个对端；无 Sync、room-log pull 或重连 |
| 时长 | 60 秒稳态阶段；100ms 加权调度 |
| 分发 | 每设备最多 1 个在途消息、最多 32 条本机保留队列 |
| 可靠性 | 普通消息写入仍走 PostgreSQL 事务；缓存分类不绕过房间、成员、策略版本或幂等锁校验 |

每个新 profile 都创建 8 个 `shard_admission_pools`。此次使用独立的 `loadtest-v6`，避免已满的 `loadtest-v5` 命令窗口产生 `RATE_LIMITED` 干扰。

## 冷关系与热关系

新账号首次进入私聊时，双方尚未都写入 `senderHasReplied`。该状态会影响陌生人配额和发送策略，不能只信任进程缓存，也不能与已建立会话混入同一种批量路径。

在干净 `loadtest-v6` 的第一轮 900 msg/s 中，安全回退到逐条授权路径：52,753 / 54,000 ACK、1,240 条本机队列溢出、7 个可重试 `UNAVAILABLE`，消息 P95 为 1,361 ms。因此它**没有通过**稳态标准。随后使用同一批已互发消息的账号重测，才代表高活跃已建立会话的稳态能力。

这不是把冷关系问题隐藏掉：它是后续 Direct Append v2 的独立优化目标。其正确做法是把首条/陌生人策略做成同样带版本围栏的 set-based mutation，而不是用缓存写回替代数据库授权。

## 已建立会话的严格结果

| 目标速率 | ACK / 计划数 | 消息 P50 / P95 / P99 | 阶段末尾队列 | 排空耗时 | 结果 |
| ---: | ---: | ---: | ---: | ---: | --- |
| 900 msg/s | 54,000 / 54,000 | 68 / 149 / 175 ms | 0 | 78 ms | 通过 |
| 1,000 msg/s | 60,000 / 60,000 | 78 / 162 / 196 ms | 3 | 137 ms | 通过 |
| 1,100 msg/s | 66,000 / 66,000 | 83 / 172 / 248 ms | 12 | 134 ms | 通过 |
| 1,200 msg/s | 72,000 / 72,000 | 90 / 205 / 335 ms | 4 | 208 ms | 通过 |
| 1,400 msg/s | 84,000 / 84,000 | 110 / 225 / 377 ms | 31 | 196 ms | 通过 |

所有通过行都满足：零连接失败、零业务失败、零本机队列溢出、阶段尾部不超过 64 条，并在 10 秒排空窗口内实际排空。1,400 msg/s 是当前测到的下界，不应表述为最终硬件上限；本模型尚未混入读同步、重连、媒体和群组流量。

## 与批量资格分区前的对照

相同 1,500 在线、800 msg/s 的早期对照中，消息 P50 / P95 / P99 为 204 / 535 / 2,361 ms；细粒度资格分区后的热态为 57 / 354 / 540 ms。PostgreSQL 观测到消息写 CTE 调用约减半、房间锁定/预读 CTE 调用约减少 62%、事务提交减少约 28%、WAL sync 累计耗时减少约 62%。这些是同类压测下的实测对照，不能外推为所有消息形态的固定比例。

## 1,400 msg/s 的数据库热点

以下统计含连接/房间预热，因此用于排序和趋势判断，而非单条消息纯成本：

| 热点 | 调用 | 累计执行时间 | 平均 |
| --- | ---: | ---: | ---: |
| set-based 消息 append CTE | 39,884 | 62.7 s | 1.57 ms |
| 锁定房间/成员/策略预读 CTE | 29,838 | 42.9 s | 1.44 ms |
| 批量预检 CTE | 5,829 | 27.7 s | 4.75 ms |
| WAL sync | 36,427 | 28.3 s | — |

下一项结构性收益应来自减少首条/陌生人关系的逐条授权工作，且必须保留：操作幂等锁、直接关系策略版本、成员/房间版本和 quota 的事务原子性。
