# Colima 独立虚拟机下的私聊扩容对照

每档从同一份数据库快照恢复，预热 5 秒，再测 60 秒。稳定档要求两次独立窗口均满足计划发送至持久化 ACK 的 P99 ≤ 100 ms、计划消息未确认率 ≤ 0.1%、线上提交被服务端拒绝的比例 ≤ 0.1%。同时检查窗口完整、客户端无最终业务或连接失败、房间承载数正确、总落库行数等于初始 16 条加所有预热和测量 ACK。

| Room Host × 主库 | 两次通过的最高实测档（条/秒） | 窗口内实际 ACK/s | 两次 P99（ms） | 更高档位的观测 |
|---|---:|---|---|---|
| 1 × 1 | 300 | 300.00、300.00 | 68、16 | 400 条/秒时 P99 为 8、214 ms |
| 2 × 1 | 200 | 200.00、200.00 | 5、5 | 300 条/秒时 P99 为 391 ms |
| 2 × 2 | 600 | 599.99、600.00 | 35、100 | 800 条/秒时 P99 为 1981 ms |

增加 Room Host 后，跨 Host 路由生效，最高两次达标档从 300 降至 200 条/秒。保持双 Host 并拆分主库后，最高两次达标档升至 600 条/秒，第二次 P99 正好达到 100 ms 上限。三倍的差异仅指本次实测档位。

## 部署与流量

一台 Apple M4 Pro（14 核，48 GiB）承载五台 Colima VZ ARM64 Linux VM，各配 2 vCPU、3 GiB。两个 Gateway/Room Host 和两个独立 PostgreSQL 16 主库各占一台 VM，未使用的角色不启动服务。第五台运行压测器和三个 Placement 投票进程。业务流量走 VM 间虚拟网络，磁盘共享宿主机 SSD。首轮发现部分 VM 的 systemd-logind 持续占满一个 vCPU，五台临时停用该服务后重跑，表格和 CSV 仅收录重跑数据。

同一批 16 个用户在 16 个私聊房间轮流发送 128 字节文本。固定逻辑分片各有 6 和 10 个房间。双 Host 实测各承载 8 个房间，客户端统一连接第一个 Gateway。第二个主库只接走 10 个房间的分片，控制库、两个用户分片和另外 6 个房间仍在第一个主库。压测器以 100 Hz 调度，16 条 TLS 连接各最多 4 条在途、128 条排队。沿用上一轮测试的放宽准入额度；仅测试既有会话发送，未加入附件、读历史和重连。

服务端与压测器使用 Swift 6.4.2 ARM64 Linux release 静态构建。为匹配 musl，临时源码副本适配了 libc 导入，构建依赖适配了 HTTP 迭代器的并发检查。压测关闭本地媒体功能。此前 macOS debug 原生进程的数值使用不同构建与网络路径。

单 Host 单库在 600 条/秒复测的测量第 48–50 秒，64 个在途名额占满，已调度但尚未提交的消息一度达到 894 条。同一时段，主库 VM 一次 1.52 秒采样内累计约 1.20 秒有任务等待 I/O，前一个采样约 0.13 秒。数据库 I/O 停顿与随后的排队放大同时出现。两主库仍共用一块物理 SSD，数据库主机的 I/O 计数无法区分 PostgreSQL、虚拟磁盘和底层 SSD 各自的贡献。宿主机还有其他工作负载。

CPU 按各 VM 两个 vCPU 的总容量归一化。CSV 的 CPU、I/O wait 与磁盘忙碌比例取负载开始后约第 11–61 秒的计数器差，宿主机空闲取相应时间段平均。数据库 I/O 压力峰值列为单个采样周期内 Linux PSI 记录有任务阻塞于 I/O 的时间比例。阶段耗时为预热和测量期间各 Host 计数器汇总均值。“稳定”描述两次 60 秒验证，容量区间内仍有未测档位。
