# 普通私聊跨房间合批实测，2026-11-18

同分片跨房间合批已接入普通私聊写路径，默认上限为 1。四组在已测档位中，通过发送门槛的最高目标均为 1000 条/秒。1000 至 3000 之间没有加测中间档。所有组的 5000 条/秒档与整轮接收端同步覆盖均未达标。

## 本机发送结果

每格为发送窗口内每秒收到的持久化 ACK 数和从计划发送到 ACK 的 P99 毫秒数。✓ 表示该短窗口的调度速率和 ACK 速率均在目标的 0.5% 内，P99 ≤ 100 ms、服务端拒绝率和计划未确认率均 ≤ 0.1%，5 万连接保持在线，客户端队列无溢出。拒绝率的分母是实际提交尝试，计划未确认率的分母是本阶段的目标消息数。重试和排空期间迟到的 ACK 单独计入该阶段的最终确认数。10000 毫秒是压测器最后一个直方图桶的下界。

单 Host 单主库开启合批时，3000 档实际确认 2998 条/秒，18 万条计划消息最终全部确认，服务端拒绝为零，但 P99 为 180 ms，超过 100 ms 门槛。5000 档合批把每千条写入的追加 SQL 减少了 51.7%。5000 档的合批批首从入队到事务确认平均 129.7 ms，执行阶段平均 35.9 ms，差值约 93.8 ms 花在领取之前。同窗口四条消息追加 SQL 的 PostgreSQL 平均执行时间为 0.88 ms。该 SQL 指标不含完整的事务提交、队列等待、远程路由和客户端等待，各计时范围及样本不同。主实例的活动会话采样中也出现 WAL 写入和轻量锁等待，本次数据不能把端到端长尾唯一归因于磁盘、TCP 或 SwiftNIO。

两个 Host 均在 5000 档处理了写入。所有连接通过第一个 Gateway 进入，2 Host + 1 主库与 2 Host + 2 主库的 Gateway 在目标窗口内分别记录 20,590、19,076 次远程 Actor 调用失败（按两端完整秒取样）。详表列出了客户端收到的忙和不可用拒绝数。远程错误日志按重试尝试计数，与终态消息数口径不同。现有日志把底层调用错误统一记成 `remote_call`。

另做了低负载对照。保留同一组 1.4 万个活跃客户端与相同消息，空闲连接从 36,000 个减到 8 个。合批上限 4，50 条/秒持续 90 秒，14,008 在线时 P99 11 ms，50,000 在线时为 28 ms。缩减连接数时，压测器原先会给每个进程默认分配 128 个恢复 worker，超过小进程自身的连接数，启动参数校验失败。修正默认值后才计入本次对照。

## 持久化与接收端

压测客户端保存每个终态请求的房间、发送者、客户端消息 ID 和结果。对每个 ACK 在权威房间库中查找唯一操作，并同时核对消息表和永久完成记录中的消息 ID、房间序号。每个使用的房间必须恰好归属一个被检查的 database。另用本轮固定 128 字节消息计数，检查是否存在客户端终态清单之外的写入。接收端指标来自两个活跃负载进程的 1.4 万个连接，按整轮结束时的覆盖证明计算。[逐条对账工具](../../scripts/verify_v2_load_message_audit.py)

|---|---:|---:|---:|---:|---:|---:|
| 1 Host + 1 主库 | 1 | 391,256 | 0 | 23 / 3 | 0 / 0 | 3,465 / 14,000 |
| 1 Host + 1 主库 | 4 | 408,710 | 0 | 12 / 1 | 0 / 0 | 4,363 / 14,000 |
| 2 Host + 1 主库 | 4 | 288,926 | 0 | 18,122 / 23 | 0 / 0 | 3,384 / 14,000 |
| 2 Host + 2 主库 | 4 | 271,186 | 0 | 18,166 / 27 | 0 / 0 | 3,337 / 14,000 |

主对照四组共逐条核对 1,360,078 个持久化 ACK，均可匹配唯一消息与永久完成记录。四组共有 54 条操作在客户端显示结果未知、在权威房间库已提交。重试时沿用原身份核对结果。接收端覆盖按包含过载阶段的整轮衡量，无法用该指标给单个 1000 档判定同步通过。每组都没有达到整轮接收端覆盖要求。

在加入最终保护检查前另做过一轮同配置、已修复 FIFO 的单 Host 合批复测。5000 档确认 1,903 条/秒，402,159 个 ACK 逐条匹配。此前未逐条记账的两轮过载试跑，关闭合批与开启合批分别确认 2167、1904 条/秒。跨轮过载吞吐有波动，表中的短测达标档位用于判断本轮收益。

## 实验条件

同一台 Apple M4 Pro（14 核，48 GiB），原生 Release Room Host/Gateway、Debug 发压器与 PostgreSQL 16.13，所有消息写连接走 TCP。每组从同一个快照启动，包含控制库、两个固定用户分片库和两个固定房间分片库。5 万个不同账号、设备和目标房间，3.6 万个连接保持在线，1.4 万个连接参与发送。六个客户端进程全部认证后统一放行。每条消息 128 字节，同一组种子和发送计划，队列饱和时实际调度会落后。所有客户端均连接第一个 Gateway，第二个进程通过真实的跨 Host 路由分担工作。

50 条/秒持续 90 秒，1000、3000、5000 各持续 60 秒，阶段间排空窗口分别为 15、20、30 秒，结尾再排空 45 秒。每个 Host 配置 4 个数据库写事件循环，流水线深度 2，集群写连接预算固定 16。单 Host 每个房间 database 8 条，两 Host 各给每个房间 database 4 条。集群活跃房间上限 3 万。所有房间主库校验 `synchronous_commit=on` 和 `fsync=on`。本次拓扑采用主库本地持久化，无同步备库。内存保护按进程足迹加 4 GiB 的数据库等预留估算，达到 30 GiB 就停止测试。macOS 原生进程共享宿主机资源。

## 正确性与故障

- 最终 Release 构建成功，选择的 12 个 Swift 测试函数通过。其中跨房间回归运行了 7 个参数化场景。真实 PostgreSQL 集成测试覆盖多房间共用一个事务、一个房间内两条消息按 Actor 输入顺序获得连续序号、不同房间复用客户端消息 ID、超过 64 KiB 时分别执行。持久化后在各 Actor 应用结果前，冷启动的存储实例能读出原 ACK，改变内容的同键请求返回指纹冲突。
- 让第二个房间的归属版本或已准备好的策略授权失效，验证整批没有写入。在写完成记录时注入约束失败，验证已执行的写入随事务回滚。三种情况下，健康房间均可独立提交。对延迟 COMMIT 的连接制造确认丢失，同一组原始操作重新核对后每条只落一次。原有取消、单房间 FIFO、回滚和物理连接复用也经过回归。
- 在两套独立数据上各做一次停机迁移。首次移动有消息的 `rooms-01`，最终版本复验移动有消息的 `rooms-primary`，目的地均为另一个 PostgreSQL 实例，源 database 禁止连接。保持分片 ID，原账号重试得到相同 ACK，迁移前历史可读，双方继续互发并读到新消息。
- 向一间已确认有写入的房间定位实际 Owner 后，用 SIGKILL 终止对应 Room Host。两个 Host 的提交增量为 [0, 1]。本机原生启动没有部署排除旧进程的 Supervisor，生存 Host 在 100 秒窗口内未确认该房间的新消息。三个投票节点在前后检查时仍指向原 Host，epoch 为 2。这组部署的 Host 自动接管未通过。[Host 监督与排除](../10-operations/room-host-supervision.md)
- 对 `rooms-01` 的独立主实例执行 PostgreSQL immediate stop。另一分片仍成功写入并由接收方读到新消息。该实例连接的备库数为 0，停机后没有自动提升。在故障后约 14.1 秒手动恢复。故障前的 ACK 对应一条持久消息，原请求重放返回同一 ACK，历史及双方后续收发通过。

目标档未达到候选容量门槛，因此未进入三轮 10 分钟及 60 分钟稳态验收。原生进程部署下，发压端、Gateway、Room Host 和数据库共享一台机器的 CPU、内存和磁盘。32 GiB 是本轮预算，macOS 原生进程没有硬隔离。独立主机横扩增益、同步备库自动提升、物理整机故障后的吞吐以及全量接收端无漏无重均待验证。
