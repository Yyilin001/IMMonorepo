# 增加服务器承载更多用户

常规验收沿用现有节点准入、入口连接均衡、房间分区迁移、路由及消息正确性机制。以增加业务服务器后的用户承载表现为主线，故障注入、崩溃接管和缩容另行安排。消息幂等、权限与唯一归属检查继续生效。

## 固定每用户活跃度的规模对照

使用相同运行包、每台业务服务器资源、固定数据库和负载发生器资源。默认每台业务服务器对应 1200 个在线用户和每秒 150 条消息，测试 1、2、4、8 台；每档测量 600 秒、重复两次，第二轮反向执行。所有档位固定八个负载分片。用户数、每用户发送频率或测量时长的调整必须在系列开始前指定。

```sh
python3 IMV2/scripts/run_v2_multiserver_capacity.py \
  --deployment /private/deployment.json \
  --output-dir /private/user-growth
```

只测试已准备好的规模时显式指定，例如先测 1、2 台：

```sh
python3 IMV2/scripts/run_v2_multiserver_capacity.py \
  --deployment /private/deployment.json \
  --output-dir /private/user-growth-two-nodes \
  --nodes 1 2 --users-per-node 1200 --rate-per-node 150
```

这些命令运行独立的固定规模实例，不在运行中迁移同一批用户。所选业务节点、账号、控制、入口、数据库和八个负载分片须预先就绪；不要求配置中未参与本系列的业务 VM 启动。运行前停止其他压测和构建。脚本冻结源码、运行包和所选 VM 资源配置，逐轮保留完整原始证据。

`user-growth.md` 是结果表；`user-growth.json` 保留逐轮发送/接收延迟、实际吞吐、失败数和前台一致性；`campaign.json` 记录运行状态。只在全部重复轮次通过正确性、消息完整性、接收延迟及退出检查时确认该档负载。失败或未测档位保留在结果中，不计为已验证用户数。

这里确认的是指定活跃度下的已测用户规模，不能将用户配置增加 8 倍写成容量增加 8 倍。用户容量上限需要逐档提高 `--users-per-node`，并始终保持相同 `--rate-per-node / --users-per-node` 比值。共享物理宿主机的 VM 结果单独注明；真实服务器的容量增长需在独立机器上复测。

## 在线扩容

在线扩容另用 `run_v2_multiserver_case.py` 已有的连续增长流程：

在线加入使用显式的离线签名环境。部署 JSON 增加 `"authorityProfile": "imv2-growth-authority"`，该 VM 必须与业务、控制和负载角色分开；共享挂载覆盖运行包与本轮私有目录，并保持相同路径。可用 `colima start --profile imv2-growth-authority --cpu 1 --memory 1 --disk 20 --arch aarch64` 准备。签名工具在隔离网络命名空间执行，构建 VM 与构建镜像不参与在线扩容。固定规模系列不需要启动签名 VM。

```sh
python3 IMV2/scripts/run_v2_multiserver_case.py \
  --deployment /private/deployment.json \
  --output-dir /private/online-user-growth \
  --nodes 1 --parts 8 --users 9600 --rate 150 \
  --seconds 9000 --warmup-seconds 120 --warmup-rate 100 \
  --dynamic-membership --live-scale-out-at 300 \
  --continuous-user-growth --live-scale-out-rebalance \
  --growth-measurement-seconds 120 --measure-visibility \
  --server-log-level warning
```

连续模式的 `--users` 指定峰值用户数，`--rate` 指定初始发送速率；本例从 1200 用户、150 条/秒增长到 9600 用户、1200 条/秒，与固定规模系列保持相同的每用户活跃度。每次加入新节点后同时检查连接分配与全量分区配额，最终核对全部消息和前台视图。该流程依赖部署中的成员和迁移控制角色；命令与详细前提见 [Host 监督与在线扩容](../10-operations/room-host-supervision.md)。本次选定运行包已完成完整在线增长验证，结果见下文。

此前逐分区串行实现会分别启动检查、迁移和复查进程。既有整轮中，每阶段 128 次迁移的首尾间隔约为 1886～1899 秒；9000 秒窗口用于覆盖三阶段迁移、后续用户预热和共同测量。2400 秒不足以覆盖已观测的迁移耗时。此窗口不是扩容耗时承诺，命令执行仍以实际迁移与完整性证据为准。

迁移检查现已合并：每次迁移前的最新快照，同时核验上一条迁移回执的结果及本次迁移前提；最后一条回执与全部已迁移分区通过最终全量快照核验。检查保留准确的 Host incarnation、epoch、退役和未完成迁移状态，并在成员最终提交及收敛时核对。全量均衡每阶段少启动 128 次独立检查进程。31 项迁移相关回归及包含授权、接收统计的 53 项流程相关 Python 测试通过；在线验证及实际耗时见下文。

持续用户增长现可同时启用 `--measure-visibility`，仍要求全部加载器共享同一个 Linux 时钟；分批启动、测量时长不同的用户组按消息原始测量阶段合并，缺失接收端样本会使验收失败。

## 专项测试

固定 1 万用户的吞吐上限搜索保留为显式选项：`--profile throughput`。它包含搜索、三次确认和长时间稳定性测试，输出吞吐边界；不会给出最大在线用户数。故障暂停及诊断观察不加入常规用户增长系列。

现有自动接管、会话权限和多数派管理互相有依赖。当前收敛常规运行与验收范围，不通过直接移除这些正确性检查来简化部署。

## 优化后的在线增长结果

`horizontal-online-growth-optimized-3` 在原有用户持续发送消息时完成 1→2→4→8 节点扩容，在线用户从 1200 增至 9600，目标消息速率从每秒 150 条增至 1200 条。每台业务 VM 为 1 vCPU、3 GiB，运行包与固定规模系列相同；构建 VM 全程关闭。扩容前后 VM 资源配置核对一致。

| 扩容阶段 | 在线用户 | 实测每台连接 | 最终每台分区 | 已核对迁移数 | 首笔至末笔迁移间隔 |
|---|---|---|---|---|---|
| 1→2 | 2400 | 1200 | 128 | 128 | 1436.81 秒 |
| 2→4 | 4800 | 1200 | 64 | 128 | 1434.09 秒 |
| 4→8 | 9600 | 1200 | 32 | 128 | 1435.62 秒 |

每阶段独立核对全部 256 个分区的准确归属、128 笔不可变迁移请求及回执、目标实例和 epoch。新增节点实际承担活跃房间工作；最终新增四台在扩容完成快照中各有 607、645、644、649 个活跃房间。三个阶段共省去 384 次独立迁移后检查进程。上述时间只覆盖首笔到末笔迁移；历史轮次使用不同运行包，不将时间差全部归因于检查合并。

八组用户的共同正式测量窗口为 3230.624 秒。5880150 条测量消息全部确认并被对端应用，9600 个最终前台视图全部追平数据库消息头，无业务失败或漏心跳。对端应用延迟 P99 为 70 毫秒，最大值为 13254.17 毫秒，本轮仍存在接收长尾；该指标测量模拟客户端连续应用消息正文，不包含 UI 渲染。816 个远程进程正常退出，无强制终止或退出失败。

原始报告、三阶段成员与迁移证据、最终视图、2439 个冻结输入及完整运行包清单已独立核验通过。证据位于 `/Users/yyl/Desktop/IMV2-Retirement-Fix-20261019/horizontal-online-growth-optimized-3` 的 `independent-online-growth-validation.json`、`assessment.json` 和 `run/candidate`。各 VM 共享同一物理宿主机；本轮证明正常在线扩容和这些已测负载，用户容量上限、独立物理服务器的容量扩展效率仍需另行测量。
