# 10,000 条停止读取连接，每条约 1 次/秒：本机传输实验

日期：2026-09-26
状态：实验未通过恢复读取检查；不能据此宣称完整消息积压可正常消费，也不能据此归因于某一层实现。

## 负载和测量范围

在同一 macOS 进程中建立 10,000 对真实 TLS 套接字，8 个 NIO 事件循环线程。
全部客户端在握手后停止读取；服务端通过生产 `V2NIOGatewayForegroundWriter` 和调度器，
每隔约 1 秒向每条连接提交一个 1 KiB 原始数据块，共 300 轮，再提交一个 1 KiB 探针。
不预装额外积压。收发套接字缓冲区均请求设为 4 KiB，实际大小由操作系统决定。
提交过程耗时 316.9 秒，因此实际平均约为每条连接 0.95 块/秒。

总计向连接提交 3,010,000 块、约 2.87 GiB 的逻辑数据；每条连接预期在恢复读取后
收到 301 KiB。这里一块只是压测字节，不是经过 protobuf 编码的业务消息。
RSS 是客户端与服务端所在测试进程的驻留内存，不包含完整的内核套接字缓冲占用。

## 实测

| 指标 | 结果 |
| --- | ---: |
| TLS 连接就绪 | 10,000 / 10,000 |
| 发送前进程 RSS | 1,060 MiB |
| 第 50 / 100 / 150 / 200 / 250 / 300 轮进程 RSS | 1,220 / 1,220 / 1,221 / 1,221 / 1,221 / 1,221 MiB |
| 生产写者因不可写而延后 / 恢复帧替换 | 0 / 0 |
| 单连接前台写队列观测峰值 | 1,024 B |
| 恢复读取 300 秒后收到末尾探针 | **0 / 10,000** |
| 恢复阶段客户端累计收到的数据 | 186,253,312 B，平均约 18.2 KiB/连接 |
| 恢复阶段结束时进程 RSS | 1,737 MiB |

发送期间进程 RSS 相对发送前增加约 161 MiB，并未随着 2.87 GiB 逻辑提交量线性增长。
这不代表只使用了 161 MiB 的总传输内存：内核套接字缓冲、TLS 层和进程内客户端均未被
单独计量。由于恢复读取未完成，此轮不能用于证明“一万慢用户可以正常消费积压”。

同样负载的第一轮在恢复阶段等待 180 秒，也只有约 18 KiB/连接且 0 条收到探针。
第二轮增加了客户端读完成后的续读，等待 300 秒，结果仍然失败。
另一个诊断实验每秒定时显式请求客户端读取，结果没有改变。
将相同 300 块压缩到约 3 秒内突发发送时，写队列进入背压并替换恢复帧，
10,000 条连接最终都收到最新探针；但中间数据被有意覆盖，不能与本轮完整积压消费等同。
将发送压缩到约 34 秒、保持 4 KiB 缓冲区时，恢复读取仍超时。

这些对照表明“最新恢复帧可达”和“缓慢累积的全部数据能被消费”是两个不同问题。
目前还不能确定恢复停顿发生在 macOS TCP 窗口、TLS/NIO 写缓冲、压测客户端读路径，
或这些因素的组合；强制 4 KiB 套接字缓冲区也是重要实验条件。
64 KiB 缓冲区对照曾启动，但会话中断后终端结果没有保留，不把它当作证据。
测试未接入认证、数据库、持久房间日志或客户端游标补拉，因此也不验证完整业务恢复路径。

## 复现

该容量测试仅在显式设置开关时运行。以下命令预计需约 10 分钟，当前预期会因恢复检查失败而返回非零状态：

```bash
cd IMV2Server
IMV2_RUN_SLOW_FANOUT_BENCHMARK=1 \
IMV2_SLOW_FANOUT_CONNECTIONS=10000 \
IMV2_SLOW_FANOUT_PAUSED=10000 \
IMV2_SLOW_FANOUT_ROUNDS=300 \
IMV2_SLOW_FANOUT_INTERVAL_MS=1000 \
IMV2_SLOW_FANOUT_DRAIN_TIMEOUT_S=300 \
swift test --filter V2GatewaySlowFanoutBenchmarkTests
```

实验夹具位于 `IMV2Server/Tests/IMV2ServerTests/V2GatewaySlowFanoutBenchmarkTests.swift`。
