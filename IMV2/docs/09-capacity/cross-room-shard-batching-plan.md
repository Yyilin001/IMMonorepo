# 普通私聊的同分片跨房间合批方案

**提案：由 Room Actor 决定房间内顺序，由 Room Host 上的分片写调度器把多个已就绪房间合成一个 PostgreSQL 事务。** 第一版最多合 4 条普通私聊消息，额外凑批等待为 0。保留 TCP、同步提交、固定分片、停机改配置和故障自动接管。目标是 5 万在线、3 万活跃房间上限、持续确认 5000 条/秒，实际收益以对照测试为准。

首版实现、逐条 ACK 对账与本机拓扑对照见[2026-11-18 实测结果](cross-room-shard-batching-results-2026-11-18.md)。

## 一条消息如何完成

| 组件 | 职责与边界 |
|---|---|
| Gateway | 沿用现有路由把命令交给当前负责该房间的 Room Host，并把执行结果送回发送方。 |
| Room Actor | 沿用本房间的授权、去重和排序规则，交出已准备好的写入及本轮激活上下文。上一次写入的提交结果在内存应用完毕，再推进本房间下一轮。 |
| 分片写调度器 | 就地复用每个 Room Host 的就绪房间队列和固定写连接。每批限定同一 Host、同一逻辑房间分片、同一目标 database、兼容的普通私聊路径。不同 Host 的批次独立执行。 |
| 房间 PostgreSQL | 在同一事务内推进房间序号，写入消息、幂等完成记录和待投递记录。满足部署要求的持久化提交确认后，才分别返回每条消息自己的 ACK。 |
| 投递与用户分片 | 后台从已提交的待投递记录生成用户侧更新，沿用事件标识做幂等重试。发送方已取得 ACK 后，后台进程重启仍可恢复投递。接收端应用消息的时间单独计量。 |

两个用户可以位于不同用户库。消息写入它所属的房间库，每个批次只有一个事务目标。现有普通私聊 SQL 已有多输入和按房间更新的结构，也已写入待投递与完成记录；主要改动在调度器选取多个房间和事务执行接口。[写调度器](../../../IMV2Server/Sources/IMV2ServerInfrastructure/V2PhysicalSendDispatcher.swift) · [消息追加](../../../IMV2Server/Sources/IMV2ServerInfrastructure/PostgresV2RoomWriteDirectBatchAppend.swift) · [完成与投递记录](../../../IMV2Server/Sources/IMV2ServerInfrastructure/PostgresV2SendCompletion.swift)

## 合批规则与延迟

1. 写连接可以工作时，立即领取最早获得调度资格的就绪房间。如果只有这一间，执行原单房间路径。如果同分片还有其他就绪房间，从现有公平队列顺序取出兼容的房间，各取队首的一轮写入。
2. 第一版跨房间批次最多 4 条消息，另设编码字节上限。先以 64 KiB 作为实验起点，并受现有请求和内存预算约束。一个房间已有多条消息的一轮保持完整；超出合批限制的合法请求走原路径。群聊、媒体和需要额外策略变更的请求沿用原执行方式。
3. 保留每房间、每分片的请求数和字节数上限。按实际消息数和字节计费；热点房间不能把自己的排队成本转成一个批次名额。临近截止时间的请求优先走原路径。每个批次保留请求与结果的对应关系。
4. 合批上限为 1 时直接走旧路径，作为基线和停机回退配置。初次 A/B 固定 4 个写事件循环、16 条写连接，其他连接池和流水线深度沿用对照组。参数 4 和 64 KiB 都是待验证的起点。

零额外等待消除了为凑批而启动的定时器；批首消息仍要等同批事务结束。因此要同时记录单条路径、批首消息和整批的尾延迟。此前高压下实际平均约 1.1 条/批。按 5000 条/秒估算，平均 1.1 条需要约 4545 次追加事务/秒，平均 4 条需要约 1250 次。即使批批装满，第一版在这个基线上减少事务数的倍数也只有约 3.6。消息行、索引和 WAL 仍随消息数增长。

## 事务、接管和重试

**第一版跨房间路径使用一条连接上的显式事务。** 复用现有借用连接及事务门控，跨房间事务独占该连接直到提交或回滚。单条兼容流量继续使用已有快速路径。显式事务增加的往返也计入压测。

1. 每个房间分别携带自己的预期分片、数据归属版本、激活令牌、授权上下文、成员版本和起始序号。整个执行期间持有各自的 Actor 轮次。按稳定的房间 ID 顺序锁行，在同一事务内校验归属和写入前提；维持现有策略与撤权的并发语义。接管必须能隔离旧写入者，数据归属版本与运行时激活令牌分别校验。[现有事务与围栏实现](../../../IMV2Server/Sources/IMV2ServerInfrastructure/Room/Activation/V2RoomActivationTransaction.swift)
2. 用集合 SQL 写入，核对各房间和各命令结果后再提交。当前追加 SQL 在更新房间后，通过关联成功更新的房间插入消息。跨房间时若一个房间条件失效，其他房间仍可能命中；因此检查必须发生在仍可回滚的事务里。
3. 已知整批回滚后，若是个别房间的归属、成员版本或幂等冲突，按房间隔离，健康房间在原截止时间内走单房间路径，失效房间重新路由或返回原有业务错误。数据库整体不可用时按分片退避，避免拆成多个重试请求。已知回滚才可拆批。
4. 已发出提交后连接中断，进入现有结果恢复路径。使用原来的房间、发送者、客户端消息 ID 和请求指纹在权威主库核对完成记录；同键同内容返回原 ACK，同键不同内容返回冲突。只有能排除旧事务继续提交，或由数据库幂等约束安全裁决时才重放。客户端断开后仍完成已提交结果的房间状态更新；Host 崩溃则由接管方从持久状态恢复。

## 多主库部署、停机迁移与回退

沿用现有布局，每个逻辑分片占一个 PostgreSQL database，初期多个 database 共用一个主实例。连接绑定目标 database。部署配置应按主实例汇总各 Room Host 指向其各个 database 的连接额度，计入后台池、管理连接和接管余量。例如两个房间库共享一个主实例，单 Host 各开 8 条就是 16 条；两个 Host 采用同一配置就是 32 条。对照实验固定集群总预算，生产预算再按正常和故障负载分别确定。[数据库拓扑](../../../IMV2Server/Sources/IMV2ServerApp/GatewayDatabaseTopology.swift)

大量独立房间可以随 Host 和主库分散。单个热点房间仍受房间内顺序约束，单独记录最热房间及各分片的写量，按实际写量选择待迁分片。扩容时按下列顺序移动完整房间分片：

1. 准备目标主实例及同步备库，备份控制库和待迁分片；停止接收新写入，让已提交或结果未知的操作完成核对，停止应用和后台写入，排空连接并封写源库。
2. 用现有离线复制脚本搬迁整个 database，校验消息、完成记录、outbox、房间序号、数据库序列和 journal source UUID。保持逻辑分片 ID、用户桶清单和房间归属。
3. 统一更新静态分片地址，保持旧库封写。从原账号读取迁移前历史，重试一个已确认的原消息 ID，验证返回原 ACK；再验证双方继续收发、待投递记录得到处理。
4. 目标库接收新写之前可切回原库；目标库一旦产生新写，则以目标库为最新源，重新停机反向搬迁。应用合批功能可单独停机回退到上限 1。[现有离线迁移手册](../10-operations/user-shard-migration-runbook.md)

整机故障采用独立于计划迁移的自动接管。数据库高可用组件先隔离旧主，再提升包含全部已确认提交的候选库，Room Host 重连当前写入口。三个分散在不同故障域的 Placement 投票节点负责房间归属。为满足失去任一台后仍可同步写入的要求，每个承载权威数据的主实例配置两个跨机候选同步备库，主库和两台备库分置三个故障域，每次提交至少等一个备库刷盘。提升后仍需一个健康同步副本，并为剩余应用节点、控制库和分片库留足容量。若要在故障后维持 5000 条/秒，也要在失去一台机器的状态下重跑容量验收。[PostgreSQL 同步复制](https://www.postgresql.org/docs/16/warm-standby.html#SYNCHRONOUS-REPLICATION)

## 实施顺序与验收

| 阶段 | 交付与通过条件 |
|---|---|
| 1. 单库正确性 | 先实现仅覆盖普通私聊的多房间事务和按请求返回结果。测试同房间顺序、重复提交、同键不同内容、撤权、单房间条件失效、取消、提交前后断线，以及提交后 Host 在返回 ACK 前退出。数据库对账，逐条验证接收端应用无重复。 |
| 2. 调度与本机 A/B | 接入现有公平队列，停机配置上限 1 或 4。同一快照、相同发送序列、128 字节消息、5 万在线、3 万活跃房间上限、同步提交和相同连接预算。分别测 50、1000、3000、5000 条/秒，交替运行新旧配置。记录批大小分布、每千条确认的追加事务数、写连接占用、批首等待和锁等待。低载逐项对比 P99，过载同时看拒绝和积压。 |
| 3. 跨机扩展 | 在独立机器上对比 1 Host＋1 主库、2 Host＋1 主库、2 Host＋2 主库。保持消息与房间分布、发压资源及同步副本策略一致；核验各 Host 和主库实际承担的写量。记录发压端计划与实际调度速率，区分主库分流收益与新增连接带来的收益。 |
| 4. 容量和故障 | 候选档先做 3 轮各 10 分钟，再对最终部署持续 60 分钟，每 5 分钟验收。目标档实际调度、窗口内 ACK/s 均应跟上 5000；建议把允许的窗口计数偏差固定为 0.5%。计划发送至持久化 ACK 的 P99 ≤100 ms，服务端拒绝率和计划未确认率各 ≤0.1%。队列无持续增长，确认消息逐条与库中唯一消息对应；接收端覆盖达标，投递积压能排空。另测突然停掉当前 Room Host、当前主库所在整机和迁移一个有历史的分片，记录恢复用时、故障期间中断、重连后的双向消息及所有故障前 ACK 的完整性。 |

低载长尾与合批并行排查。上一轮在 5 万在线、50 条/秒时，4 和 8 个写循环的后五分钟 P99 分别为 119 和 118 ms。固定 50 条/秒，比较较少在线连接和 5 万在线连接两组，并对慢消息分别记录计划发送、实际提交、Gateway 收包、Actor 就绪、SQL 提交、驱动确认和 ACK 到达的时间；跨机阶段使用关联 ID 和各进程的单调时钟计算本地耗时。即使追加事务数明显下降，只有端到端延迟、错误率、接收端完整性和故障接管均通过后，才把测得的吞吐列为部署容量。
