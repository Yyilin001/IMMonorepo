# 业务节点横向扩展模拟（2026-10-16）

从一个业务节点（Gateway 与 RoomHost 同进程）起步，依次测试 1、2、4 个业务节点。账号服务和三个 Placement 控制进程作为固定基础设施；这不是把整个系统改为单进程部署。

## 资源口径

| 组件 | 固定预算 | 扩容时的变化 |
|---|---|---|
| 每台模拟业务服务器 | 独占一个 Linux vCPU；3 GiB 内存上限总和 | 业务服务器从 1 增至 2、4 台 |
| Gateway／RoomHost | 2816 MiB，8 条消息写连接，数据库／TCP EventLoop 各 1 | 每台保持相同配置 |
| HTTPS 入口 | 256 MiB，与对应 Gateway 共用其唯一 CPU | 随业务服务器增加；不额外借用控制 CPU |
| PostgreSQL | 固定 2 vCPU、4 GiB、512 MiB shared_buffers | 不扩容，单主库，同步持久化不变 |
| 负载发生器 | 固定 4 个分片，共用固定 4 vCPU，每分片上限 1536 MiB | 不随业务节点数增加 |
| 账号与 Placement | 共用其余固定两个 vCPU；单进程 1 GiB 上限 | 账号与投票节点数量固定 |

业务节点固定在 CPU 0…3，PG 在 4…5，负载器在 6…9，控制与运行器在 10…11。CPU 集合限制各角色的总执行资源，避免仅增加进程并让它们任意争用整机 CPU。镜像、四个 Release 二进制、消息池设置及同一份用户夹具在各档复用。

压测器固定源端口为 1024…41023；独立网络命名空间的自动端口范围固定为 42000…47999，业务监听端口从 50000 起，三者不重叠。正式测量前的启动失败不计为吞吐上限。

全部容器仍位于同一台物理 Mac 的 Linux VM 内，共享内核及独立的 loopback 网络命名空间。此测试测量资源受控的业务节点扩展和跨进程 Actor 开销；不包含真实跨服务器 RTT、独立磁盘或物理故障域。数据库仍是共享的固定容量资源。

## 负载与判定

- 固定 10,000 在线用户、10,000 个直聊房间、5,000 个双端前台房间；按节点数均匀接入。
- 先完成真实认证、房间初始化和订阅，再以 200 msg/s、轮转选择发送者预热 60 秒，静置 10 秒。
- 每档正式测量 60 秒，保持原 10 Hz 调度、128 字节消息和每连接四条在途消息。正式阶段使用原加权发送选择；不注入重连或故障。
- 每个吞吐档位使用新建、明确标记的独立数据库；完成事实校验后删除该轮数据库。只有本系列的资源参与清理。
- 消息按原始计划阶段归属，含客户端排队及全部最终 ACK，不能只按窗口内完成的 ACK 计算 P99。
- 合格要求完整 ACK、原质量门槛、全部前台游标与数据库头一致、全部覆盖 Ready、零工作失败、零漏心跳、无强制关闭、进程正常退出。P99 的一毫秒桶上界需不超过 500 ms。
- 先测试共同的 500 msg/s，再上探各节点数的合格档位，最高合格档位另跑一次确认。边界细化至不超过 500 msg/s；未测点不能宣称为精确容量。

扩展比按最高合格的发送档位之比计算，扩展效率为扩展比除以业务节点数。同时保留共同负载下的延迟，以及业务节点、负载器、控制服务和 PG 的实际容器 CPU／内存计数，判断何时瓶颈转移到共享资源。

### 判断与边界

在这套资源预算下，项目可以通过增加业务服务器提高吞吐，但没有线性扩展：两台相对单台提高 25%，四台提高 75%；四倍业务资源换来 1.75 倍合格吞吐。四节点 4,000 档一次通过、一次失败，不能当作可复现容量。

四节点 4,000 档首轮各 Gateway 平均为 0.89–0.97 核，复测中一个节点达到 1.00 核，尽管合计仅约 3.79 核仍出现长尾；合计 CPU 会掩盖单节点热度差异。失败档位的 Gateway 接近各自 CPU 预算，四节点 6,000 档还明确出现 `process_count` 在途发送准入拒绝。PG 平均 CPU 未用满固定两核，当前证据更支持业务节点 CPU 与跨节点额外工作的限制；它不排除数据库短暂等待，也不能替代函数级 CPU 采样。下一轮应对照本地与远程房间调用、实时分发的 CPU 成本，而不是仅增加连接或队列容量。

四节点 4,000 档复测的 P99 为 2,916 ms，虽已启动消息最终全部 ACK，仍有 1,062 个前台游标落后，因此本轮未将其计入可复现容量。降档复测采用同一原始运行器的独立调用副本，仅将上探序列改为四节点配对确认；资源、二进制、场景参数和业务夹具 SQL 摘要不变，变换摘要单独保留。补充系列重新生成了等长随机认证密钥与令牌；用户／设备／房间 ID、关系数据和负载拓扑完全相同，认证在测量前完成，凭据差异也已单独记录。

本轮没有修改生产 Swift 实现。新增的是可复用拓扑参数、按进程容器资源隔离及横向扩展运行器。真实多机还需测跨机 RTT、独立网络和故障域；本轮不覆盖它们。两轮 60 秒复现也不等同于长时间稳定性认证。

原始证据位于本地私有目录 `~/Desktop/IMV2-HorizontalScale-20261016` 的 `series-3` 和 `series-4`：包含最终结果、逐轮质量判断、完整计划阶段 ACK 延迟、服务退出记录、实际容器限额、CPU／内存计数、二进制摘要与源码冻结校验。夹具与凭据不提交仓库。

## CPU 与节点偏斜定位（2026-10-16）

补充三组诊断，资源、四个 Release 二进制摘要及原始运行器保持一致；每组在正式阶段第 15 秒起采 20 秒、99 Hz 的 Linux `perf cpu-clock` 栈。样本是实际运行中 CPU，包含用户态与内核态，不是等待栈。帧指针采集跨不过所有异步挂起边界；函数栈占比包含下层调用并会重叠，不能与叶节点分类相加。匹配 Build ID 的 libc 调试符号仅用于离线符号化，没有更换运行库。诊断有采样开销，全部排除在前面的容量结论之外。

### 已对应到代码的成本

1. 房间远程调用仍经过 PB 报文、认证包和 DistributedCluster 调用生命周期；本地房间路径省去远程报文。额外 RPC 的构建与回收会增加 ARC、分配及任务工作，而不只增加网络等待。
2. `HotDeliveryReceipts.model → HotActivation.model → V2Identifier.init → UUID.init → sscanf` 在真实栈中可见；UUID 转换／标识规范化相关栈约占单节点 7.72%、四节点 6.80%。相对占比降低并不代表绝对 CPU 下降，因为四节点总 CPU 更高。该占比是含下层调用的估计，不能承诺全部可回收。
3. `V2RealtimeClusterSender.sendRoomSubscriptionBatch` 在调用分布式 endpoint 前无条件执行 `session.mac.seal`，收到回执后 `open` 并重建回执模型；同进程回调也会走这段认证报文路径。房间调用的本地优化并未覆盖全部实时回调。
4. `V2RoomClusterPeer.boundedDispatch` 为实际调用与截止时间分别创建任务，并登记／结算请求；本地缓存命中也经过这里。采样支持关注这类生命周期成本，但取消、截止时间和实际调用清理职责仍需保留，不能直接删除任务。

### 为什么最忙节点会换位置

发现压测控制变量缺口：`prepare_v2_room_actor_configuration.py:103` 每轮为逻辑 Gateway 随机生成 Host ID；`initialSnapshot` 对 Host ID 排序后把 256 个分区轮转分配。连接与 persona 分片仍固定接入 Gateway，因此每轮房间到物理 Gateway 的映射会变化。之前“同配置复测”应限定为资源与主要参数相同，不代表完整冻结了房间归属拓扑。

| 分区序号模 4 | 首轮 4,000：归属／Owner 写入每秒 | 复测 4,000：归属／Owner 写入每秒 |
|---|---|---|
| 0 | Gateway 0／1066 | Gateway 1／1042 |
| 1 | Gateway 1／1089 | Gateway 3／1064 |
| 2 | Gateway 3／906 | Gateway 0／891 |
| 3 | Gateway 2／946 | Gateway 2／927 |

计数窗口均位于正式阶段，采样起止略有差异，表为近似速率。同一个最忙分区组从 Gateway 1 移到 Gateway 3，Owner 写入份额随之转移。房间分区平均分配不能保证按消息热度或 CPU 成本均衡。

在失败复测中，Gateway 3 Owner 写入约 1,064/s，Gateway 0 约 891/s，后端执行工作相差约 19%；接入连接数则均为 2,500。Gateway 3 平均单核已满，其他节点的空闲 CPU 无法直接接手它持有的执行状态。

`V2NIOGatewayChannelHandler.scopedNotificationWriter` 在请求 processing、待处理入站帧、待写响应或前台帧队列未清时拒绝这次通知入队；这与 TCP 缓冲区不可写不同。`consumeRoomSubscriptionHeads` 会保留最新水位并休眠 100 ms 再试。已确认存在响应与通知的调度耦合，以及热点节点更多暂缓；没有发现立即空转的重试循环。固定 100 ms 重试与 10 Hz 压测突发可能形成重试放大，但其净 CPU 占比尚未通过干预对照验证。

### 判断及下一步

现有证据支持优先处理：固定压测逻辑 Host ID／分区映射，保留每次启动的新 incarnation；然后分别对照减少不必要的认证报文模型重建和标识转换、已授权同进程回调使用内存模型、通知依赖通道状态变化唤醒而非固定间隔重试。房间归属优化需同时考虑实际热度和接入节点关系，不能只按房间数平均。以上是可验证的优化方向，并非本轮已实施的生产改动。

本次四节点 4,000 诊断轮 P99 为 145 ms，没有复现前次 2,916 ms 长尾；不能声称已经抓到失败现场的全部函数级根因，也不能用这轮重写容量结论。已找到随机拓扑这一可观测干扰项，及业务负载与响应／通知耦合，后续需冻结拓扑做针对性干预对照。

本轮未修改生产 Swift 源码。原始 perf.data、符号化栈、逐节点 CPU／工作量、Host ID 排序到 Gateway 的映射及校验记录保存在 `~/Desktop/IMV2-HorizontalScale-CPU-20261016`。

## 固定拓扑及本地通知、UUID 优化对照

**本轮有小幅 CPU 收益，但 4,000 msg/s 优化后复测失败，不能认定为稳定容量。** 本节是固定档位对照，不重新计算最高容量或扩展效率。

### 改动与复现边界

1. 本地部署生成器新增 `--identity-seed`，使用角色和节点名派生逻辑 Host／voter ID。横向扩展运行器默认使用 `cc50ac35-0881-4366-9502-08f8bb6c118a`；每轮密钥和进程 incarnation 仍独立生成。原始部署生成器不传此参数时仍生成新逻辑身份。此参数只服务于新的独立测试部署，不能用来重置已有集群。
2. 每轮记录初始 256 分区的 Host 分配及摘要；新增 `--case NODES:MSG_PER_SECOND` 执行指定对照点，此模式不输出容量扩展率。新旧组及优化后复测的逻辑身份、初始分配均核对相同。
3. 实时订阅批次在目标完整描述符与本进程绑定描述符相同时，直接传递已验证领域模型；移除本地 PB／MAC 往返与分布式 Endpoint 跳转。仍检查来源权限、分片、批次、回执，保留并发准入、关闭与调用排空；远程调用仍走原有鉴权协议。不是对所有本地 RPC 的全面重写。
4. `V2Identifier` 对标准 36 字节 UUID 直接解析 ASCII 并缓存 16 字节 UUID；规范文本直接复用，只有小写输入才生成大写副本。从 UUID 构造文本改为固定格式写入，避开 Linux Foundation 的格式扫描／格式化。其他合法不透明 ID 保留原语义。

继续使用本报告的每节点 1 核／3 GiB、8 条消息写连接、数据库／TCP EventLoop 各 1，以及固定 PG、4 个负载器和 10,000 在线。各档预热 60 秒、静置 10 秒、正式 60 秒。四个负载分片在所有版本中始终使用同一个旧版二进制，避免客户端的 Core 变化干扰服务端对照。基线四个二进制的哈希与之前 CPU 采样完全一致；新旧完整哈希、命令、容器资源及分配摘要保存在原始证据中。

### 失败复测暴露的剩余问题

两轮新版的二进制、资源、分区分配相同；最忙 Gateway 的正式采样 CPU 由约 0.957 核升到 0.990 核。失败轮未观察到 `socketNotWritable` 增量，但 Gateway-2 的 `socketResponseBusy` 约 127→878 次／秒：通知因前台响应仍在处理而推迟，不能解释成 TCP 缓冲已满。

Gateway-2 的房间队列采样均值约 14.37→59.48 ms，`policy_owner_state` 约 0.014→43.52 ms，内存探测仍约 0.019 ms。该外层阶段包含初次探测、未命中加载及条件性的陌生人策略读取，不能把两者差值全部当成 Actor 调度。失败轮 Gateway-2／3 分别记录 501／1,015 次初次权限缓存探测未命中，通过轮对应增量为零。缓存读取可因条目不存在或所绑定控制会话不再有效而未命中，缓存也有容量淘汰路径；现有计数没有区分这些原因，尚未确认冷加载与节点接近满载的因果顺序。

细分阶段和通知频率来自正式窗口内可用指标采样的首尾差值；失败轮 Gateway-2 的有效区间约 28.5 秒，并非完整 60 秒均值。正式 ACK 延迟表来自完整消息 cohort。现有均值不能完整解释 5 秒 P99。下一步应首先区分权限缓存未命中的原因及发生时刻，关联控制会话推进、冷加载和前台响应占用，再决定是否调整调度或控制通道隔离。

Linux 小基准每轮构造 500,000 个大小写混合 UUID 标识并消费其文本与 UUID，四轮交替顺序：旧实现中位约 352.88 ms，新实现约 48.06 ms，约快 7.34 倍。这只是标识构造微基准，不代表整条消息链路加速倍数。
