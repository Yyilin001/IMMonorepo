## 阶段 2 双 Gateway 验证

用一个 Gateway/Core、一个仅接入 Gateway 和一套 PostgreSQL 16 主库运行 Release 二进制。两端各维持 50 个连接，每个私聊房间的两位参与者分居两个 Gateway。`--single-core --nodes 2 --kind candidate --allow-small-canary` 场景以合计 12 条/秒为目标运行 10 秒。

两个 Gateway 各发送 59 条，118 条全部收到持久化 ACK。100 个前台视图的游标均追平 PostgreSQL 提交水位，历史拉取返回记录数为 0，实时序号缺口为 0。Core 指标报告 256 个实时发布分区，接入 Gateway 为 0。连接与工作负载失败均为 0，服务正常排空退出。

故障测试中，Core 先于接入 Gateway 独立就绪。接入 Gateway 在发压期间暂停 6 秒并被强制终止。主库消息数在暂停前、暂停末和终止后分别为 62、182、320，320 条均收到持久化 ACK，Core 写入代次和进程标记一致。原接入 Gateway 的 50 个客户端先连到存活 Gateway，再连到重启后的接入 Gateway，两次均从零补齐 320 条房间记录，全部前台房间游标与主库水位一致。首次重连同时校验了账号已应用游标，第二次重连校验了账号 Ready 状态。

## 阶段 3 吞吐对照

冻结版与单活版均用一个 Gateway、一套 PostgreSQL 主库和同一份 50,000 用户快照。六个发压分区分别以 60 连接/秒、每批 8 个爬坡，认证后以 `--loader-workload-ramp-per-second 96` 预热房间。两轮各使用 16 条消息写连接、4 个写事件循环，主库开启 `fsync` 和 `synchronous_commit`。使用同一份 Release 发压器和发送计划，待 50,000 个连接都完成房间预热后才开始发送。

本机监听端口移出发压源端口范围，已知占用端口写入同一份排除列表。若快照后又出现本机端口占用，发压器在认证爬坡时使用范围内的新端口，最多重试 4 次。占用首个源端口的实测中，101 次套接字尝试获得 100 个已认证连接，119 条消息全部获 ACK，所有前台视图均追平。正式对照仍要求全量在线、完整发送窗口、完整排空及收件覆盖。3,000 档沿用既有短测门槛，调度和窗口 ACK 速率在目标的 ±0.5% 内，计划发送到持久化 ACK 的 P99 ≤100 ms。

## 阶段 4 停机与同库重启验收

连接注销批量清理在线租约，并撤去尚未提交的续租。TERM 后停止接纳新续租与实时覆盖任务，已提交的操作保留连接归属，等待物理数据库连接或调用结束。投递和账户维护任务使用有截止时间的物理数据库连接借用。

按阶段 3 的 50,000 用户快照、同一 Release 发压器、同一发送计划和 TCP 主库连接复验。3,000 档确认 180,000／180,000 条消息，达到 2,999.50 ACK/s，计划发送到持久化 ACK 的 P99 落在 68–69 ms 桶内。全程 244,488 条消息获得持久化 ACK，50,000 个前台视图全部追平主库。

发压进程排空后给 Core 发 TERM。连接、后台任务、注册表和房间完成排空，Core 以状态码 0 退出，代次 1 的 `incarnation` 已清空，在线租约表为零。同一 PostgreSQL 主库保留 244,488 条消息，房间序号之和同为 244,488。重启取得代次 2 和新实例标记，TLS 和 256 个实时发布分区恢复就绪。再次 TERM 后代次 2 的 `incarnation` 清空，进程状态码为 0。验收使用的 Gateway Release 摘要为 `f5b6ea4eefed095954db4c6b9845c7601ad6efb34bfe2bddfb4d3bac2f6a3162`。

仓库的本地账户启动和验证脚本已改用单活 Room Core。分片验证脚本显式选用 Placement 拓扑。单活默认使用独立的 PostgreSQL 卷。

全量复验中 Account 的邀请创建恢复任务仍有一次停机超时。补齐该任务的物理数据库连接期限后，单独对领取邀请任务的 SQL 注入无回包故障。修复前 TERM 在 30.173 秒后以状态码 1 退出，修复后在 0.022 秒内关闭借用连接并以状态码 0 退出。默认 Compose 拓扑配置解析通过，本机 Release 进程也通过 PostgreSQL 空库启动、Core 同库重启以及 Account 和 Operator 的停机检查。

## 独立 Core 与双 Gateway 复测

运行环境需要 Docker Compose、与 Docker 主机架构一致的三个 Linux Release 可执行文件（IMV2ServerApp、IMV2AccountServerApp、IMV2GatewayLoadGenerator）、包含相应 Swift 运行时和 Python 的本地镜像 `improject-facade-ci-tools:latest`，以及加入 PATH 的 PostgreSQL 客户端工具。以下命令在仓库根目录运行。`IMV2_RELEASE_BIN` 指向三个可执行文件所在的目录，`RUN_ROOT` 指向本次测试专用目录。

```bash
mkdir -p "$RUN_ROOT"
python3 IMV2/scripts/prepare_v2_actor_realtime_direct_fixture.py \
  --output-dir "$RUN_ROOT/fixture" --seed 73cce983-8198-4eae-9c25-f2af4c487a72 \
  --users 50000 --foreground-paired
python3 IMV2/scripts/run_v2_separate_core_benchmark.py \
  --output-dir "$RUN_ROOT/result" --fixture "$RUN_ROOT/fixture" \
  --runtime "$IMV2_RELEASE_BIN" --context colima-improject-facade-ci \
  --rates 500 750 1000 --core-write-connections 12
```

脚本创建独立的 Compose 项目、数据库和网络。第一个发压进程通过 HAProxy 接入 Gateway 0。已有认证连接后，脚本将扩展后的配置原子替换到原节点目录，启动 Gateway 1，并核对扩容前后的 Core 写入代次与实例标记。两个 Gateway 各有 25,000 个连接、全部订阅完成且稳定 30 秒后，6 个发压进程开始计量。每个目标速率持续 60 秒。报告合并各发压进程从计划发送到持久化 ACK 的直方图，并在排空后将前台视图游标与主库房间序号逐一核对。输出目录含测试凭据，使用独立的私有目录。运行结束后容器停止，保留本轮数据库卷和报告。

部署新增 Gateway 时，先让原节点能通过内部 DNS 解析新增节点的地址。向 `prepare_v2_room_actor_configuration.py --single-core --extend-from` 提供当前私有部署目录，用 `--output-dir` 指定新的空路径，并列出原节点和新增 Gateway。既有 Core 与 Gateway 继续挂载各自的节点目录，在目录内原子替换各自的 `configuration.json`。进程定期读取本地配置，仅接纳新增 Gateway 的端点、公钥和权限范围。新节点挂载生成的专属目录。将业务流量引到新节点前，在 Core 和 Gateway 的指标中确认 `im_v2_actor_realtime_reachable_nodes` 已覆盖扩容后的节点数。下一次扩容从本次生成的完整私有部署目录继续。原 Core 的房间归属与 PostgreSQL 写入权贯穿整个扩容过程。

### 2026-11-22 发送长尾定位

在 1,534 ms 的历史窗口中，六个客户端共发起 61,005 次提交，收到 1,009 次 `DEFERRED_admissionUnavailable` 和 59,996 次最终确认。共有 1,015 条消息的端到端耗时达到 1 秒。相同拓扑下 153 ms 的历史窗口只有 59,996 次提交，没有延后响应。压测客户端收到无重试提示的延后响应时，首次重发等待 1 秒，再叠加最多 500 ms 的随机退避。历史数据保留了客户端事件，服务端各拒绝原因的累计计数当时没有归档。

继续使用相同的 Release 工作负载、六个发压进程、每秒十次调度及 500 → 750 → 1,000 条/秒的阶梯。原实现复验的 1,000 档 P99 为 143 ms，零重发。946 个关联样本中，房间排队和等待数据库写执行器的 P99 分别为 59.97 ms 和 44.79 ms。单活 Core 采集房间指标时仍在遍历全部房间并重复检查共享资格，该窗口的单次扫描最长约 83 ms。

在相同的 PostgreSQL 2 GiB 容器中，将共享缓冲区从 128 MiB 调为 512 MiB，并为 WAL 整页镜像启用 LZ4。保持 fsync、full_page_writes 和同步提交开启。只改变这两项的对照轮中，1,000 档 P99 为 106 ms，零重发。约 59.5 秒的采样区间内，`pg_stat_bgwriter.buffers_backend` 的增量由 505,494 页降至 33,758 页，WAL 由 801 MiB 降至 559 MiB。共用一个写入权的单活 Core 现按资格代次维护就绪房间数，指标读取时直接检查当前资格。分区所有权独立变化的部署仍逐房间验证。

运行上述基准时追加 `--trace-sends` 可生成 `send-stages.json`。每阶段按操作 UUID 关联 Gateway、Room RPC 和房间执行记录，保留匹配数和剔除数。Gateway 本地耗时扣除其 RPC 往返，Core 本地耗时扣除有埋点的 SQL 往返，数据库客户端耗时合并同一操作的底层 SQL Future 区间。各段分位数独立计算。端到端验收使用六份客户端全量直方图，并核对实际发包次数、延后响应、同步重试和主库游标。

数据库采样中可见插入和更新执行器初始化 CHECK 表达式。PostgreSQL 16 在第一次为当前结果关系执行约束检查时反序列化约束表达式，批内后续行可以复用。把多条就绪消息放进一个事务和一条集合追加语句，能够摊薄这类固定开销。批量对照还改变了每次提交涵盖的消息数，仅凭该实验无法分别量化 WAL 刷盘、协议往返与约束初始化的贡献。[PostgreSQL 16 执行器 ExecRelCheck](https://github.com/postgres/postgres/blob/REL_16_STABLE/src/backend/executor/execMain.c) [PostgreSQL 16 扩展查询协议](https://www.postgresql.org/docs/16/protocol-flow.html)

在本节的复现命令中，把目标速率设为 `--rates 5000`，加上 `--trace-sends --core-write-connections 8`。放宽配额使用 `--core-cpus 6 --gateway-cpus 4 --postgres-cpus 5 --ingress-cpus 2`，合批使用 `--core-cross-room-limit 4`。Docker 宿主核数、数据库卷位置、Release 二进制以及采样开关须另行记录。

在 4 房间合批下，新旧二进制的 8 写连接对照各跑一次，窗口实际 ACK/s 相差 6.6%。新版本将房间待写轮数改为增减计数，提前计算可重放结果和策略作用域，复用消息的 UUID 键和已准备的持久化回执。两轮同时包含这些改动，不能给单项改动分配收益。候选版再改为 12 写连接后，窗口实际 ACK/s 仅增加 2.1%。三个窗口分别收到 225,776、126,544 和 100,421 次发送端 SERVER_BUSY。

在 12 写连接、4 权限连接轮次，两台 Gateway 在测量窗口的首末采样之间分别记录了 183,170 和 183,216 次 `message_credit_wait_timeout`。这是 Gateway 向 Core 提交 RPC 时等待连接额度超时的次数，一条逻辑消息可能有多次尝试。发送端记录的 SERVER_BUSY、Gateway 内部拒绝和传输层超时属于同一链路的不同计数，直接相加会重复计数。

在同轮 Core 采样时，已有 16,571 次权限快照借用完成。限流队列累计等待 704,280 ms，平均 42.5 ms，最长 243.75 ms。获得额度后等待驱动平均 0.76 ms，持有连接期间的 SQL 阶段平均 3.55 ms。同轮主库两次内部快照相隔 59.02 秒，15,931 次权限快照 SQL 的平均执行时间为 0.046 ms。两边的统计区间和计时边界有差别，Core 的 SQL Future 包含排队和获得连接的时间。相应的成功链路中，权限准备 P99 为 326.83 ms。[PostgreSQL 16 pg_stat_statements 指标](https://www.postgresql.org/docs/16/pgstatstatements.html)

保持 12 个写连接和每批 4 条消息，只将 Core 专用权限池从 4 调至 16 个连接，仍共用一个非消息数据库 EventLoop。窗口内确认 129,106 条，折合 2,151.72 ACK/s。该档最终确认 152,240 条，发送 P99 ≥ 10 秒，45,103 个游标追平。抓取的权限池计数显示，15,813 次借用平均排队 55.4 ms，持有连接期间 SQL 平均 13.83 ms。该配置的一次过载运行同时出现重试放大，无法把性能回落唯一归因于连接数。

这一轮还暴露了单独的停机失败。两个 Gateway 停止后，Core 收到 TERM，完成连接注册表排空并进入房间投递排空。165 秒后容器被强制终止，退出码 137，Docker 记录 OOMKilled 为 false。主库仍保留代次 1 的写入标记，同库重启验收失败。本组 4 权限连接的五轮均在 TERM 后清除写入标记，同库重启取得代次 2 并恢复 256 个实时分区。扩大权限连接的配置仅用作诊断。

用 12 个写连接、4 个权限连接将合批上限从 4 改为 16。测量窗内两次快照之间确认了 6,217 个十六房间事务。窗口实际 3,279.04 ACK/s，196,745 次窗口内 ACK，该档最终确认 219,483 条，P99 ≥ 10 秒。恢复后 32,935 个游标追平。403 条可完整关联的成功发送中，等待写执行器 P99 为 37.43 ms，权限准备 P99 为 425.99 ms。与 4 条合批的实测相比，写执行器排队缩短，端到端吞吐下降。此上限用于有界实验，部署默认仍是 1。该轮 TERM 后清除写入标记，同库重启取得代次 2。

### 5,000 档冷权限读取与房间补拉

将通过原 4 vCPU 验收的 Release（`0b88603b40b0`）放回 14 vCPU 模拟拓扑，两个 Gateway 各维持 25,000 个连接。沿用 12 个写连接、4 个权限连接、每批 4 条、每条 Room RPC 连接 512 额度。场景文件 SHA-256 前缀为 `6942c731df96`。每轮都从相同夹具建新主库。

这轮窗口内持久化确认 299,951 / 300,000（4,999.15 ACK/s），本档的 300,000 条最终全部确认。发送 P50/P95/P99 为 74/246/1,420 ms，传输层提交 306,950 次，发送延后 6,950 次。50,000 个前台游标追平，发送最终失败、同步失败、同步重试均为零，同库重启通过。

* 升档初期约 8 秒的抓取区间中，有 7,916 次权限连接排队结束，平均耗时 62.07 ms。7,777 次已结束的权限 SQL 平均 2.51 ms。随后两个区间连接平均排队降至 3.73 和 1.88 ms。
* Core 的 `im_v2_room_recovery_batch_busy_before_acquire_total{purpose="pure_pull"}` 增加 3,723，两个 Gateway 分别记录 1,752、1,971 次 `group_event_pull` 的 SERVER_BUSY，客户端也记录了 3,723 次可重试拒绝。这些拒绝发生在 Core 收集房间补拉请求、检查保留项或字节额度时。后三十秒附近的抓取区间占 3,427 次。

另行测试了一个冷权限读取合批候选版（`7fd0313a2b08`）。候选版收集正在等待权限池额度的独立请求，按各自的顺序、权限状态、取消和截止时间返回结果。四项 PostgreSQL 与 TCP 回归测试通过。[DataLoader 批处理契约](https://github.com/graphql/dataloader#batch-function) 和 [PostgreSQL 16 事务快照](https://www.postgresql.org/docs/16/transaction-iso.html)说明了批量读取的结果顺序与可见性。

#### 跨房间写入往返与提交后投递

以 `0b88603b40b0` 为对照，单独测试将锁定并检查房间写入者的 SELECT 合入消息追加语句（候选 `f5384e5f27db`）。显式事务仍在完整核对消息、游标、事件和回执数量后提交。该候选按房间 UUID 排序取锁，等待并发写入时由 PostgreSQL 重新检查该行。[PostgreSQL 16 行锁](https://www.postgresql.org/docs/16/explicit-locking.html#LOCKING-ROWS) 与 [READ COMMITTED](https://www.postgresql.org/docs/16/transaction-iso.html#XACT-READ-COMMITTED)

14 vCPU 模拟拓扑和施压节奏与对照相同。中、后两个采样区间中，跨房间执行均值从 13.32 / 13.95 ms 降至 11.99 / 13.19 ms。60 秒内确认 299,999 / 300,000 条（4,999.96 ACK/s），1 条发送延后重试耗尽，15,091 次发送延后，4,609 次房间补拉可重试拒绝。确认消息的 P50/P95/P99 为 76/392/1,583 ms。50,000 个游标追平已提交房间头，Core 两次 TERM、同库重启和全部分区恢复通过。此候选保留为独立实验。

该实现通过 PostgreSQL 上 10 个跨房间提交用例，含并发变更写入者、游标过期、部分约束失败以及 COMMIT 结果未知后的回执恢复。并发用例在另一事务实际阻塞于房间行锁后才提交写入者变更。通过 `pg_locks` 和 `pg_blocking_pids()` 确认等待，避免在长事务中反复读到先前的活动统计快照。[PostgreSQL 16 统计快照](https://www.postgresql.org/docs/16/monitoring-stats.html#MONITORING-STATS-VIEWS) 与 [pg_locks](https://www.postgresql.org/docs/16/view-pg-locks.html)

原 4 vCPU 的 1,000 档独立确认记录了零房间补拉。14 vCPU 的 5,000 档对照窗口发出 15,016 个房间补拉请求，收到 179,661 条记录。在随后的恢复窗口，另有 69,852 个请求和 344,188 条记录。约第 30–58 秒内，166 个已结束的补拉批次平均耗时 138.20 ms。数据库连接的 SQL 区间平均 17.35 ms（393 段），两次 SQL 之间等应用继续执行的区间平均 23.06 ms（558 段）。各计数对应各自完成的区间，不能按单条请求直接相加。

另用带分段计数和计时的基线定位提交后投递。Core 的 `V2RoomSubscriptionHost` 只有一个消费任务，每轮先处理已取出的投递通知，再逐房间等待提交记录或数据库修复读。约升档第 7.3 秒，单轮取出 6,474 个房间，约 61.4 秒后才进入下一轮。期间到达的新投递通知要等这一轮结束。后半段（约第 30–58 秒）落在区间内的完整计数桶里，4,355 次提交因物理所有者的 4,096 条正文额度已满而退化为水位，另有 114,123 次提交到达时该房间已处于待修复状态。单房间处理均值从初期 1.22 ms 升至 17.13 ms。该诊断版窗口内为 4,388.79 ACK/s，18,161 个游标落后，计时和日志开销均在测量中。上述结果用于定位阻塞，同配置关闭探针的候选 Release 另行验收。

在同一 14 vCPU 拓扑另测固定数量的房间消费任务，按房间分配任务，在相邻两次房间处理之间处理新投递通知。候选 Release `fd69ccf697ee` 关闭了上述诊断探针。全程房间补拉请求从对照组的 92,488 次降至 34,799 次，直接应用的在线正文从 16,611 条增至 24,082 条。但 60 秒内仅确认 239,613 条，实际 3,993.50 ACK/s。本档计划的 300,000 条最终确认 257,454 条，已确认消息的 P99 落入 10,000 ms 以上的溢出桶。升档初期的权限数据库连接排队均值从 62.07 ms 升至 135.07 ms。测量窗口共记录 477,943 次发送延后及 100,293 次服务端繁忙拒绝，均按尝试计数。50,000 个游标最终匹配主库已提交的房间头，停机重启检查通过。该实验未通过吞吐与发送门槛，交付版本仍为 `0b88603b40b0`。

#### 8 条合批与冷权限路径

在 14 vCPU、双 Gateway 各 25,000 连接的拓扑中，以同一份 `0b88603b40b0` Release 单独将跨房间提交上限从 4 改为 8。两个阶段快照间，等写执行器的平均时间在中段从 12.64 ms 降至 3.54 ms，在后段从 15.30 ms 降至 3.12 ms。后段完成了 11,884 个八房间事务。同期单个合批执行的平均时间从 13.95 ms 增至 15.95 ms。

60 秒内确认 299,808 条，实际 4,996.75 ACK/s。计划发送的 300,000 条最终确认 299,818 条，181 条发送失败，1 条队列溢出。已确认消息的 P50/P95/P99 为 71/2,029/4,125 ms。前两个区间的消息 RPC 额度等待超时分别为 30,714 和 33,803 次，后段只有 59 次。首段权限连接排队均值为 125.32 ms，四条合批时为 62.07 ms。窗口共记录 65,017 次发送延后、零房间补拉可重试拒绝。全部游标都追平实际提交头，Core 停启恢复 256 个分区。该结果将后半段写排队同升档初期的权限和 RPC 等待区分开来。

保留八条提交上限，换用之前独立测过的冷权限合批版 `7fd0313a2b08`。首段完成的物理权限 SQL 从 9,161 次降至 1,327 次，等待权限连接的均值从 125.32 ms 降至 0.05 ms。第 30–58 秒的区间中，消息 RPC 等待额度超时升至 121,588 次。整档出现 133,939 次延后和 10,381 次房间补拉可重试拒绝。窗口内确认 290,954 条，实际 4,849.17 ACK/s。已确认消息的 P50/P95/P99 为 125/3,252/5,908 ms，最终 298,845 条获 ACK，8,523 个游标仍落后。

#### 权限快照的任务调度耗时

复核早期 14 vCPU、12 写连接、4 权限连接、每批 4 条、每条 RPC 连接 256 额度的开启追踪轮次。在正式窗口内选出 3,500 条命中权限快照内存缓存的 Room 执行记录，每条都包含一套完整的任务生命周期标记。对每条记录分别计算创建独立任务到开始执行、加载返回到清理完成、清理完成到原等待者恢复的三个间隔，再对三个间隔之和取分位数，P50/P95/P99 为 **8.77/21.66/27.51 ms**。任务开始执行到加载返回的 P50/P95/P99 为 0.02/0.19/4.90 ms。不同记录可能属于同一逻辑消息的不同尝试，测得的时间包含调度等待与追踪开销。

`PostgresV2RoomPolicyAuthorization.preparationSnapshot` 为每次读取创建一个独立任务，热缓存命中也经过任务创建和等待者恢复。普通异步调用可在现有任务中挂起、恢复。写事务在完成 COMMIT 前仍须持有执行权，关闭房间时须等实际读写全部结束。独立验证这两条生命周期，是改变读路径任务所有权的前提。[Swift 结构化并发](https://github.com/swiftlang/swift-evolution/blob/main/proposals/0304-structured-concurrency.md)

候选 `d71ac5c03aca` 在调用任务内读取权限快照，持久化写入仍有独立任务，停机等待进行中的读取和写入全部退出。回到 1 GB WAL，沿用原发压器、12 写连接和 4 条合批。两台 Gateway 各 25,000 个连接，所有订阅稳定 33.38 秒后发压。5,000 档窗口内持久化确认 292,094 条，实际 4,868.22 ACK/s。发送 P50/P95/P99 为 646/5,345/8,772 ms，7,838 条发送失败，68 条队列溢出，18,434 个前台游标落后。同步失败和房间补拉拒绝为零。Core 两次清除标记，同库从代次 1 升到 2，恢复 256 个分区，13 个容器均正常退出。10 项 Linux 与真实 PostgreSQL 测试通过，包含两个关闭调用同时等待冷读与写事务。该实现仍未达到端到端门槛，仅用于对照。

同一批跟踪中有 262 条冷读取能关联到一次本地权限 SQL。一次本地读取走了两层快照缓存，先经过节点缓存，再进入同一进程的权威权限目录缓存。逐条计算外层开始读取到进入权威目录之前、权威目录返回到外层读取完成之后的时间之和，P50/P95/P99 为 **16.38/121.04/223.36 ms**。完整冷读的 P50/P95/P99 为 159.42/326.47/437.74 ms。统计包含队列调度和发布结果的时间，只覆盖这批诊断样本，移除外层后可节省的端到端时间须另行实测。设计上可在启动时验证权限分区全部归本 Core，直接使用现有权威目录，权限变更、失效和持久化校验仍沿用同一套实现。[Swift Actor 隔离与任务调度](https://github.com/swiftlang/swift-evolution/blob/main/proposals/0306-actors.md)

#### 单独增加 PostgreSQL WAL 空间

用同一份 `0b88603b40b0` Release、原发压器和原 5,000 档场景，仅将主库 `max_wal_size` 从 1 GB 增至 4 GB。启动后查询确认 4 GB 生效，`fsync`、`full_page_writes`、`synchronous_commit` 均开启。原 1 GB 对照在升档后第 26 和 53 秒启动检查点。4 GB 轮有一次时间触发的检查点在升档前约 45 秒开始，整个 60 秒窗口中没有新的检查点启动。[PostgreSQL 16 检查点与 WAL](https://www.postgresql.org/docs/16/wal-configuration.html)

60 秒内确认 167,801 条，实际 **2,796.61 ACK/s**。计划的 300,000 条最终确认 191,774 条，已确认消息 P99 达到直方图上界（≥10 秒）。窗口内有 317,018 次发送延后和 491,989 次发送繁忙拒绝，两者均按尝试计数。5 万个连接保持在线，最终所有游标匹配主库实际提交的房间头。窗口内新增检查点次数下降未消除过载，单轮也无法判定增大 WAL 空间导致了性能回落。

这轮 Core 在 TERM 后 165 秒仍未退出，退出码 137，代次 1 的写入标记保留。同一停机期间的两次抓取中，未完成房间命令均为 0，活跃房间从 25,063 降至 23,724，已完成空闲回收从 1,073 升至 2,412，两次都有 8 个房间正在回收。该计数反映房间回收在继续，具体阻塞组件还需由停机阶段日志确认。保留原数据库卷供检查。

#### 按计划发送时刻核对首次提交与重试

在原服务端 Release 上，只给发压器的每五秒计划队列增加「一次线上提交获 ACK」和「多次提交后获 ACK」直方图，Core 开启 notice 停机日志。各桶按消息原计划时刻分组；合并六个发压器的两类桶后，逐毫秒计数与原端到端直方图完全一致。

本轮 Core 收到 TERM 后约 9 ms 已经过连接注册表排空并进入房间投递排空。房间投递阶段持续 **138.53 秒**。Core 随后正常清除写入标记，同库重启取得代次 2，恢复 256 个分区，第二次 TERM 后标记为空。该阶段在过载后可以接近整个进程的 165 秒停机预算。12 秒的用户态 CPU 采样仅得到 37 个样本，尚不能确定是哪个异步等待消耗了大部分墙钟时间。

#### 从提交到 Gateway 首次确认通知的排队

在 Swift 6 的受控复现中，直接编译生产 `V2RoomSubscriptionHost` 的消费循环，使用模拟房间读取和投递接收端。让两个待处理房间进入同一批，固定暂停第二个读取 250 ms。第一个房间完成读取并产生通知后，原实现三次都等到第二个读取释放才通知投递泵。实验改为在该房间处理完成后取出它已登记的投递通知，重新核对激活代次再通知投递泵，三次都在第二个读取释放前发出。两版在释放后都完成了两个房间的通知。这项复现确认了跨房间等待的执行顺序。

真实负载按同一 Core 的单调时钟关联提交、取出待处理房间、消费连续前缀、首次发送水位和收到 Gateway 回执。采样选择固定 UUID 尾缀的房间。水位可以覆盖多条已提交消息，匹配点取首次覆盖该序号的事件。另按 Gateway 和投递序号关联唯一发送和精确回执。该回执只证明 Gateway 接受了投递，客户端最终是否应用仍逐游标核对。分别报告已观测耗时和截止时仍缺失的阶段。[AWS 对异步队列首次投递年龄的测量](https://aws.amazon.com/builders-library/avoiding-insurmountable-queue-backlogs/)

#### 权限缓存命中时省去独立任务的对照

候选 Core（`4b439186aeb3`）在普通私聊的当前房间激活中同步读取权威权限缓存。缓存缺失或需要陌生人权限时，继续执行原来的异步读取。命中也需要校验账户、关系、调用截止时间和参与者身份。55 项 Linux 测试在真实 PostgreSQL 环境中通过，覆盖缓存失效、拉黑、陌生人回退和激活关闭。这个改动针对的是采样看到的调度等待。Swift 的 `Task.detached` 会创建一个独立任务。[Swift SE-0304](https://github.com/swiftlang/swift-evolution/blob/main/proposals/0304-structured-concurrency.md#detached-tasks)

真实 PostgreSQL 上的 9 组共 53 项 Linux 测试通过。跨房间提交覆盖 15 个场景，包括并发写入权变更、单房间游标失效、被触发器跳过的投递或回执，以及提交后丢失 ACK 的幂等恢复。另有用例验证有界消息头、连续序号和授权水位。通过回归后把该 Release 的权限预热、分组提交、提交后释放写连接及有界消息头实现纳入本地工作树。主库使用包含 `im_v2.complete_room_append` 约束域的新库引导脚本。已逐文件核对 947 个服务端源码输入和 542 个 Swift 测试输入与验证快照一致。1,000 档的三个服务端进程均使用新 Release。上述 5,000 档的对照只替换了 Core，双 Gateway 仍使用原发压基线中的服务端程序。

#### 同一节拍内的成对发送

六个发压进程共用场景种子 `20260828`，按连接顺序轮流分配夹具。第 0/1、2/3、4/5 个进程各自成对，每对进程连接数相同、抽样顺序相同，同位置用户的第一个目标房间相同。客户端在可用性提示模式下向这个前台房间发送。按原场景的权重洗牌、随机取样、每档余数和同步拉取消耗的随机数重放 60 秒发送计划，30 万次发送全部有同一节拍的同房间发送。按每个 100 ms 节拍内的房间计，共有 144,745 次安排 2 条、2,557 次安排 4 条、47 次安排 6 条。不同进程的调度和网络延迟会影响它们到达 Core 的实际间隔。

诊断 Core `5bd500141553` 只记录抽样房间的请求类型、房间内执行次序和单调时钟耗时。5,000 档内有 3,926 条发送样本，其中 1,906 条入队时已有同房间发送在执行。排队至少 20 ms 的 1,317 条全部遇到前一轮发送，其中 1,316 条至少 90% 的排队时间与前一轮重叠。排队至少 50 ms 的 34 条全部在等入队时已在执行的同一轮发送，前一轮结束后至分发的 P99 为 0.07 ms。在靠近满载的首末两次 Core 抓取之间，共准入 289,998 条发送，只有 8,371 条在包含多条同房间命令的轮次执行，占 2.89%。这解释了该场景中一部分慢发送的房间等待。整轮 300,000 条在窗口内确认，发送 P99 为 132 ms，有 162 次发送延后和 849 次可重试补拉拒绝，最终发送和同步零失败，50,000 个游标追平。两次 TERM 释放写入标记，同库重启进入代次 2 并恢复 256 个分区。

工作树版本按已有队列中的相邻发送合批。候选对照使用同一发送计划，单独启用 Core 现有的 2 ms 房间收集窗口，验证同房间批量提交对端到端延迟、补拉拒绝和提交轮数的影响。数据库持久化参数沿用对照轮。

#### 房间收集窗口对照

在相同双 Gateway 配额、场景和数据库设置下，实验 Release `26afe4b97805` 对单活 Room Core 启用 2 ms 收集窗口。窗口内只确认 213,155 / 300,000 条，实际 3,552.56 ACK/s。最终确认 235,420 条，已确认发送的 P99 落入 ≥10 秒桶，54,911 次发送失败、683 次同步失败。第一个抓取区间 6.51% 的命令参与同房间合批，最后一个区间降至 1.91%。满载后段等写执行器的均值升至 32.82 ms，消息 RPC 额度超时和发送重试随之增加。最终 50,000 个游标追平实际提交头，Core 在两次 TERM 后均清除标记，同库重启取得代次 2 并恢复 256 个分区。当前工作树继续按已在队列中的相邻发送合批。

#### 单台独立接入 Gateway 承载 50,000 个客户端

单独生成一个 Room Core、一个接入 Gateway 和 Account 的身份配置。HAProxy 只有一个后端，六个原发压进程的前台房间与发送计划逐字节相同。Gateway 和 Core 均运行 `ed7fd4494c3e`，Core 与 PostgreSQL 的配额和持久化配置同上。Gateway 合并原接入层配额，使用 8 vCPU / 6 GiB、4 个 TCP 事件循环、4 条同步连接，连接上限 60,000，限流身份预算 120,000。HAProxy 为同一上游监听端口预留充足的临时源端口，仍以 64,000 为连接上限。首轮配置预检发现限流身份预算低于连接上限两倍，Gateway 在接受流量前拒绝启动。更正后从独立新库完成以下测量。

单个 Gateway 与 HAProxy 同时观察到 50,000 个已建立连接，全部前台订阅就绪并稳定 31.15 秒。5,000 条/秒窗口内确认 227,093 / 300,000 条，实测 3,784.85 ACK/s。1,024 个进程级发送在途额度下，最终确认 248,657 条，已确认发送的 P50/P95/P99 为 1,588/8,039/9,955 ms。客户端记录 46,632 次发送失败，另有 564,235 次可重试发送繁忙拒绝、1,088 次队列溢出，同步最终失败和漏心跳均为零。50,000 个游标均匹配实际提交头。Core 正常排空，并在同一主库取得下一代写入权和全部 256 个分区。

约第 48 秒的 Gateway 抓取显示在途发送 1,024 / 1,024，因进程请求数上限被拒累计 385,568 次。连接级和字节预算的拒绝计数均为 0。满载窗口 59 秒内，Gateway 平均使用 3.23 核，CPU 节流时间为零，两次内存采样最高 4.18 GiB。双 Gateway 对照中，同一进程级上限各为 1,024。两处在最后一个满载快照观察到的生涯峰值为 590 和 575，进程请求数上限拒绝均为 0。单节点已经验证连接承载量，该窗口的消息吞吐和发送长尾未通过验收。

在新库上只把 Gateway 的 `IM_V2_MESSAGE_SEND_MAX_IN_FLIGHT_PROCESS` 从 1,024 调到 2,048，与原双 Gateway 的总额度对齐。逐项核对场景、主库持久化设置、运行中角色与二进制挂载，以及 Gateway 和 Core 的数值配置。全部前台订阅就绪后，单个 Gateway 持有 50,000 个连接，稳定 31.24 秒。窗口确认 152,717 / 300,000 条，实际 2,545.25 ACK/s。最终确认 167,415 条，已确认发送 P99 ≥10 秒，101,981 次发送失败、5,425 次队列溢出。同期同步最终失败和漏心跳均为零，游标全部追平实际提交头，Core 的两次 TERM 和同库重启均通过。发压失败的消息未计入提交头。

新上限仍在窗口中被用满。约第 58 秒，Gateway 累计因进程在途请求数上限拒绝 763,870 次。约 59 秒采样期 Gateway 平均使用 3.37 核、CPU 节流时间为零。把同时驻留的请求数翻倍没有改善本轮吞吐。该参数仅作对照，单 Gateway 的 5,000 档仍未达到延迟与失败率目标。10 万在线单 Gateway 的业务容量仍需单独验证。
