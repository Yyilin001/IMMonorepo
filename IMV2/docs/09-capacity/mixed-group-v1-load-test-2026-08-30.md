# 混合群聊 V1 容量测试（2026-08-30）

## 结论

本轮在 1,000 个 TLS 长连接上同时施加标准群 fanout、万人混合群写入和
标准群 Sync 拉取。所有实际发出的 7,943 条消息最终都收到 ACK，数据库也
形成了精确对应的 7,943 个 terminal fanout plan；185,760 条标准群 delivery
全部 terminal，没有遗留 outstanding plan、delivery 或 admission unit。

> 复现说明：本轮标准群测的是**逐用户投递**形态，因此复现时必须显式设置
> `IM_V2_GROUP_DELIVERY_AUTHORITY_MODE=fanout`（负载画像已固定该值）。标准群的部署
> 默认此后改为 `room_log`，读模型下的容量数字需要另跑一轮，不能与本轮直接比较。

但是，这一档不能作为稳定容量：15 秒稳定段计划发送 8,039 条消息，客户端
有界队列溢出 96 条；阶段结束时仍有 487 条在本地队列、4,255 条已发送但尚未
收到 ACK，最长需要 23.952 秒才能排空。PostgreSQL 在 61 秒活跃窗口内峰值
CPU 达 734.66%（8 核），而数据盘峰值利用率仅 18.6%。主瓶颈是数据库事务、
fanout 写放大和 Sync 竞争，不是云盘吞吐，也不是 Gateway 前台 admission。

## 拓扑与夹具

- Gateway：4 vCPU / 8 GiB，单实例。
- PostgreSQL：8 vCPU / 16 GiB，单实例、单库。
- Load Generator：4 vCPU / 8 GiB，与 Gateway 使用云内网连接。
- 在线连接：1,000；五个压测进程使用互不重叠的 user/device。
- 标准群：20、200、1,000、5,000 人各一个。
- 混合群：10 个互相独立的 10,000 人 `large_group_hybrid` 群，分散到四个
  room shard；700 个在线账号平均分配到十个群。
- 消息：128 bytes。
- 标准群连接启用 Sync；混合群容量腿不启用 Room Log 拉取，读侧另跑 canary。

测试夹具只保存用户和房间关系，不在 PostgreSQL 中保存 access token。临时
凭证按不重叠区间生成，传输到压测机前校验 SHA-256。

## 负载模型

所有进程同时运行 15 秒稳定段。使用 100 Hz 场景调度器和每连接最多四条的
有界客户端队列；停止调度后，最多等待 60 秒排空在途请求，再保持连接五秒
才关闭。该流程避免固定时长模式在服务端仍返回 ACK 时提前断开连接。

| 负载腿 | 连接 | 目标消息/s | 逻辑 fanout delivery/s |
|---|---:|---:|---:|
| 标准群 20 | 20 | 20 | 400 |
| 标准群 200 | 80 | 10 | 2,000 |
| 标准群 1,000 | 100 | 5 | 5,000 |
| 标准群 5,000 | 100 | 1 | 5,000 |
| 10 × 万人混合群 | 700 | 500 | 0（Room Log 模式） |
| 合计 | 1,000 | 536 | 12,400 |

## 客户端结果

下表“阶段 ACK”只统计 15 秒稳定段内返回的 ACK；“最终 ACK”包含明确的 drain，
因此可以区分稳定吞吐与最终一致性。

| 负载腿 | 计划 | 阶段发送 | 阶段 ACK | 队列末值 | 溢出 | 最终 ACK | 阶段消息 P95 | drain |
|---|---:|---:|---:|---:|---:|---:|---:|---:|
| 标准群 20 | 300 | 289 | 189 | 9 | 2 | 298 | 4,321 ms | 23,952 ms |
| 标准群 200 | 149 | 149 | 110 | 0 | 0 | 149 | 3,175 ms | 6,238 ms |
| 标准群 1,000 | 75 | 75 | 69 | 0 | 0 | 75 | 2,054 ms | 3,291 ms |
| 标准群 5,000 | 15 | 15 | 13 | 0 | 0 | 15 | 1,916 ms | 2,271 ms |
| 10 × 万人混合群 | 7,500 | 6,928 | 2,820 | 478 | 94 | 7,406 | 9,376 ms | 16,647 ms |
| 合计 | 8,039 | 7,456 | 3,201 | 487 | 96 | 7,943 | — | 最长 23,952 ms |

所有实际发送的消息都在 drain 内收到 ACK，`send_message` 没有失败或拒绝；
96 条溢出属于客户端明确记录的未发送需求，不能算作服务端成功。

## 数据库闭环

- 7,943 条消息对应 7,943 个新增 terminal plan。
- 四个标准群分别接受 298、149、75、15 条消息。
- delivery 数量精确为：`298×20 + 149×200 + 75×1000 + 15×5000
  = 185,760`，全部 terminal。
- 十个万人群分别接受 700–777 条消息，合计 7,406，分布没有集中到单房间。
- 所有测试房间的 `outstanding_fanout_units` 和 `outstanding_plans` 都回到零。
- 峰值 open plan 为 266，峰值 ready delivery backlog 为 103,159。

## 资源与放大

| 指标 | 观测值 | 判断 |
|---|---:|---|
| PostgreSQL CPU 峰值 | 734.66% / 8 核 | 接近 CPU 上限 |
| Gateway CPU 峰值 | 304.68% / 4 核 | 高，但仍有约一核余量 |
| PostgreSQL 数据盘写入峰值 | 25.54 MiB/s | 不是带宽瓶颈 |
| PostgreSQL 数据盘写 await 峰值 | 0.5 ms | 延迟健康 |
| PostgreSQL 数据盘利用率峰值 | 18.6% | 不是 I/O 上限 |
| 主机最小可用内存 | 10.65 GiB | 内存充足，无 swap 压力 |
| WAL 平均速率（活跃窗口） | 10.94 MiB/s | 写放大明显，但未打满磁盘 |
| 事务提交速率（活跃窗口） | 806.69/s | 数据库 CPU 饱和期间的闭环速率 |
| Gateway foreground queue 峰值 | 0 | 前台 admission 不是瓶颈 |
| Gateway Sync queue 峰值 | 254 | fanout 与 Sync 发生资源竞争 |
| Sync 排队平均等待 | 约 144 ms | 尾延迟来源之一 |

61 秒数据库活跃窗口产生约 700 MiB WAL、733,743 次 tuple insert 和
571,114 次 tuple update。15 秒标准群负载制造的 185,760 条 delivery 需要在
稳定段结束后继续处理，因此 12,400 delivery/s 是提供速率，不是可持续完成
速率。

## Room Log 读侧 canary

同一夹具另行执行了 50,000 人混合群的 100 连接、50 msg/s canary：391 条
消息 ACK，消息 P95 4,273 ms，Room Log pull P95 2,796 ms，心跳 P95
3,722 ms；收到 10,453 个 availability hint，触发 2,905 次 pull，获得
25,985 条事件。该结果说明热群读放大和 pull 合并仍需单独优化，不能用本轮
写入腿的成功率代替读侧容量结论。

## 下一档建议

下一轮先定位稳定点，不继续提高当前档位：将标准群逻辑 fanout 提供速率降到
约 4,200 delivery/s，同时将十个万人群合计消息速率降到 200 msg/s。保持相同
连接、群分布、15 秒阶段和严格 drain 判定。通过条件应同时满足：

1. 场景队列零溢出，阶段末排队不超过 64 且没有材料级 in-flight 积压；
2. 消息 P95 小于 1 秒、P99 小于 2 秒；
3. fanout backlog 在阶段内不持续单调增长，停止负载后十秒内归零；
4. PostgreSQL CPU 持续值低于 650%，Sync queue 不持续超过 64；
5. 所有实际发送消息、plan、delivery 和 admission 计数闭环一致。

稳定点确认后，再分别提高混合群消息速率和标准群 delivery 速率；不要同时提高，
否则无法判断是房间 sequence、消息持久化还是 fanout 投影先饱和。
