# 两个 Room Host、一个 PostgreSQL 主库的远程发送对照

2026-11-18，本机 Apple M4 Pro，14 核、48 GiB，原生 Release Gateway / Room Host 及 Release TCP 发压器，PostgreSQL 16.13。两个 Gateway 分别与一个 Room Host 同进程运行。客户端只选接入网关，发送仍按房间 ID 经现有路由找到房间。

在 3000 条/秒档，引入跨节点调用后，发送端先耗尽了 RPC 连接上的在途调用名额。过载又触发房间引用失效和重复查找。100% 远程时，仅保留过载房间的引用就把窗口确认从 1899 提高到 2992 条/秒，该档 P99 仍为 204 毫秒。

## 测量条件

每轮从同一份房间和账号快照恢复，配置两个逻辑用户分片库和两个逻辑房间分片库，全部在同一 PostgreSQL 主库。消息数据库走 TCP，逐库检查同步提交与 fsync 开启。每 Host 4 个数据库写事件循环，每个房间库 4 条写连接，集群合计 16 条。写流水线深度 2，跨房间合并上限 4，集群活跃房间上限 3 万。采用本地主库持久化，无备库。

每个 Gateway 接入 2.5 万个不同账号，每个 Host 负责 7000 个参与发送的私聊房间。另有 3.6 万个已登录空闲连接。用 Placement 检查工具读取已提交的房间归属，按归属选择接入 Gateway，使 0%、50% 或 100% 的目标负载需要跨节点。8 组客户端的账号、房间与随机种子在四轮中相同，房间归属在每轮前后均核对。业务请求不携带 Host ID。

每轮等待 5 万连接完成认证后统一放行，发送 128 字节消息。先以 500 条/秒预热 16 秒，再跑 1000 条/秒 45 秒、空载 12 秒、3000 条/秒 45 秒、空载 25 秒、5000 条/秒 60 秒，最后排空 45 秒。合计内存按所观察进程足迹加 4 GiB 预留估算，达到 30 GiB 就中止。该值是保护阈值，macOS 和其他进程共享机器资源。

基线完整运行日志中，0% 组未记录房间发送传输错误。50% 组的 overloaded、unknown_actor、outcome_unknown、deadline_exceeded 分别为 28924、1234、167、61 次，包含排空。100% 组记录的 105766 次全部为 overloaded。50% 组在 5000 档的远程 dispatch 具体有 8608 次 overloaded、59 次 deadline_exceeded、24 次 outcome_unknown，另有 11 次远程已认证响应返回 outcome_unknown。

两台 Host 间每个方向按目标端点和流量类型复用 RPC 连接，每条连接初始 256 个在途调用名额。请求发出后消耗一个名额，接收方完成执行并回复后才归还。等待提交、回程或事件循环期间仍然占用名额。多个房间共用这条连接。此次拒绝计数按检查顺序记录首因，调用额度耗尽时不会再检查剩余字节。

远程发送抛出原始传输错误时，当前实现会移除对应的缓存房间引用。后续发送可能再做物理查找或恢复。第四轮只在隔离副本中对有缓存引用的发送跳过 overloaded 引起的移除，保持传输额度、协议、其他错误处理和客户端程序相同。

## 瓶颈定位

100% 远程的两轮在 3000 档都保持 5 万在线。跳过过载引起的引用移除后，物理查找从 18587 降到 3654 次，发送因 overloaded 出错从 20974 降到 135 次，窗口 ACK/s 提高约 58%。在 5000 档，实验组确认 735 条/秒，期间出现 321245 次远程发送 overloaded，重试仍会反复撞上连接额度。每种条件只有一次短测，1000 档两轮均无过载驱逐，其 P99 差异也体现了单轮波动。

在 3000 档，50% 组进入阶段约 9 秒后开始记录远程 overloaded，100% 组约 13 秒后开始，两个窗口均无 PostgreSQL 的锁、语句或空闲事务超时日志。0%、50%、100% 三组中，房间写队列头部到提交的平均时间约为 49、281、63 毫秒。该时间包含等待，无法分摊为 PostgreSQL、Swift 调度或主机 I/O 各自的耗时。

同在 5000 档，0% 组也只确认 2398 条/秒，房间写队列头部至提交平均约 477 毫秒。50% 组同时出现数据库锁、语句及空闲事务超时，最低在线跌至 49188，服务端监控首末样本只覆盖约 9 秒。100% 组在整个目标阶段保持 5 万在线。50% 与 100% 的过载结果未随远程比例单调变化，5000 档也承接了上一档的重试。

## 数据库对账

按房间、发送账号和客户端消息 ID，把每个 ACK 的消息 ID 与房内序号同时对照数据库消息和永久完成记录。下表的数据库新增数扣除快照内的 16 条种子消息。

| 远程负载 | 窗口及排空合计 ACK | ACK 不匹配 | 数据库新增 | 原账本失败但已提交 | 修正后未知且已提交 | 活跃连接整轮覆盖就绪 / 14000 |
|---|---:|---:|---:|---:|---:|---:|
| 0% | 350,504 | 0 | 350,504 | 0 | 0 | 3,630 |
| 50% | 141,719 | 0 | 142,856 | 50 | 1,137 | 0 |
| 100% | 191,434 | 0 | 191,434 | 0 | 0 | 3,389 |
| 100% 保留引用 | 238,394 | 0 | 238,394 | 0 | 0 | 3,667 |

四轮使用同一份已冻结的发压器。原程序在计划重新提交时耗尽重试预算，会将操作登记为失败，此时已有尝试可能已经提交。修正后的发压器将这类操作记录为结果未知。对每个活跃客户端分别核对唯一的旧失败原因与账本行数，再仅重分类对应记录，并在各轮原数据库重新逐条校验。两次审计的数字均保留在 CSV。
