# Actor 实时路由本地压测

当前 Gateway 使用房间 Actor 独立排序、内存权限判断和房间独立事务。实例归属由三个原生多数派控制节点确认；正常转移等待实际排空，崩溃接管由 Supervisor 排除旧进程并收尾数据库会话。房间不使用 SQL 实例租约或逐房间续租。部署与故障验收见 [Room Host 监督部署](room-host-supervision.md)。

## 构建与夹具

使用同一 Swift 工具链构建最新 Release。Runner 不自动构建，并在启动前核对负载器的协议与算法摘要。二进制路径应来自对应构建的 `swift build --show-bin-path`。

消息延迟以 `messageSendCohorts` 的原始计划阶段归属为准。计划时间随客户端排队、重试及重连保留；阶段结束后的 ACK 仍计回原阶段。`measurementLatency` 的消息两项只有在十二份报告的该阶段全部已发送消息均获得 ACK、直方图计数一致时才返回分位数，缺失或未完成时返回 null。原 ACK 完成窗口分布单独列为 `measurementWindowLatency`，不能用它替代完整消息集合的 P99。心跳等其他操作仍按观测窗口统计。该调整只改变测量记录，不改变速率、10 Hz 调度、发送窗口或重试策略。

```sh
cd IMV2Server
swift build -c release --product IMV2ServerApp
swift build -c release --product IMV2AccountServerApp
swift build -c release --product IMV2PlacementControlApp
swift build -c release --product IMV2GatewayLoadGenerator
cd ..

python3 IMV2/scripts/prepare_v2_actor_realtime_direct_fixture.py \
  --output-dir /tmp/imv2-direct-ring-fixture \
  --seed 4a5a8a27-cb40-5627-a0b9-3bcfb21ebec1 \
  --foreground-paired

python3 IMV2/scripts/run_v2_actor_realtime_benchmark.py \
  --kind candidate \
  --fixture /tmp/imv2-direct-ring-fixture \
  --output-dir /tmp/imv2-direct-ring-current \
  --candidate-binary /path/to/release/IMV2ServerApp \
  --candidate-account-binary /path/to/release/IMV2AccountServerApp \
  --candidate-placement-binary /path/to/release/IMV2PlacementControlApp \
  --loader-binary /path/to/release/IMV2GatewayLoadGenerator
```

夹具默认有 50,000 个账号、设备和直聊房间。用户 i 与 i+1 是房间 i 的成员，每个连接保留两个目标、一个前台详情订阅。`--foreground-paired` 使相邻双端共享第一目标，形成 25,000 个双端前台房间。不要将全部房间数量解释为同时具有双端订阅的房间数。

若要运行 10,000 在线诊断，生成夹具时添加 `--users 10000`，运行时指定对应 `--scenario`、`--allow-scaled-diagnostic` 和 `--measurement-phase`。包含发送预热的场景必须明确指定测量阶段；连接订阅预热不等于房间发送状态与权限已经预热。

正式默认场景为 `high-active-50000-uuid-ab-5000.json`。缩放诊断保留完整质量检查，但不等于正式容量验收。历史版本对照可使用 `--kind both` 和三个 `--baseline-*` 参数；旧 wire45 适配只属于测量工具，生产端严格使用当前协议。

## 纯在线诊断

使用 `--online-only --allow-scaled-diagnostic --measurement-phase online-idle`，场景选择
`IMV2/load-scenarios/online-only-idle.json`。该模式只登录、保持 TCP 连接和正常心跳；不创建聊天房间、不建立前台房间订阅、不发送消息、不主动补拉、不注入重连。全部负载分片到达共同屏障后，观察 180 秒。

前台数据库池采用弹性续期预算：空闲续期名额可以借给认证与接纳，续期排队后优先取得归还的连接；不会增加物理连接上限或提前回收执行中的连接。新连接接纳保留用户、设备锁及全局连接数限制，事务正文只有锁查询和合并接纳查询两次往返。认证、接纳、续期的借用观测分别标记为 `authentication`、`presence_admission`、`presence_renewal`，避免用通用来源推断具体业务耗时。在线投影续期使用每连接一项的可更新到期堆，撤销时删除该项，临近到期工作合并在最多 10 ms 的调度窗口内；TCP 心跳不会等待该投影写入。

启用数据库工作池隔离时，消息写入、前台认证／控制、后台工作分别拥有独立的数据库 EventLoopGroup。前台组线程数仍取非消息数据库线程配置，各池连接预算保持原值；后台借用队列的超时处理不再占用认证连接所属的 EventLoop。主机资源采样同时记录网络缓冲分配拒绝计数和文件句柄使用量，不能把这两类系统资源耗尽误判为 SQL 执行慢。

纯在线观测完成后，负载器先在全部连接上停止新心跳，等待已经发出的心跳得到 ACK，再开始分批断开；等待沿用心跳原始期限，拒绝、超时或断连仍记录为漏心跳并使验收失败。每个场景阶段单独记录心跳发送、确认、漏心跳计数，整体报告也保留完整生命周期计数，验收条件不会因主动退出而放宽。

该模式使用独立的在线质量判定：达到目标连接数、完整共同观察窗口、零接入／业务失败、零心跳漏应答，并由负载器报告确认没有房间或消息工作。它不要求消息 ACK 或前台消息追平，不作为消息吞吐验收。启动前额外等待六个 Actor 服务资格就绪；服务退出与停机排空仍单独记录。夹具生成工具允许最多 100,000 个测试账号，每个负载分片仍受原有 10,000 连接上限约束。固定源端口范围与本机其他监听器冲突时，可用 `--loader-excluded-local-ports` 指定需要跳过的端口；不停止其他应用，也不放宽失败质量标准。

`--loader-local-port-base` 可修改两个固定源端口段的起点（各 10,000 个端口），默认整体为 25000–44999；旧连接元组检查和证据中的端口范围使用同一配置。所选范围应避开系统自动端口范围及本轮服务监听端口，不能直接将 macOS 的选择套到 Linux。Linux 通过 `/proc/net/tcp` 与 `tcp6` 检查实际元组，macOS 使用系统 netstat；两者均不修改系统端口设置。

## 服务与资源配置

本地 runner 默认将 Account、控制状态、用户分片和房间消息存储汇聚到同一个临时 PostgreSQL 实例及数据库；工作连接池与 EventLoop 隔离不等于物理分库。生产装配支持不同存储地址，不能把这个合并部署的结果直接解释为独立数据库实例的容量。

`--pg-shared-buffers-mib` 仅允许为本轮自有 PostgreSQL 显式设置共享缓存，不修改既有共享实例；省略时保留 initdb 默认值。`postgres-settings.json` 记录实际共享缓存、自动计算的 WAL 缓存、连接上限及持久性参数。缓存变化可能同时改变自动 WAL 缓存大小，对照报告必须披露。活动采样按具体等待事件和固定 SQL 类别分组，不输出查询正文；`LWLock` 采样计数不能直接当成等待时长。

`--pg-track-wal-io-timing` 为自有测试实例开启 WAL 写入和同步计时，不改变提交持久性；该轮用于诊断，不能据此单独宣称无计时开销下的容量。未开启时，`pg_stat_wal` 的写入及同步时间为零，不代表实际 I/O 没有耗时。同步方法及计时开关随生效配置一起记录。

`--pg-wal-sync-method` 可对照 `fdatasync` 与 `open_datasync`，仅作用于本轮自有实例，默认不覆盖平台选择。两者均保持同步提交；`open_datasync` 的写入自身包含同步，因此应查看 `wal_write_time`，不能把 `wal_sync_time=0` 解释为没有持久化成本。

Runner 启动 6 个 Gateway/RoomHost、1 个 Account、3 个归属控制节点和 12 个负载分片。全部请求连接就绪后，Driver 释放共同场景屏障。连接与订阅预热、发送预热、测量、排空分别记录。

| 参数 | 当前默认值 |
|---|---:|
| TCP EventLoop／Gateway | NIO 检测到的 CPU 核心数 |
| 消息数据库 EventLoop／Gateway | 4 |
| 消息写连接／Gateway | 8 |
| 独立权限控制连接／Gateway | 4 |
| 前台读／控制工作池连接 | 4 |
| 同步／投递／投影／维护连接 | 1／1／2／1 |
| 非消息工作池 EventLoop | 1 |
| 临时 PostgreSQL 最大连接数 | 320 |

消息写连接总量由 `--candidate-message-write-connections` 指定，通过 `--candidate-event-loop-threads` 在配置的 EventLoop 间平均分配，两者必须整除。消息写入使用实际写连接调度，不经过通用前台写准入。读、同步与后台任务使用隔离连接预算；数据库 CPU、WAL 和磁盘仍是共享资源。运行时实际配置和拓扑证据优先于历史报告中的连接数量。

### 账号与房间初始化的资源边界

TCP 线程预算可通过 `IM_V2_TCP_EVENT_LOOP_THREADS` 显式设置，压测对应 `--candidate-tcp-event-loop-threads`；省略时保留 NIO 原默认值。该预算独立于消息数据库 EventLoop、写连接和每连接发送窗口，同机多 Gateway 的总线程预算应合并评估。减少线程是否改善提交与调度延迟必须通过同流量对照确认，不能预先作为优化结论。

账号初始化及成员关系刷新共用节点内有界调度器。队列保存任务数据，只为正在执行的步骤创建 Task；一页处理完毕即让出执行槽。相同账号的变化合并，取消和关闭等待实际步骤结束后才释放槽位。临时错误保留已读取页面和已安装进度，通过共享截止时间堆延迟重试，不创建逐账号休眠任务。

实时分区控制请求的容量只在传输发送器管理：总并发四个、同一目标节点两个，最多等待 256 个请求；忙节点不阻挡其他可执行节点。等待不占 RPC 名额，取消、截止时间、引用退役和关闭会移除对应等待者；已分配的名额保留到本地调用实际返回。协调器不再另建控制准入队列。`im_v2_actor_realtime_control_queued` 及 `control_queue_seconds_sum/count` 记录实际容量等待，拒绝原因区分 `queueFull` 和 `queueTimeout`；远端过载及未知结果仍遵守原有恢复边界。重复房间激活在重新核对权限快照后，复用同一授权围栏、Pump、Relay、目标描述及分片的现有绑定，避免将正在发送的绑定误判为过载；退役、关闭或新围栏不能复用旧绑定。这些结构修复的容量收益仍须完整场景验证。

Gateway 的传输控制包装器先按 PB body 选择处理器：只有设备进度、房间订阅和在线发布控制进入连接注册表，普通消息与同步直接委托业务处理器。消息发送、发送结果恢复及心跳使用独立的会话异步路径；认证、协商和请求关联在共享同步入口校验，响应编码与请求关联释放由共享同步出口完成，复杂页面与作者展示的临时状态不再占据这些高频请求的挂起上下文。此处不改变权限、消息提交或恢复协议。分配采样只说明记录窗口中的新增分配和未归还字节，不能把采样结束时仍保留的任务上下文直接称为泄漏，也不能用有采样器的吞吐作为容量验收。

进程发送准入同时限制报文字节和在途请求数量：`IM_V2_MESSAGE_SEND_MAX_IN_FLIGHT_PROCESS` 默认 1,024，独立于单连接窗口和 64 MiB 报文预算。数量名额在创建业务 Task 前申请，与字节预算一起保留到业务及响应写入实际结束；取消请求不会提前归还仍被实际工作持有的名额。上限保护小报文对应的异步上下文与 RPC 状态，不在 Gateway 增加等待队列；超出沿用 `SERVER_BUSY`。指标 `im_v2_gateway_message_send_maximum_in_flight_requests` 公布配置上限，`process_count` 与 `process_bytes` 分别统计数量和字节拒绝。该边界不等同于数据库并发，也不证明目标吞吐已经达成，仍需原负载与原质量门槛验证。

目录首次加载使用独立初始化池，`IM_V2_DATABASE_INITIALIZATION_CONNECTIONS_PER_EVENT_LOOP` 默认四条连接，计入每个物理数据库的总连接预算。相同物理库的拓扑、成员、房间和路由在一条 SQL 的同一快照中读取；跨物理库仍保留必要的拓扑一致性检查。空页也返回权威拓扑代次。连接借用采用按类别的索引 FIFO 和截止时间堆，取消删除定位到具体等待者，不扫描整个等待数组。每个池仅维护一个截止时间定时器。

房间 activation 恢复及发送状态的必要冷加载也显式使用所属物理数据库的初始化池，不再借用前台读／控制池的 activation 子额度；复用已有初始化连接预算，不增加连接池。恢复的一条 SELECT 同时读取房间、私聊状态及成员信息，依靠单语句快照，不再发送 BEGIN、事务内超时配置和 COMMIT。物理借用看门狗继续负责绝对期限、取消和实际查询收尾，Host 在安装前后仍验证原生 activation 生命周期。此改动减少初始化往返，不代表已经证明十万在线／5000 档容量。

生产装配的 Gateway 与 Policy Owner 权限事实缓存，统一按 `max(32768, maximumActiveRooms × 5)` 设置有限保留预算；远端接收者的权限订阅及待推送更新使用同一上限。私聊的五项来自双方账号、关系及双方陌生人设置。该预算随房间驻留能力增长，避免固定 32,768 项在大规模场景下反复淘汰活跃事实；群聊发送者或归属倾斜仍可能触发 LRU。预算不预分配全部存储，也不改变权限版本推进、控制会话失效或首次读取规则。`im_v2_policy_memory_events_total` 分别统计 `node_snapshot_eviction`、`owner_snapshot_eviction` 和 `snapshot_release_reset`，不能只凭冷加载次数认定容量不足。权限 Publisher 与释放队列的可变字典由所属 Actor 独占，异步调用只携带已形成的不可变请求，避免修改一个订阅时复制整个订阅表。

## 质量检查与故障边界

有效结果要求报告完整、测量窗口达到要求、连接覆盖证明通过、没有业务失败或队列溢出／遗弃、在途请求完成排空，以及全部前台视图追平已提交水位。吞吐使用测量阶段实际 ACK 和实际时长，不能使用配置速率或预热、排空阶段的 ACK 冒充。

消息提交后丢失 ACK 时，客户端按同一消息身份查询或重试，通过成功记录确认结果。数据库存在消息不等于客户端已经确认成功；恢复与实时投递需要分别检查。

本工具保留小规模通知丢弃、Actor 通道分区和 App 验收入口，其范围以 `--help` 和对应验证脚本为准。旧的直接 SIGKILL 后依靠自然 TTL 重启入口已经移除。原生 Host 崩溃接管由 `test_v2_native_host_crash.py` 验证，它覆盖 Supervisor、旧容器排除、数据库会话收尾和未知发送结果恢复。

## 按实际阶段定位热点

Analyzer 使用全部分片实际阶段的交集窗口，披露计数器边界偏移、缺样和重启。客户端 P50/P95/P99 属于各分片，不能直接平均成全局分位数。CPU 使用窗口内相邻采样计算，不能把预热峰值当成测量资源占用。

发送指标由 `V2SendOperationStage` 定义，已移除没有实际生产调用的旧授权路由、回执预检、证明写入和房间租约 SQL 来源标签。阶段输出在途、开始、完成、耗时总量和生命周期最大值。均值使用 `Δ耗时总量 / Δ完成数`；阶段调用可能处理整批消息或以错误结束，完成数不是消息成功数。

优先核对以下边界：

- `room_queue_wait`：房间轮次排队。
- `owner_ready_wait`：准备完成到数据库执行调度获准。
- `owner_connection_acquire`：实际连接借用。
- `owner_ticket_task_wait`：执行任务开始前的调度等待。
- `owner_single_statement`：单语句隐式事务完整周期。
- `owner_write_future`／`owner_write_resume`：SQL Future 等待与 Swift 恢复。
- `owner_pool_return_to_resource_release`：归还连接到调度资源释放。

完整周期与子阶段存在嵌套，不能相加当作客户端延迟。复杂消息仍可能使用显式事务及回退路径，BEGIN／正文／COMMIT 应按实际调用计数解释。SQL 来源中的 `*FenceRooms` 表示持久化数据归属校验，不是已移除的房间实例租约。

写调度诊断将等待拆分为实际连接全部借出、归还待处理、任务／分配／回调待运行和槽位可用等区间。采样只说明该请求的观测边界，不能单凭平均值判定锁竞争或运行时调度是唯一原因。

`capture_gateway_perf_when_busy.sh` 使用 `IM_V2_GATEWAY_OWNER_QUEUED_TURNS_THRESHOLD` 和 `im_v2_send_operation_owner_queued_turns` 触发采样，单位是等待调度的房间轮次。历史性能证据保存在 `docs/reviews`；历史 Collector、额度 tail、逐房间租约及旧指标不再作为当前操作说明。

### 纯在线心跳诊断

`--online-only --candidate-heartbeat-diagnostics` 开启服务端心跳分段观测。生产环境默认关闭；直接启动 Gateway 时对应 `IM_V2_GATEWAY_HEARTBEAT_DIAGNOSTICS=true`。按完整连接 UUID 的进程内哈希固定选择约 1/64 的连接，该连接的全部心跳形成同一采样群体；不能只取轻量连接 UUID 的固定进程前缀。没有用户、连接或请求身份标签，不新增执行任务。

`im_v2_heartbeat_stage_milliseconds` 分别记录入站批次到分发、任务启动、ByteStream／Session／Registry／LeaseController 入口与返回、ACK EventLoop 入口及本地写完成。`server_total` 与其连续子阶段嵌套，不能重复相加。入口和返回包含并发运行时调度；Actor 正文单独计时。入站时间是解码批次最后一次使用的通道入站回调，包含其排队，排除内核、TLS 和客户端处理；分片／合并帧应按该批次边界解释。

`cohort="slow"` 仅包含服务端总耗时至少 25 ms 的同一批已完成采样，便于比较长尾中的阶段占比。累计计数用实际测量阶段的差值分析；在新慢样本到来时淘汰 30 秒以前的例子，最多保留 16 条最大慢样本，以 `# im_v2_heartbeat_slow_example` 注释导出匿名阶段明细与完成时间，分析时仍须按阶段窗口过滤。失败采样独立计数，不混入成功耗时。ACK 写完成仅表示本地传输完成，不能视为客户端收到。

开启诊断及 CPU 栈采样的运行用于定位，不用于容量或优化收益对比。先测阶段边界，再在稳定在线窗口使用 `profile_v2_owned_benchmark.py` 或 Time Profiler 附加本次压测拥有的 Gateway，明确采样 PID 与时间窗口。

同一诊断开关还导出 `im_v2_gateway_journal_checkpoint_failure_total`，将缓存当前性校验的失败拆为绑定缺失、过期、覆盖变化、代次变化、用户控制版本未补齐、checkpoint 缺失或落后；它只解释实际执行过的缓存校验，不代表全部恢复请求。`im_v2_gateway_journal_snapshot_fallback_total` 记录增量恢复前置条件失败和回放无效，不能将其与心跳失败等同。

`im_v2_gateway_journal_diagnostic_stage_milliseconds` 记录批量协调、证明查询、同步绑定检查、实际恢复、连接选择、用户快照、状态应用和安装的完成耗时。异步阶段包含 SQL 等待、Actor／运行时调度；父子阶段重叠，不能相加或当作 CPU 用时。至少 5 ms 的匿名阶段以 `# im_v2_gateway_journal_slow_example` 注释给出开始、结束时间，最多保留最近 30 秒内的 64 条较慢阶段；与同节点慢心跳按时间关联只提供相关性，因果判断仍需 CPU 栈或控制变量对照。关闭诊断时不建立阶段记录、不查询额外数据库、不创建任务。

### Journal 控制恢复

在线连接注册时计算一次用户分区和二进制用户／设备身份；退出及注册回滚同步维护索引与本地控制版本。恢复只捕获目标分区的生命周期票据，快照安装仅更新该批身份。连接排序使用 UUID 字节，不反复格式化字符串。

远端恢复与本地冷刷新共用 `GatewayJournalRecoveryCoordinator`：同一 source、发布者、路由、会话与兴趣代次合并执行，最多四个实际恢复任务。晚到的更高 cut 或控制版本不能由旧结果完成，需要后续轮次。缓存只在当前绑定、截止时间、版本要求和本地连接代次仍有效时使用；取消一个等待者不撤销其他等待者所需的实际执行，关闭等待实际任务退出。

维护轮次按实际来源数据库批量读取活跃分区的来源身份、Publisher 租约和 Journal cut，一条 SQL 使用同一语句 MVCC 快照；不读取用户／设备，不开启显式事务，不做 JSON 编解码。每个证明的单调截止时间从请求开始计算，逐分区使用时再次检查来源与路由代次；不能用批量读取时的判断覆盖后续失效。请求准备复用仍有效的本地来源代次，缓存命中或加入共享恢复不再逐请求查询来源数据库；实际恢复任务重新验证来源。批量观察到租约缺失或来源身份变化时，只撤销查询前捕获的旧代次，迟到结果不能撤销后继绑定。已由实时流推进且当前 floors 覆盖的 checkpoint 可以推进缓存证明；无变化回放直接续用当前投影，避免重新安装产生短暂未就绪状态。

Journal 分块每项只计算一次保守内存预算，线性累计数组与条目成本，保留原有条目上限和包头预留。控制条目与房间 head 使用固定字段预算，授权条目按实际 viewer 数量累计，不经过反射。预算不是 PB 字节长度；传输边界继续检查实际编码包上限。

`im_v2_gateway_journal_recovery_total` 记录固定原因：请求、缓存命中、合并、实际执行、后续轮次，以及首次基线、代次变化、本地连接变化、版本要求推进、绑定不可用和回放结果。原因计数存在重叠；`executed` 才是实际执行轮次。`incrementalLoaded` 表示选择性读取轮次，`selectedConnections` 是实际数据库读取涉及的连接票据累计数；`sourceProofQueries` 和 `sourceProofPartitions` 分别计证明查询次数及请求分区数，不能将这些不同单位直接相加。压测对照需关闭心跳诊断和 CPU 采样，并保持全部连接及数据库配置相同。

### 在线规模相关的增量处理

Journal 匹配直接查询接收者已有的 `interests` 字典，不逐条构造订阅 Set。Gateway 普通订阅更新维护唯一增删队列，只形成最多 128 项的实际差异；完整收集和排序只用于首次／换代快照。Shard 先验证整批变化并预留预算，再更新受影响的订阅、反向索引与缓存预算；拒绝、重复批次和旧 generation 删除不会部分改变索引。稳定维护不再重新生成完整 desired 字典。Gateway 已安装订阅和 Shard 会话订阅使用 Swift Collections 持久化字典，发布的快照共享树结构，增量更新只复制受影响的树路径，不触发普通 Dictionary 的整表写时复制。

激活等待者按 topic／分区索引，完成、取消、失败和关闭都会移除反向索引。待恢复 topic 使用去重 FIFO，每次取最多 128 项，不反复排序全部剩余项；移除订阅会同步移除队列项，不积累失效票据。

本地连接版本变化与来源权威换代分开：同来源、发布者、路由及控制会话下，可以保留旧连接生命周期的已验证基线。新增生命周期必须读取自身的账号／设备状态；连续 Journal 中发生变化的既有用户也必须读取。覆盖撤回后旧基线只能用于可信恢复准备，不能授权发送；过期、来源换代和控制会话换代都不能复用。

协调的快速证明／续用与冷恢复采用分别持有的生命周期任务。冷恢复去重且最多四个实际轮次，不创建逐连接维护任务；失败由下一次真实维护事件重试，不立即循环。快速证明不会等待用户快照完成。连接变化唤醒期间复用五秒观测周期内仍有效的保守来源证明，新增分区或已过期证明才提前查询；实际冷恢复仍独立核对数据库发布者。Ready 屏障检查本地连接版本，不能仅凭已有账号 floor 跳过新设备生命周期初始化。关闭时取消并等待两个任务及共享恢复 Owner。

生产装配启用连续控制进度判定：所有物理来源的绑定、控制 checkpoint 和已确认投递会话都仍有效时，省去周期性逐 topic head 重读；首次订阅、失败重试、断档／过期和换代仍执行权威恢复。此机制依赖已有持久化 wake 与可靠投递重试，不将 TCP 心跳或节点存活当作消息／权限证明。性能变化必须由新一轮同配置对照验证，不能复用前一版本的 CPU 收益。
