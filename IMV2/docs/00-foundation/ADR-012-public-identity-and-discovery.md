# ADR-012：公开身份、联系人发现与目录边界

## 状态

Accepted — 2026-07-25

2026-09-27 更新：成员目录与资料展示按[资源系统实施记录](../../../docs/proposals/resource-system-implementation.md)分离。本文包含尚未提交的 protocol 32 协调升级行为，不表示旧客户端已兼容。

## 背景

V2 的 `user_id` 是只供协议、授权和持久化使用的不透明 UUID。当前密码
fallback 的 `account_handle` 仅是登录标识；它没有被定义为可公开查询的身份。
历史客户端曾让用户输入内部 UUID，并将房间 ID 的后缀作为会话标题。这不满足
常规聊天的私聊、拉群和群成员展示需求。

不能由客户端把本地备注、UUID 或登录标识伪装成公开昵称：这样会造成跨设备不一致，
也会把认证凭据/账号枚举策略意外变成产品协议。电话、邮箱、通讯录和模糊搜索还会
引入额外的同意、发现、反枚举、地区合规及删除规则，不能在没有决定时加入。

## 决策

采用 A：独立公开 `@handle`、精确匹配查询、可修改显示名。`user_id` 和
`account_handle` 均不得以“联系人名”形式暴露给产品 UI 或目录 API。

| 选项 | 身份与发现 | 安全/产品后果 |
| --- | --- | --- |
| A（建议） | 独立的公开 `@handle`，精确匹配查询；另有可修改显示名。登录 handle 与公开 handle 不复用。 | 能支持常规私聊、好友与拉群，同时不扩大密码登录标识暴露面。目录必须限流、无前缀/模糊搜索且不泄露屏蔽/隐私原因。 |
| B | 复用当前 password `account_handle` 作为公开 `@handle`。 | 实现较少，但把登录标识变成可发现数据，增加凭据填充、钓鱼和账户枚举风险；仅在安全策略明确接受后可选。 |
| C | 无公开目录；通过已认证好友、一次性 QR/邀请或人工交换的联系人码建立关系。 | 隐私面最小，但首次私聊/拉群体验需要额外邀请流程，不能保留当前 UUID 输入作为最终产品 UI。 |
| D | 手机号、邮箱或通讯录发现。 | 需要单独的验证、哈希匹配、用户同意、可见性、删除、反枚举、地区合规和滥用处理 ADR；不属于本 ADR 的默认范围。 |

## 已接受的不变量

首发版本的可执行规则如下：

- `user_id` 永不变且只用于内部授权/持久化；公开 handle 和显示名均不能替代它。
- 登录凭据和公开身份分表保存。密码 verifier、Passkey credential、refresh
  credential、电话或邮箱不能写入公开身份投影、群事件、Push、日志或指标。
- handle 仅支持精确、规范化查询；不得提供前缀、模糊、批量或未认证查询。请求
  需认证、限流、最小响应、`no-store`，且“未找到、不可发现、被屏蔽、无权查看”
  使用同一外部可见结果。
- 精确 handle 发现返回绑定查询账户、设备和 handle 的独立短期结果，最长 60 秒且
  不晚于认证截止。它只允许当前发现页面展示，不授权头像下载，也不能替代关系或群
  上下文。客户端扣除完整往返耗时，到期、修改输入、后台或离页清除；不自动轮询目录。
- 只有满足已批准的可见性策略的用户才能收到公开资料。群成员目录仅返回成员标识、
  角色与分页事实；可见成员的资料通过携带完整房间上下文的有界接口取得，并具有独立
  展示期限。资料同步投影也必须由服务端授权产生，持久内容不能替代当前展示授权。
  陌生人是否可按 handle 发现，必须作为明确的服务端策略，不能由 App 缓存决定。
- 显示名已有 UTF-8 长度、Unicode 规范化和可同步的幂等变更规则。当前首发范围的
  公开 handle 在注册后不可修改，且没有面向用户的账号/公开资料删除接口；因此不得
  推断 handle 的改名频率、旧值保留、删除或复用语义。若要支持这些行为，必须先通过
  单独 ADR 决定不可逆数据、关系、历史消息和旧 handle 的处理，再实现权威冲突检查与
  同步事件。

首发实现将公开 handle 规范化为 3–32 位小写 ASCII 字母、数字或下划线（输入
可带一个 `@` 前缀），显示名采用 NFC 并限制为 1–80 UTF-8 字节、禁止控制符和
换行。目录仅接受已认证设备的单个精确查询；默认额度为每用户 60 秒 30 次，且
响应使用 `no-store`。未找到和目标已屏蔽查询者均返回相同的 `404`；查询者自己已屏蔽
的目标仍可按现有精确查询策略解析，以支持解除屏蔽，这不授予新的私聊或群操作权限。公网 HTTPS
边缘仍必须按可信 IP/客户端做独立限流，不能把内部账号服务的用户额度当作唯一
防护。

## 影响范围与实施门槛

需要作为完整纵向能力交付，而不是仅替换 SwiftUI 文案：

1. 已实现的第一阶段：SQL profile/唯一 handle/查询额度、Core 身份类型、认证
   目录路由、密码注册的原子 profile 创建、仅本人可读/写的显示名 API、ClientKit
   HTTPS 客户端，以及 iOS 的资料设置、私聊、建群和拉成员 `@handle` 解析。
2. 第二阶段经资源系统迁移：`ListRoomMembers` 保持最多 100 人的 seek 分页和 active-
   member 授权，条目只含成员标识和角色。App 对可见行另取房间上下文资料；这不是
   roster sync，不会为显示名变化生成 O(n²) 成员投影。显式通过 `@handle` 打开的
   私聊可以保存对端与 room 的绑定作为查询线索，列表和详情页通过当前展示授权取得
   名称；本地旧内容不延长授权，未知资料保守降级，不以 UUID 充当名字。
3. 第三阶段已实现一对一会话的初始同步基线：创建 direct room 时，单一事务向双方
   各写入一条仅含对方公开资料的用户同步记录；snapshot reset 从当前 active direct
   pair 权威重建同一有界投影。客户端以该服务器投影覆盖本地显式解析缓存；该内容
   不作为无限期展示权限。群成员目录和按可见范围批量读取的资料分离，绝不写入
   roster sync。
4. 第四阶段已实现既有 direct 会话的显示名增量投影：账户服务把资料修改和唯一
   `public_profile_update_outbox` 源记录放在同一事务；网关以“每轮最多 N 个接收方”
   的预算枚举 direct pair，并在每页全部落到目标用户分片后才推进 checkpoint。进程
   在 checkpoint 前中断会重投同一页，但 `(接收者, source event, kind)` 幂等键不
   会重复可见记录；迁移期间仍由既有 shadow-forwarder 写入当前 owner 和 forwarding
   target。群成员资料按完整上下文、可见范围和期限读取，绝不变成 roster sync。
   离线/多设备交付走既有 user-sync 与 live-sync hint。iOS 联系人页只可对本地
   `pending`/`accepted` 关系发起有界（最多 100 条）`relationship` 上下文资料读取；
   这不是目录、通讯录发现或 UUID 批量查询，关系消失后同一读取立即不可用。仍需对删除、
   handle 改名、隐私策略和容量阈值做单独的产品与压测回归。
5. 覆盖规范化冲突、重放、并发抢注、屏蔽/不可发现、目录限流、离线重试、隐私
   日志和真实账号服务 HTTPS 回归。

## 发布门槛

电话/邮箱/通讯录发现需另行批准，不能作为本方案的隐含扩展。显示名变更现在会
可靠进入既有 direct 接收方的 user-sync，并以 live-sync hint 尽快唤醒在线设备；
设备离线时由其既有 cursor 在下次同步拉取。snapshot reset 仍从权威 direct pair
重建资料作为修复基线。群聊显示名通过可见作者补充和按需资料读取刷新，展示期限
到期必须重新授权；群昵称事件只携带主体与失效版本，不含昵称正文。该机制不因资料
变化生成全量成员资料同步。作者主动补充仍受部署开关与预算限制，HTTP 回退沿用
相同权限；完整容量与剩余旧入口的验收范围见资源系统实施记录。
