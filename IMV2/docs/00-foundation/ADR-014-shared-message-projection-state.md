# ADR-014：消息投影正文单写与用户窄引用

状态：已被房间日志唯一模型替代，保留历史背景
原决定日期：2026-08-17

## 原始问题与历史样本

原模型将完整消息 JSON 写入每位接收者的每个个人快照版本，正文和索引成本随接收者增加。
当时样本约 202 万 projection rows、99.7 万条不同消息、约 2.5 GiB relation，正文逻辑字节
约 1.33 GiB，直接消息接近完整双份。这些是旧版本样本，不代表当前实现的容量或吞吐。

原方案将正文保存为共享消息状态，每用户保留窄引用，再通过 join 恢复个人快照。
它降低了正文复制，但仍保留逐用户公共消息事实、跨用户分片状态复制及升级回填工作。

## 替代决定

当前实现将公共消息及其变更统一保存在房间日志，个人同步与个人快照仅保存用户状态。
`user_projection_versions` 不再引用消息状态；用户分片迁移不复制公共消息正文或共享引用。
用户权限、成员撤销、自己的已读水位及其他个人事件仍可靠投递，不因删除公共投影而丢失。

房间自身的消息 revision state、正文压缩和 GC 继续按实际房间库维护，服务于当前房间内容。
房间事件和消息行两种接受存储表示属于同一当前契约，不是新旧部署的兼容路径。
内容读取结合当前成员资格和事件发生时成员区间；共享状态存在本身不能授予访问权限。
事件身份、版本和幂等收据仍须一致，不通过跨数据库读取去补齐个人快照中的公共内容。

项目尚未上线：历史 expand、dual、backfill、shared、contract 升级流程及相关 SQL 已删除。
新数据库仅从[规范 schema](../../sql/schema.sql)初始化。当前运行要求见
[房间日志运维](../10-operations/room-read-model-rollout-runbook.md)和
[个人快照运维](../10-operations/personal-snapshot-runbook.md)。

## 历史性能边界

旧样本平均 payload 约 698 B，原方案曾据两名直接消息接收者估计正文 heap/TOAST 接近减半；
这只是当时结构的容量假设，不能套用到当前房间日志模型。

一次旧版本的 1,000 连接、1,000 msg/s、no-sync ceiling A/B 中，关闭 admission 仅把 ACK
从 28,611 提高到 30,981，同时 p95 变差，仍未达到当时延后投影排空版本的 34,240。
该记录不证明当前版本的吞吐或延迟；当前验收必须固定负载重新测量 WAL、写入行数、
CPU、p50/p95/p99 和客户端追赶时间，参见[容量验收](../09-capacity/standard-100k.md)。
