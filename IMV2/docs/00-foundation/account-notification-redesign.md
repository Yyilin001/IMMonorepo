状态：本轮 Mac 与服务端改造、部署和验证已完成（2026-11-05）。不保留历史协议或旧 schema 兼容分支。真实 APNs 与手机测试按用户要求延期；客户端高负载补读仍有明确的限流瓶颈，见最终结果。

范围调整（2026-11-05）：用户明确回复 APNs 密钥“先不管这个，预留就行”。本轮保留通知责任、投递接口与配置边界，不接真实 APNs、不要求提供密钥，也不把真机 APNs 展示作为本轮完成门槛；不得将持久化待办测试描述为真实推送成功。1000 房间重连与消息一致性验证仍须完成。

## 必须达到的结果

- 房间唯一 Actor 继续拥有接受消息、成员权限与房间序号分配；不引入第二个房间写入者。
- 接受确认意味着消息和分发意图均持久化；同步提交、fsync 和 WAL 保证不降级。
- 账号在没有在线设备、没有房间实时订阅时，仍有持久化变化与可见通知任务。
- 1000 房间的普通重连恢复账号通道及增量游标，不再安装全部房间 Owner 订阅。
- 仅正在查看的房间保留详情/输入状态等按需订阅。
- 离线通知是 APNs alert，静默 wake 仅用于优化，不是消息正确性或展示提醒的前提。
- 多设备、退群/重入、设备撤销、租约过期、跨库重试和旧实例延迟响应不能扩大权限或丢失任务。
- 本轮验证无连接时的持久化通知责任与故障恢复；真实 APNs 联调留待配置密钥后进行。1000 房间重连测试仍须完成。

## 持久化边界

房间提交：消息/完成记录 + `room_dispatch_outbox` 同事务，保存事件身份、消息身份、房间序号、成员修订、发送者、提及集合及创建时间；不复制正文，不逐成员展开。普通私聊合批在原单语句 CTE 内追加意图，不新增每条消息 COMMIT。

异步分发：按提交时 `joined_revision <= membership_revision < left_revision` 的历史区间分页枚举，包含发送者以同步其其他设备。每页只有在所有账号目标已持久化后才推进源游标；目标用稳定事件/账号身份去重。到期租约不能确认或删除后继工作。源意图不引用可裁剪消息行。

账号域：复用现有 user_sync_log 持久化游标、user_state_event_receipts 回执和 user_sync_wake_outbox 通知，新增 room_head 投影。用户归属路由围栏下，同一目标事务保存去重回执、账号序号、日志、唤醒和 account_notification_outbox；来源页确认丢失后不会重新分配序号或重建已消费通知。投影快照按 room_sequence 单调合并，不能作为成员权限；消息正文仍以房间日志为权威。

其他房间变化：room_events_account_dispatch 语句触发器捕获非 message.accepted 事件（含编辑、撤回、表情及房间控制），与日志同事务写入不含消息通知的派发项。删除经过保留期围栏的旧日志不会删除派发项。消息接受仍在原 CTE/事务显式提供消息、发送者和提及事实，避免触发器重新解码正文。

客户端：room_head 应用与个人游标同 SQLite 事务提交，并持久排入房间补读队列；保留最高水位，不能推进正文游标或授予权限。快照只写影子表，ACK 激活后使目录扫描失效，按页读取权威房间状态；普通重连复用同账号/安装的目录进度与完成态。

推送域：持久化通知计划独立于在线订阅，根据当前撤销/账号状态、通知偏好、已读和设备状态决定发送。不能仅用“某台设备在线”永久抑制另一台设备提醒。APNs 成功仅表示提供方接受；重试可能产生重复提醒，不能宣称端到端 exactly-once。

## 真实测试中发现的问题与修复

- 真实账号快照暴露 SDK 已有缺陷：`direct_read_receipt` 服务端实体键规范化为小写 UUID，客户端错误按载荷原始大小写比较。统一为服务端键规则，保留严格的快照键/排序校验；回归先复现失败，再验证修复，旧隐私隐藏版本不会因恢复而重新可见。
- 第一轮五分钟 100 条/秒：1000 发送者全部认证，30,000 条全部 ACK，发送错误/心跳超时/发送队列溢出均为 0；但房间派发队列持续增长，发送结束后约 128.7 秒才排空，120 秒验收截止失败。此轮不得作为实时吞吐通过。
- 第一轮收尾后逐房间核对 1000 个测试私聊共 60,080 条消息，消息数量、按房间顺序的消息 ID/正文 MD5 聚合和权威房间游标完全一致（包含本轮 30,000 条）。Mac 本地另有 2 个原有会话，共 60,107 条消息。
- 正在优化分发存储：最终接收者页提交后，在同一带租约围栏的 SQL 内检查剩余历史成员并直接完成任务，省去每条私聊再认领空页；读取接收者合并租约检查；账号 room_head 在原检查点事务锁内，用单条依赖 CTE 提交序号、回执、个人日志、唤醒和通知责任，不新增房间写入者、不合并不同房间的消息提交、不降低持久化。

- 分发优化数据库回归：`dispatch-optimized-tests-2.log` 7 项通过，包括 12 个不同事件各并发重放 3 次，最终仅 12 个回执/日志/通知，账号序号连续且每次重放返回同一序号。
- 广泛并发运行 214 项 SDK 测试时，12 个时序断言因调度延迟失败；降低测试并行度后，恢复/回执 34 项与剩余截止时间 2 项均通过。未放宽原断言。直接回执快照修复前两组参数均复现，修复后通过。

## 账号分发瓶颈定位（2026-11-05，提交 00ce3f32 后）

本轮只诊断，没有部署代码或调整数据库参数。沿用同一批 1000 个私聊和正式 Mac Release SDK，以每秒 100 条发送 180 秒。采集 PostgreSQL 活动与阻塞关系、数据库累计统计差值、网关指标、90 秒全机 CPU 采样，以及每秒磁盘和 CPU 指标。采样有额外开销，本轮不是优化效果对照，也不能替代跨多个 checkpoint 周期的长测。

### 复现结果

- 18,000 条消息全部确认；发送失败、心跳遗漏和发送队列溢出为 0。
- 源分发队列采样峰值 1,050 条，最老等待 11.46 秒；发送结束后 6.31 秒观测到源队列清空，7.00 秒完成 Mac 同步。
- 1000 个房间累计 258,080 条消息的数量、按序消息 ID/正文摘要、房间游标、会话摘要全部一致。
- Mac RSS 采样峰值 94.73 MiB；网关与 PostgreSQL CPU 峰值分别为 167.04% 和 144.60%（一个逻辑核心为 100%）。服务器为 4 个逻辑核心，没有容器 CPU quota，也未发生 CPU throttling 或 OOM。
- 原监控中的 `projection=2723` 是对整个 `user_state_event_outbox` 的行数统计；本轮核对全部为 `delivered`，不是 2723 条待处理积压。所有账号投影 checkpoint 都是 `ready` 且无失败码。以后应按状态区分，不能用此总行数判断投影阻塞。

### 已证实的阻塞与放大点

1. **通知追加与快照投影共用 checkpoint 行锁。** `PostgresV2UserStateEventProjector.projectRoomChanges` 先锁定 `user_projection_checkpoints`；`PostgresV2UserProjectionWorker.runOnce` 也锁同一行，并在整个逐条快照折叠期间持有。活动采样捕获通知端 `SELECT ... FOR UPDATE` 等待 `transactionid`，最长观测等待 310.23 毫秒。另一次连续 90 秒、每 100 毫秒采样的阻塞追踪中，900 个采样时刻有 134 个出现阻塞，其中 125 个“等待方/阻塞方”观测是 checkpoint 等待快照投影；该子窗口最长为 106.83 毫秒。SQL 形状确认持锁方正在查询、更新或插入 `user_projection_versions`，不是凭 CPU 使用率推测。
2. **批量事务内仍有大量逐条 SQL。** 一个源私聊消息产生发送者和接收者两个账号事实。18,000 条消息对应 36,000 个账号事实，`user_state_projection` 观测到 20,201 次目标事务借用、112,402 次事务体 SQL；平均每个目标事务仅 1.78 个事实。公共接收者可以在一轮中合并，但随机发送者大多仍是单条事务。每个目标事务初始化/锁定 checkpoint，每个事实另做回执查询和写入 CTE。快照中的每个正常递增 `room_head` 又逐条做成员状态查询、读取当前版本、关闭旧版本、插入新版本，网络往返与事务持锁时间持续累积。借用统计中的 SQL 计数不包含由 Fluent 外层执行的 BEGIN/COMMIT，不能把它当作数据库总语句数。
3. **8 条一组的分阶段等待会传播慢请求。** `V2RoomDispatchWorker` 领取最多 8 条后，先等全部收件人查询，再等全部账号目标写入，再等全部源确认，才领取下一组。一个热点账号的锁等待会延迟该组其他任务及后续房间。账号路由池、投递池各 4 个连接，路由事务等待目标写入期间继续占用连接。账号投影观测的平均准入排队约 0.59 毫秒、进入驱动阶段约 0.88 毫秒，尚不支持把“连接池太小”作为唯一或首要结论；池容量与分阶段调度是放大因素。
4. **频繁持久化提交产生了真实的 WAL 等待。** 约 230 秒全库采样窗口内增加约 18.69 万次事务提交、9.12 万次 WAL 同步；包含认证、后台维护、其他链路及采样查询，不能直接宣称每条业务消息固定产生这些次数。2,141 个活跃会话观测中，734 个处于 `WALSync` 或 `WALWrite` LWLock 等待，约 34.3%；这是会话采样占比，不是单条消息耗时占比。SQL 之间还存在 Swift/Fluent 调度与序列化开销，CPU 采样呈现 PostgreSQL 解析/内存分配和 Swift 引用计数/调度等分散热点，没有发现一个独占 CPU 的业务函数。

## 账号日志与快照解耦（2026-11-05，schema82）

房间 Actor 的接受事务、房间序号和历史成员权限仍是权威。此轮将房间提交后的账号分发改为按账号存储分片追加日志；不把不同房间的权威写入合成一个事务。

- 账号追加只锁定 `user_sync_sequences`，按稳定的用户 UUID 顺序取得多个账号的写入序号。一个存储分片事务批量校验回执、分配各账号连续序号，并同时写入账号日志、幂等回执和离线通知责任。重放不重复分配序号、不重新创建已消费通知。
- 快照消费者只持有自己的 `user_projection_checkpoints`。连续 `room_head` 先批量读取当前状态和成员撤销状态，按账号序号验证单调性，再批量关闭和插入版本。保留每个有效中间版本的序号区间，控制记录切断批次，退群与可见性控制保持原有顺序。
- `user_projection_ready.revision` 是短事务结束时使用的调度信号。每次追加递增修订号，消费者只有在修订号未变且后续日志为空时才能删除它；如果删除先提交，追加会重新创建信号。消费者不在快照折叠期间锁住该信号，也不再锁账号写入序号。
- 分发器最多并行推进两组、每组至多 32 个源任务；收件人查询保持有界，每次目标写入最多 1024 个账号事实、每账号最多 32 个事实。各目标存储分片独立提交，源批量确认仍校验租约 token、期限、旧游标和历史成员区间；未提交目标继续由持久源任务负责重试。

新程序要求 schema82，不保留 schema81 运行兼容路径。[离线升级 SQL](../../sql/upgrade-account-journal-schema82.sql) 保留现有数据，必须在停止业务写入后执行；全新安装使用当前 schema。`user_sync_sequences` 的 0 只用于追加事务中首次初始化写入锁，成功追加前必须分配正序号，失败时整个事务回滚。

本次 SDK 调整：

- 状态、最新可见摘要和完成判断各按最多 100 房间进行有界 SQLite 事务；正文最多 16 房间一次事务，复用原来的逐房间验证与投影逻辑。

- 每个房间都在事务内校验个人流 generation、成员资格、Owner epoch、请求修订和消息序号。任一房间发生抛错则整批回滚；旧响应不会借用新成员资格越权提交。摘要不能替代正文游标，也不能完成正文确认。
- 批次完全提交后才逐房间通知持久化进度；取消会等待已拥有的请求退出，再释放房间占用。没有修改服务端顺序、持久化配置、限流或权威写入方式。
